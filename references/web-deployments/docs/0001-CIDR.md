# 0001. CIDR 이해하기

> 시리즈: B6-1(과거 B3-1) "내가 만든 웹사이트를 인터넷에 올려 누구나 쓰게 하기" 과제 분석 문서.
> 이 과제의 모든 레포가 등장하는 네 가지 CIDR(`10.0.0.0/16`, `10.0.1.0/24`, `0.0.0.0/0`, `내IP/32`)을 하나씩 계산으로 풀이한다.

## 1. CIDR가 해결한 문제

과거 IPv4는 클래스 A/B/C(고정 마스크 8/16/24비트)로 네트워크를 나눠서, /17처럼 중간 길이의 네트워크를 만들 수 없었다. 클래스 A는 1600만 주소, 클래스 B는 6만5천 주소가 통째로 묶여 작은 회사에 클래스 B를 주면 수만 개의 주소가 낭비됐다.

CIDR(Classless Inter-Domain Routing, 1993, RFC 4632)은 "클래스 따위 무시하고 `/` 뒤 숫자로 네트워크 길이를 자유롭게 지정하자"는 것이다.

```
10.0.1.0/24
          └─ 네트워크 주소 비트 길이(prefix length)
```

## 2. IPv4 주소 = 32비트

IPv4 주소는 4칸(옥텟) × 8비트 = 32비트다. 한 칸은 0~255(8비트가 표현할 수 있는 모든 값)를 쓴다.

```
10 . 0 . 1 . 0
└────┬────┘└──┬──┘
 10.0.1.0 = 00001010 00000000 00000001 00000000  (32비트)
```

## 3. `/n`의 의미

`/n`은 **앞의 n비트를 네트워크 주소로 고정**한다는 뜻이다. 뒤의 `32-n`비트만 변할 수 있다.

| CIDR | 고정 비트 | 가변 비트 | 주소 개수 (2^(32-n)) |
|---|---:|---:|---:|
| `/16` | 16 | 16 | 65,536 |
| `/24` | 24 | 8 | 256 |
| `/32` | 32 | 0 | 1 |
| `/0` | 0 | 32 | 4,294,967,296 (전체 IPv4) |

핵심 직관: **`/` 뒤 숫자가 클수록 범위 작다.** (고정 비트가 많으면 변할 비트가 적으니까.)

## 4. 과제에서 실제로 쓰이는 CIDR 계산

### 4.1 VPC `10.0.0.0/16`

앞 16비트 = 앞 두 칸 `10.0` 고정. 뒤 두 칸(16비트)이 자유.

```
10.0.0.0   ~ 10.0.255.255
2^16 = 65,536개 주소
```

이 65,536개가 이 VPC 안에서 서브넷을 쪼개서 나눠줄 수 있는 전체 주소 공간이다.

### 4.2 Public Subnet `10.0.1.0/24`

앞 24비트 = 앞 세 칸 `10.0.1` 고정. 마지막 한 칸(8비트)만 자유.

```
10.0.1.0   ~ 10.0.1.255
2^8 = 256개 주소
```

AWS는 서브넷 주소 중 **5개를 예약**한다.

| 주소 | 용도 |
|---|---|
| `10.0.1.0` | 네트워크 주소(서브넷 자체를 가리킴) |
| `10.0.1.1` | VPC 라우터 |
| `10.0.1.2` | AWS 제공 DNS |
| `10.0.1.3` | AWS 향후 예약 |
| `10.0.1.255` | 브로드캐스트 |

그러므로 실제로 EC2 등에 줄 수 있는 주소는 **256 - 5 = 251개**다. EC2 1대만 올리는 과제에 251개면 충분 — 과하게 주지 않고 /24로 끝내는 이유가 여기 있다.

### 4.3 Route Table의 `0.0.0.0/0`

0비트만 고정 = **32비트 전부 자유 = 모든 IPv4 주소**. "목적지가 어디든"이라는 뜻이다.

Route Table에서 `0.0.0.0/0 → Internet Gateway`는 "VPC 내부(`10.0.0.0/16 → local`)로 가는 트래픽을 제외한 모든 트래픽은 IGW로 보낸다"는 기본 라우트다. 이 한 줄이 없으면 퍼블릭 IP가 있어도 응답 패킷이 나갈 길이 없어 사실상 프라이빗 서브넷이 된다.

### 4.4 Security Group의 `내공인IP/32`

32비트 전부 고정 = **IP 정확히 1개**.

SSH(22) 규칙의 소스를 `121.135.181.35/32`처럼 쓰면 그 IP에서만 SSH가 들어온다. `0.0.0.0/0`이면 전 세계 스캐너가 전부 시도하는 셈이므로, 관리 포트는 /32로 좁히는 것이 최소 노출 원칙이다. 단점도 명확하다: 카페·모바일로 가면 공인 IP가 바뀌어 접속이 끊키므로, 바뀐 IP로 규칙을 갱신해야 한다.

## 5. 포함 관계: 서브넷은 VPC 안에 들어가야 한다

`10.0.1.0/24`는 `10.0.0.0/16`의 일부다(10.0.1.x는 10.0.x.x 안에 포함). 서브넷은 VPC 대역 안에 완전히 들어가고 서로 겹치면 안 된다.

```
VPC 10.0.0.0/16          10.0.0.0 ~ 10.0.255.255
├─ public  10.0.1.0/24   10.0.1.0   ~ 10.0.1.255   (실제 사용)
├─ private 10.0.2.0/24   10.0.2.0   ~ 10.0.2.255   (확장 예시)
└─ ...       10.0.254.0/24                              (최대 254개 /24 가능)
```

`/16` 안에는 `/24`가 256개(2^8) 들어갈 수 있다.

## 6. 과제 연결

| 과제 구성 | CIDR | 역할 |
|---|---|---|
| VPC | `10.0.0.0/16` | 프로젝트 전용 주소 공간 확보 |
| Public Subnet | `10.0.1.0/24` | EC2 1대 배치에 충분한 최소 단위 |
| Route Table 기본 경로 | `0.0.0.0/0 → IGW` | "VPC 밖이면 전부" 인터넷 출구 |
| SG HTTP 80 | `0.0.0.0/0` | 웹은 누구나 접속 가능해야 함 |
| SG SSH 22 | `내IP/32` | 관리 포트는 본인만 |

13개 웹 배포 레포 모두 동일한 4개 CIDR을 사용했다. 차이가 있었던 것은 이 숫자의 *계산 과정*을 문서에 남겼느냐다(예: bangahee는 2^8 계산과 예약 주소 5개를 README에서 풀이했고, bllancck는 `docs/ipv4-cidr.md`를 별도 문서화, segretoo는 OCI VCN/서브넷에 `10.0.1.0/24`를 그대로 사용했다).
