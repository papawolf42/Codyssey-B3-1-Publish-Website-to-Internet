# 코딩 PBL 학습 운영 원칙 — B3-1 적용판

## 프로젝트부터 시작하되, 인프라 이해로 끝내기

[교육 목표와 범위](0004-educational-goals-and-learning-scope.md) · [수준별 확장 안내](0005-level-appropriate-expansion-guide.md) · [필수 요구사항](0002-required-checklist-and-extension-rules.md) · B1-1 적용판 (다른 로컬 저장소의 참고 자료, 이 Git 저장소에는 미포함)

> 이 문서는 42, PBL, 탑다운 학습, PRIMM에 관한 조사 원칙을 B3-1 AWS 실습에 적용한 제안이다. 42의 공식 규칙이나 Codyssey의 공식 평가표를 그대로 옮긴 문서가 아니다. 아직 AWS 리소스를 생성하거나 평가를 진행하지 않았다.

## 1. B3-1에서 배우려는 능력

겉으로 보이는 결과는 ‘웹사이트가 외부에서 열린다’이지만, 교육 목표는 다음 능력이다.

- 외부 요청이 IP·포트·라우팅·보안 그룹·웹 서버를 거쳐 응답으로 돌아오는 흐름을 설명한다.
- VPC·Subnet·Route Table·Internet Gateway의 역할을 구분한다.
- Security Group과 IAM, SSH 운영체제 인증을 서로 다른 보안 층으로 판단한다.
- 서버가 켜졌다는 것과 웹 서버가 요청을 처리한다는 것을 구분한다.
- 내부 성공·외부 실패를 증거로 나누어 원인을 좁힌다.
- 최소권한·필요한 포트만 공개·개인 IP 제한을 실제 구성에 적용한다.
- 생성한 자원의 수명·비용·삭제 순서를 관리한다.
- 다이어그램·접속 증빙·트러블슈팅 보고서로 자신의 구성을 재현 가능하게 설명한다.

따라서 콘솔에서 리소스를 생성했다는 사실만으로 학습 완료로 보지 않는다. 반대로 AWS의 모든 서비스를 알아야 시작할 수 있는 것도 아니다.

## 2. 이 방식의 이름과 적용

B3-1에는 다음 학습 전략을 결합한다.

| 전략 | B3-1에서의 적용 |
| --- | --- |
| Top-down | 외부에서 포트폴리오를 여는 전체 요청 그림부터 본다 |
| Problem-Based Learning | 접속 실패나 권한 오류를 문제로 삼아 필요한 지식을 찾는다 |
| Project-Based Learning | 네트워크·서버·보안·문서·정리를 하나의 결과물로 통합한다 |
| Just-in-time learning | 현재 실패한 계층에 필요한 IP·라우팅·SG·Nginx만 먼저 배운다 |
| Deliberate practice | 정상·내부 성공·외부 실패·권한 거절을 작은 변형으로 비교한다 |
| PRIMM | 구성 예측 → 실제 관찰 → 설정 조사 → 작은 변경 → 독립 진단 |

이것은 ‘AWS를 아무것도 모르고 무작정 콘솔에서 클릭한다’는 뜻이 아니다. 비용·보안·삭제 위험이 있으므로 요청 흐름과 안전 경계를 먼저 설명하고, 승인된 작은 구성만 만든다.

## 3. 10가지 원칙을 B3-1에 적용하기

### 원칙 1. 기능보다 능력을 먼저 정한다

| 표면 작업 | 실제로 연습하는 능력 |
| --- | --- |
| VPC 만들기 | 네트워크 범위와 격리 설명 |
| Public Subnet 만들기 | 주소 구역과 외부 경로 구분 |
| IGW·Route Table 연결 | 요청과 응답의 경로 추적 |
| EC2 실행 | 컴퓨트 자원과 OS 서비스 구분 |
| HTTP 80 공개 | 필요한 서비스만 외부에 노출 |
| SSH 22 제한 | 관리 경로를 개인 IP로 제한 |
| IAM 사용자/Role | AWS 관리 작업의 최소권한 설계 |
| Nginx 설치 | 파일·프로세스·포트·로그 관찰 |
| 외부 접속 증명 | 내부와 외부 검증을 분리 |
| 정리 체크리스트 | 자원 수명·비용·운영 책임 관리 |

리소스 개수나 콘솔 화면 캡처 개수보다 각 설정의 이유와 실패 시 확인할 위치를 설명하는 능력을 본다.

### 원칙 2. 최종 요청 흐름은 먼저 보여주고 내부 구성은 고정하지 않는다

먼저 아래 흐름을 결과 그림으로 제시한다.

```text
외부 브라우저 또는 curl
        ↓
퍼블릭 IP : 80
        ↓
VPC → Public Subnet → Route Table → Internet Gateway
        ↓
EC2의 네트워크 인터페이스와 Security Group
        ↓
EC2 내부 Nginx : 80
        ↓
HTML / B1-1 포트폴리오 응답
```

공개할 조건과 검증 결과는 고정한다.

- 어떤 URL 또는 IP로 접속하는가.
- HTTP 200 또는 정상 페이지를 어떻게 확인하는가.
- 내부 localhost와 외부 접속을 어떻게 구분하는가.
- HTTP 80 공개·SSH 22 개인 IP 제한을 어떻게 확인하는가.
- 어떤 리소스를 만들고 어떻게 정리하는가.

반면 다음은 학습자가 선택할 수 있다.

- Ubuntu와 Amazon Linux 중 명세 범위 안의 선택.
- Nginx 설정 파일을 수정하는 방법.
- A 브라우저 검증과 B `/health` 검증 중 하나.
- 아키텍처 다이어그램의 도구·배치.
- 트러블슈팅에서 선택할 관찰 명령과 기록 방식.

보안·리전·SSH·정리처럼 명세가 학습 목표로 고정한 것은 선택 사항으로 바꾸지 않는다.

### 원칙 3. 자기주도와 방치를 구분한다

AWS 콘솔의 메뉴 위치만 알려주고 끝내지 않는다. 다음 순서로 지원한다.

1. 요청 그림에서 어느 계층을 확인할지 알려준다.
2. 명령·콘솔·로그 중 관찰 위치를 좁혀준다.
3. 관찰 결과가 의미하는 범위를 질문한다.
4. 필요한 개념만 설명한다.
5. 변경할 범위를 한 번에 하나로 제한한다.
6. 복구·비용·보안 위험을 확인한 뒤 실행한다.
7. 해결 후 동일하지 않은 작은 진단 문제를 도움 없이 풀게 한다.

안전 위험이 있는 AWS 작업에서는 ‘힌트만 제공’과 ‘무제한 실행 권한’을 혼동하지 않는다. 리소스 생성·삭제·포트 공개는 학습자의 의사와 범위를 확인한 뒤 진행한다.

### 원칙 4. 작동하는 작은 인프라 성공을 반복한다

처음부터 HTTPS·Docker·ALB를 붙이지 않는다.

1. 종이에 외부 요청부터 Nginx까지 흐름을 그린다.
2. EC2 내부에서 기본 Nginx `localhost` 200을 확인한다.
3. VPC·Subnet·IGW·Route Table의 실제 연결을 확인한다.
4. HTTP 80은 공개하고 SSH 22는 개인 IP로 제한한다.
5. 외부에서 퍼블릭 IP 응답을 확인한다.
6. B1-1 정적 파일을 배포하고 브라우저에서 실제 자원/API를 확인한다.
7. 승인된 한 가지 오류를 관찰하거나 실제 오류를 기록한다.
8. 증빙을 저장하고 전체 리소스를 정리한다.

각 단계는 앞 단계의 결과를 사용하지만, 실패 범위가 한 단계에 머물도록 한다.

### 원칙 5. 선택권과 제약을 구분한다

제약을 추가할 때마다 ‘이것으로 무엇을 배우는가?’를 묻는다.

- 서울 리전·Public Subnet·EC2·SSH는 공식 학습 범위다.
- HTTP 80 공개·SSH 22 제한은 보안 원칙을 학습하기 위한 조건이다.
- 모든 포트를 열거나 AdministratorAccess를 쓰는 것은 편의를 위한 우회이지 학습 방법이 아니다.
- Nginx 설정 방식·다이어그램 도구·검증 A/B는 합리적 범위에서 선택할 수 있다.
- Docker·HTTPS는 선택 보너스이므로 핵심 경로를 이해한 뒤 선택한다.

새 서비스를 추가하는 것이 더 실무적이라는 이유만으로 좋은 것은 아니다. NAT Gateway·ALB·RDS는 비용과 의존성을 늘리고 현재 교육 목표를 흐릴 수 있다.

### 원칙 6. 정상 접속보다 실패 구간을 발견한다

정상 브라우저 화면은 하나의 증거일 뿐이다. 다음을 구분한다.

- DNS가 주소를 찾지 못함.
- TCP 연결이 거부되거나 시간 초과됨.
- Security Group에서 차단됨.
- Route Table·IGW·퍼블릭 주소 조건이 부족함.
- EC2는 실행 중이나 Nginx가 중지됨.
- Nginx는 실행 중이나 포트·파일 경로가 잘못됨.
- HTML은 200이지만 CSS·JS·이미지·GitHub API가 실패함.
- IAM 권한 부족으로 AWS 관리 작업이 거절됨.
- SSH 네트워크 연결과 Linux 사용자 인증이 실패함.

실제 오류가 있으면 증상 → 가설 → 검증 → 조치 → 결과 → 재발방지를 남긴다. 오류가 없다면 사용자 승인과 복구 계획 아래 통제된 변경을 검토하되, 의도한 실험을 실제 장애처럼 꾸미지 않는다.

### 원칙 7. 평가를 설명·진단·대안의 시간으로 만든다

자기 점검 또는 동료평가에서 다음 질문을 사용한다.

1. 왜 이 Subnet이 Public인가?
2. IGW와 Route Table은 각각 어떤 문제를 해결하는가?
3. HTTP 80과 SSH 22의 공개 범위를 왜 다르게 했는가?
4. EC2 생성 권한 오류와 SSH 접속 오류는 어느 층의 문제인가?
5. localhost가 성공하고 외부가 실패하면 무엇부터 확인하는가?
6. Nginx 200이 포트폴리오 전체 정상의 증거가 아닌 이유는 무엇인가?
7. 이 구성을 다른 사람이 재현하려면 어떤 리소스 ID·규칙·순서가 필요한가?
8. 더 안전하거나 단순한 대안은 무엇이며 왜 이번 과제에서는 선택하지 않았는가?

질문자는 답변자의 지식과 함께 자신의 진단 순서도 배운다.

### 원칙 8. 협업은 구성 요소를 나누는 것보다 전체 경로를 공유하는 것이다

팀으로 한다면 한 사람에게 네트워크·한 사람에게 Nginx만 영구 배정하지 않는다.

- 네트워크 담당자가 Nginx의 localhost 검증을 설명한다.
- 서버 담당자가 SG·라우팅 조건을 설명한다.
- 문서 담당자가 실제 자원 목록과 삭제 순서를 검증한다.
- 한 사람이 만든 장애를 다른 사람이 로그와 설정으로 진단한다.
- 다이어그램을 그린 사람이 실제 콘솔 구성과 대조한다.

개인 학습에서는 구현하지 않은 계층을 말로 설명하거나, 기존 구성에서 한 설정을 찾아 역할을 적는 방식으로 대체한다.

### 원칙 9. AI를 클라우드 튜터로 사용하되 실행 권한과 판단을 맡기지 않는다

AI에게 다음을 요청할 수 있다.

- VPC·SG·IAM·SSH 용어 비교.
- 관찰할 콘솔 항목이나 안전한 읽기 명령 제안.
- 로그에서 확인할 후보 계층.
- 다이어그램과 보고서의 누락 점검.
- 새로운 작은 트러블슈팅 문제 출제.

AI가 제공한 명령과 정책은 바로 실행하지 않는다. 먼저 다음을 확인한다.

- 어느 리전에 적용되는가?
- 대상 리소스가 정확히 무엇인가?
- 읽기 명령인가, 변경·생성·삭제 명령인가?
- 비용이 발생할 수 있는가?
- 공개 범위를 넓히는가?
- 실행 후 되돌릴 방법이 있는가?

#### AI 없이 확인할 변형 문제

- IGW는 연결됐지만 Route Table에 기본 경로가 없는 경우의 조사 순서.
- Nginx는 localhost 200이지만 외부 접속이 안 되는 경우의 후보 세 층.
- SG에는 HTTP가 허용됐지만 서비스가 중지된 경우의 확인 방법.
- EC2를 종료했는데 EBS·EIP가 남아 있는지 확인하는 방법.
- IAM 권한 오류와 Linux `Permission denied`를 구분하는 설명.

### 원칙 10. 완료가 아니라 새로운 장애·구성으로 전이한다

완성한 구성을 그대로 다시 만드는 것만으로는 충분하지 않다. 다음과 같이 작게 바꿔본다.

- 기본 Nginx 페이지에서 B1-1 정적 파일로 교체.
- `/health`를 추가하되 브라우저 페이지 검증과 목적을 구분.
- HTTP 응답은 유지하고 특정 CSS 파일만 누락시켜 Network에서 찾기.
- 내부 localhost 성공·외부 실패 상황의 조사 순서를 설명.
- SSH 소스 IP가 바뀌었을 때 규칙을 안전하게 갱신하는 계획 세우기.
- 정리 체크리스트에서 의도적으로 한 항목을 미생성으로 표시하고 실제 목록과 대조.

전이 문제의 목표는 새로운 AWS 서비스를 많이 쓰는 것이 아니라, 같은 원리로 다른 실패를 해결하는 것이다.

## 4. PRIMM을 B3-1에 적용하기

| 단계 | 학습자 행동 | B3-1 예시 |
| --- | --- | --- |
| Predict | 실행 전 결과 예측 | Route Table에 기본 경로가 없으면 외부 요청이 어디서 막힐까? |
| Run | 승인된 작은 구성 실행 | EC2 내부 `curl localhost` 또는 읽기 전용 상태 확인 |
| Investigate | 설정·로그·경로 조사 | SG, Route Table, Nginx status/log를 비교 |
| Modify | 한 조건만 변경 | HTTP 규칙·파일 경로·서비스 설정 중 하나만 조정 |
| Make | 비슷한 구성·진단을 직접 수행 | 새로운 외부 접속 실패의 조사 계획 작성 |

비용·보안 위험이 있는 변경은 Run 전에 범위·복구·정리 방법을 확인한다. 실제 자원을 만들지 않고도 다이어그램과 통제된 로컬 실험으로 Predict·Investigate를 연습할 수 있다.

## 5. B3-1 실행 루프

### 단계 0. 전체 결과와 안전 경계를 본다

- 공식 제출물과 최소 아키텍처를 확인한다.
- 실제 계정의 프리티어·크레딧·권한·리전 조건을 확인한다.
- 만들 자원, 비용 가능 항목, 삭제 순서를 목록화한다.
- 아직 AWS 자원을 만들지 않고 요청 그림과 다이어그램 초안을 만든다.

### 단계 1. 서버 내부의 작은 성공

- EC2와 OS의 역할을 이해한다.
- Nginx가 무엇을 제공하는지 이해한다.
- `localhost` 200 응답과 프로세스·서비스 상태를 확인한다.
- 외부에서의 접속과 혼동하지 않는다.

### 단계 2. 네트워크 경로의 작은 성공

- VPC·Subnet·IGW·Route Table의 연결을 확인한다.
- 주소와 경로를 실제 설정과 다이어그램에 대응시킨다.
- HTTP 80과 SSH 22의 목적·소스를 분리한다.

### 단계 3. 외부 응답

- 퍼블릭 IP로 A 또는 `/health`로 B를 선택한다.
- 내부 성공·외부 성공을 별도 증거로 남긴다.
- B1-1 파일을 배포했다면 HTML·CSS·JS·이미지·API 요청을 각각 확인한다.

### 단계 4. 실패·수정·보고

- 하나의 실패를 관찰한다.
- 가능한 계층을 나누고 가장 값싼 읽기 확인부터 한다.
- 한 번에 하나의 조치만 수행한다.
- 변경 전후와 결과를 보고서에 기록한다.

### 단계 5. 정리·회고·전이

- 접속 증거를 먼저 저장한다.
- 실제 생성 리소스와 체크리스트를 대조한다.
- 승인 후 자원을 정리하고 남은 EBS·EIP·네트워크 의존성을 확인한다.
- 다음 날 같은 흐름을 말로 재현하고, 일주일 뒤 작은 실패 시나리오를 독립적으로 진단한다.

## 6. B3-1의 작동·이해·변형 단계

| 단계 | 작동하는 작은 성공 | 핵심 설명 | 독립 변형 |
| --- | --- | --- | --- |
| 요청 그림 | 외부→IP→포트→Nginx 흐름 | 각 계층의 역할 | 어느 지점이 없으면 실패할지 표시 |
| 네트워크 | Route Table과 IGW 연결 | 경로와 주소 | Public 이름만 있고 경로 없는 경우 |
| 보안 | HTTP 공개·SSH 제한 | SG·IAM·SSH 구분 | 각 오류의 조사 층 선택 |
| 서버 | localhost 200 | 인스턴스와 서비스 구분 | 서비스 중지·포트 변경 진단 |
| 외부 검증 | 퍼블릭 IP 정상 응답 | 내부/외부 증거 분리 | HTTP/경로/SG 가설 세우기 |
| 배포 | B1-1 파일과 자원 로드 | 서버와 브라우저 분리 | CSS·JS·API 하나만 실패시키기 |
| 트러블슈팅 | 보고서 한 건 | 증거 기반 수정 | 다른 실패의 조사 계획 |
| 정리 | 자원·비용 근거 확인 | 수명과 책임 | 남은 리소스 찾기 |

## 7. 지원을 줄이는 기준

| 수준 | 제공하는 도움 | 다음 단계 조건 |
| --- | --- | --- |
| 입문 | 요청 그림·용어·안전한 읽기 관찰 | 내부/외부 차이를 질문할 수 있음 |
| 초급 | 콘솔 위치·명령 목적·오류 후보 | 한 계층을 확인하고 결과를 해석함 |
| 중급 | 공식 문서·검증 기준·힌트 | 원인을 두세 후보로 좁힘 |
| 숙련 전환 | 증상·제약·완료 기준만 제공 | 새로운 구성/장애를 독립 진단함 |

지원량은 AWS 개념별로 다를 수 있다. B1-1을 잘해도 VPC는 입문일 수 있다.

## 8. B3-1을 평가한다면

공식 배점표가 아닌 학습 확인 제안이다.

| 영역 | 질문 |
| --- | --- |
| 동작 | 내부·외부 검증이 요구 방식으로 되는가? |
| 설계 설명 | 각 자원·규칙을 왜 만들었는가? |
| 보안 | 불필요한 공개·관리자 권한을 피했는가? |
| 진단 | 실패 계층을 증거로 좁히는가? |
| 전이 | 처음 보는 접속·권한·정리 변형을 설명하는가? |
| 운영 | 비용·삭제·남은 자원을 확인하는가? |
| 문서 | 그림·README·보고서가 실제 상태와 일치하는가? |
| 회고 | 무엇을 이해했고 무엇을 다음에 배울 것인가? |

정상 화면만 확인하거나 AWS 콘솔 캡처만 모으는 방식은 전체 학습 성과를 보여주지 못한다.

## 9. 회고 기록 형식

각 작은 성공이나 장애 뒤에 다음을 기록한다.

```text
이번에 작동한 요청 경로:
내가 확인한 자원·규칙·로그:
처음 세운 가설과 실제 결과:
변경한 것과 되돌리는 방법:
다음에 도움 없이 진단할 변형 문제:
아직 설명하지 못하는 것:
```

개인키·비밀값·세션 토큰·공개하면 안 되는 IP 정보는 회고에 기록하지 않는다. 필요한 경우 IP는 예시값으로 치환하고 리소스 식별 정보도 공개 범위를 검토한다.

## 10. 적용하지 않을 원칙도 명시한다

- 비용이 발생하거나 외부에 포트를 공개하는 것은 무작정 반복하지 않는다.
- 실제 장애가 없는데 제출물을 채우려고 장애를 조작하지 않는다.
- 명세에 없는 AWS 서비스를 많이 붙이는 것을 학습 성과로 보지 않는다.
- AI가 만든 IAM 정책·삭제 명령을 검토 없이 실행하지 않는다.
- 자동화 도구를 도입했다고 네트워크·보안·수명 주기 이해가 생겼다고 보지 않는다.
- 개인 경험담이나 특정 교육기관의 홍보 문구를 B3-1의 공식 평가 기준으로 사용하지 않는다.

## 11. 한 문장으로 정리

> AWS에 먼저 안전한 작은 요청 경로를 만들고, 필요한 개념을 역추적해 이해한 뒤, 실패를 증거로 진단하고, AI의 도움을 점차 줄이며, 마지막에는 새로운 장애와 정리 문제를 스스로 해결한다.
