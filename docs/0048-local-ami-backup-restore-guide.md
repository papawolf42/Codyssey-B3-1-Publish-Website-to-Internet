# 로컬 AMI 백업: 보관 상태와 나중에 복원하는 방법

> **백업 작업 이후의 후속 상태:** 사용자가 별도 승인·직접 실행으로 원본 EC2와 실습 네트워크를 정리했고 루트 EBS 부재도 확인했다. 아래 백업 단계의 ‘원본 보존’은 당시 범위다. 로컬 암호화 백업·복구키는 보존하며 AWS 재업로드·새 EC2 부팅 시험은 하지 않았다. [원본 자원 정리 결과](cleanup-checklist.md).

작성 기준: 2026-10-19 실제 백업·검증·임시 자원 정리 결과.

[실제 작업·캡처 기록](0047-ami-local-backup-worklog.md) · [과제 자원 정리표](cleanup-checklist.md)

## 1. 결론: AWS 백업을 지웠어도 복원 자료는 남아 있다

**암호화된 백업 파일과 복구키를 안전하게 가지고 있으면, 나중에 파일을 복호화해서 AWS에 다시 업로드하고 새 AMI·EC2로 복원할 수 있다.** AWS에 AMI·스냅샷·S3 파일을 계속 남겨 둘 필요는 없다. AWS의 임시 백업 자원을 삭제한 것은 PC 파일을 삭제한 것이 아니다.

다만 ‘로컬 백업이 확보돼 있다’와 ‘어떤 시점에도 즉시 원클릭으로 전체 서비스가 살아난다’는 다르다. 복원할 때 AWS 계정·필요 권한·비용·서비스 지원 조건을 확인해야 하고 네트워크·DNS·인증서도 점검해야 한다. 실제 재업로드·새 EC2 부팅까지 시험한 것은 아니므로 복구 성공을 이미 실증했다고 기록하지 않는다.

## 2. 어디에 무엇이 있나?

Windows 탐색기의 주소창에 다음 경로를 붙여 넣으면 된다. `.aside` 폴더가 숨김이어도 전체 경로로 접근할 수 있다.

```text
C:\Users\alsgu\.aside\u\0\backups\B3-1\20261019-01
```

이 폴더는 Git 저장소 밖에 있고, 생성 당시 현재 Windows 사용자와 SYSTEM만 접근하도록 ACL을 설정했다.

### 반드시 잃어버리지 말 것

- `ami-080ac9f0097d7ff75.bin.age`: 암호화된 AMI 보관 파일.
- `recovery\b3-1-archive.agekey`: 위 파일을 복호화하는 **비밀 복구키**. 분실하면 복호화할 수 없다. 이 문서에는 경로만 적었으며 키 내용은 기록하지 않았다.

### 함께 보관하면 편한 파일

- `manifest.json`: 파일 크기·SHA-256·출처·검증 상태.
- `verification.txt`: 검증 및 임시 AWS 자원 정리 결과.
- `Restore-LocalArchive.ps1`: 로컬 검증·복호화 도우미. AWS를 조작하지 않는다.
- `tools\age\`: age v1.3.2 portable 도구. 별도 시스템 설치 없이 사용한다.
- `README-복원방법.md`: 저장소가 없어도 백업 폴더 안에서 읽을 수 있는 복원 설명.
- `recipient.txt`: 공개 수신자 정보. 비밀 복구키를 대체하지 않는다.

백업의 age 복구키와 EC2 접속용 SSH 개인키(`.pem` 등)는 **서로 다른 파일**이다. SSH 개인키는 원래 PC에 있던 파일이므로 EC2 디스크 이미지에 자동으로 보관된 것이 아니다.

## 3. 무엇까지 검증했나?

### 완료

- 원본 EC2로 비공개 AMI 생성, `available` 확인.
- AMI를 S3 단일 파일로 보관하는 Store 작업 `Completed`, 100% 확인.
- PC 다운로드의 바이트 수·SHA-256을 S3 원본과 대조해 일치 확인.
- 로컬 파일을 age로 암호화.
- 실제 복원 도우미로 암호화 파일을 복호화하고, 원본 크기·SHA-256과 일치 확인.
- 원본 평문 이미지의 작업용 임시 사본은 정리하고 암호화 파일과 복구키 유지.
- 사용자 승인 후 이번 백업용 임시 AMI·스냅샷·S3 객체·버킷 삭제 확인.

### 아직 하지 않은 것

- 로컬 파일을 AWS에 **다시 업로드**하는 실제 복원 시험.
- 복원된 새 AMI로 EC2를 부팅해 SSH·HTTP·HTTPS까지 확인하는 전체 복구 시험.

따라서 상태를 한 문장으로 표현하면 **‘복원용 파일과 키를 확보했고 무결성·복호화 검증까지 완료했으며, AWS에서의 실제 복구 시연만 미실행’**이다.

### 파일 식별값

복호화한 원본 `.bin`:

```text
크기: 603450438 bytes
SHA-256: 7c9c9618f466f7fd7e30007db617ac6dd56df3cd771a28e75a10e0af16e7ea49
```

보관 중인 암호화 `.bin.age`:

```text
크기: 603597950 bytes
SHA-256: 186bb6595857d87b51223b903d0ec5ed1dbb1a6075daf0e5142ecdc5c1cf8e3f
```

SHA-256은 파일 손상·전송 오류를 확인하는 식별값이지 복구키가 아니다. 키 대신 위 값을 입력해 복호화할 수는 없다.

## 4. 나중에 복원하는 순서

### A. PC에서 검증·복호화

PowerShell에서 다음을 실행한다.

```powershell
Set-Location 'C:\Users\alsgu\.aside\u\0\backups\B3-1\20261019-01'
.\Restore-LocalArchive.ps1
```

- 도우미는 도구·암호화 파일의 해시와 복호화 결과의 크기·SHA-256을 확인한다.
- 성공하면 같은 폴더에 `ami-080ac9f0097d7ff75.bin`을 만든다.
- 기존 출력 파일이 있으면 덮어쓰지 않는다. 이미 있는 파일의 정체를 확인하고 무작정 삭제하거나 검증을 우회하지 않는다.
- 복구키를 따로 보관했다면 `-IdentityFile '실제 복구키 파일 경로'`로 지정한다. **키 내용 자체를 명령줄에 붙여 넣지 않는다.**
- 복구키·도구·파일이 없거나 해시가 다르면 중단하고 원인을 확인한다.

복호화한 `.bin`은 인증서 개인키 등을 포함할 수 있는 **민감한 원본 파일**이다. Git·공개 저장소·공개 S3에 올리지 않는다.

### B. 새 비공개 S3에 .bin만 업로드

1. AWS 계정과 리전 `ap-northeast-2`를 확인한다. 필요한 최소 권한을 점검하고 root 로그인을 복원 절차로 삼지 않는다.
2. 서울 리전에 작업용 S3 버킷을 준비한다. 공개 액세스 차단과 적절한 암호화를 확인한다.
3. 복호화한 `ami-080ac9f0097d7ff75.bin` **하나만** 업로드한다.
4. 이 예시 명령을 사용할 경우 객체 키도 위 파일명 그대로 유지한다. 다른 경로로 올렸다면 실제 객체 키로 명령을 바꾼다.

**`.age` 파일을 그대로 Restore API에 주는 것이 아니다. 복구키·recovery 폴더·백업 폴더 전체를 S3에 올려서는 안 된다.**

이전에 만든 임시 버킷은 이미 삭제했다. 새 버킷의 실제 이름을 사용해야 한다. 이 백업 형식의 AMI 복원은 S3를 경유하며, Store/Restore 작업에는 CLI·SDK·API를 사용한다.

### C. CloudShell/AWS CLI에서 새 AMI 복원

아래는 **나중에 실행할 예시**다. 첫 줄 버킷 이름은 반드시 실제 생성한 이름으로 바꾼다. 코드 블록은 CloudShell의 Bash 기준이며 PowerShell 줄바꿈 문법과 혼동하지 않는다.

```bash
RESTORE_BUCKET='실제로-생성한-비공개-버킷-이름'

RESTORED_AMI=$(aws ec2 create-restore-image-task \
  --region ap-northeast-2 \
  --bucket "$RESTORE_BUCKET" \
  --object-key ami-080ac9f0097d7ff75.bin \
  --name "b3-1-restored-$(date -u +%Y%m%dT%H%M%SZ)" \
  --query ImageId --output text)

printf 'Restored AMI: %s\n' "$RESTORED_AMI"
```

성공 응답으로 받은 새 AMI ID를 기록하고 상태를 조회한다.

```bash
aws ec2 describe-images \
  --region ap-northeast-2 \
  --image-ids "$RESTORED_AMI" \
  --query 'Images[0].{ImageId:ImageId,State:State,StateReason:StateReason}' \
  --output json
```

`pending`이면 기다렸다가 **상태 조회만** 다시 한다. 생성 명령 전체를 반복 실행해 불필요한 AMI·스냅샷을 중복 생성하지 않는다. `available`을 확인한 뒤 EC2를 생성한다. 실패하면 원인·잔존 자원을 먼저 확인한다.

원래 AMI ID `ami-080ac9f0097d7ff75`가 되살아나는 것은 아니다. 복원 AMI와 EC2·볼륨·스냅샷은 새 ID를 받는다.

### D. EC2와 네트워크·도메인 연결

- 복원 AMI의 `x86_64`·HVM 조건에 맞는 인스턴스와 필요한 용량·비용을 선택한다.
- VPC·공개 Subnet·IGW·라우팅·Security Group은 별도로 준비하거나 적절한 기존 구성을 선택한다. AMI가 이 외부 자원을 자동 복원하지 않는다.
- SSH 22는 **복원 시점의 내 공인 IP /32**로 제한한다. HTTP 80·HTTPS 443은 실습 목적에 맞게 설정한다.
- 접속할 SSH 키 페어와 보유 SSH 개인키가 맞는지 확인한다. age 복구키는 SSH 접속 키가 아니다.
- 새 EC2의 공인 IP를 확인한다. 과거의 `13.125.99.141`을 그대로 쓰면 안 된다.
- Cloudflare에서 `kodyssey.kr`의 승인된 A 레코드를 새 IP로 변경한다. 기존 메일·다른 서비스 레코드는 건드리지 않는다. 기존 A 레코드를 무작정 중복 추가하지 않는다.
- DNS 반영 후 SSH·Nginx·HTTP·HTTPS 동작을 실제 확인한다. Windows에서 HTTPS GET을 확인한다면 `curl.exe -i https://kodyssey.kr/`를 사용할 수 있다. 인증서 오류를 `-k`로 숨겨 성공으로 처리하지 않는다.

### E. 인증서 확인

백업 당시 인증서의 확인된 만료일은 **2027-01-17**이었다. 이미지를 복원해도 인증서 유효 기간은 연장되지 않는다.

- 복원 시 같은 도메인·유효한 인증서·개인키·설정이 갖춰져 있다면 기존 인증서를 사용할 수 있다.
- 만료됐거나 조건이 맞지 않으면 DNS와 서비스 상태를 맞춘 뒤 갱신·재발급을 진행한다.
- 자동 갱신 타이머는 백업 당시 `disabled/inactive`였고, 자동 갱신을 켜지 않기로 했었다. 복원만으로 자동 갱신이 활성화된다고 생각하면 안 된다.

## 5. 보관·비용·정리 주의

- **파일과 복구키를 같은 디스크 한 곳에만 두지 않는다.** 디스크 고장 시 둘 다 잃을 수 있다. 별도 안전한 저장장치 등에도 백업한다.
- 암호화 파일과 평문 복구키가 함께 유출되면 보호 효과가 사라진다. 복구키는 별도로 보호하고 공개 공유하지 않는다.
- 폴더를 다른 디스크·공유 폴더로 복사하면 기존 Windows ACL이 그대로 적용된다고 보장할 수 없다. 새 위치의 접근 권한도 확인한다.
- 로컬 파일 보관 자체에 AWS 저장료가 붙는 것은 아니다. 하지만 새 S3 업로드·요청·전송, 스냅샷·AMI 복원·EC2·EBS 등에는 비용이 발생할 수 있다.
- 실제 복원 후 사용하지 않는 작업용 S3·AMI·스냅샷·EC2·네트워크를 확인해 정리한다. 원본과 다른 프로젝트 자원을 혼동하지 않는다.
- 평문 `.bin`은 업로드·검증 후 더 필요하지 않으면 안전한 취급 원칙에 따라 정리한다. 평문 삭제가 SSD의 복구 불가능한 보안 삭제를 보장하는 것은 아니다.

## 6. 2026-10-19 정리 당시 상태

- 로컬 암호화 백업·복구키: 보존, 검증 완료.
- 이번 백업용 AMI·스냅샷·S3 객체·버킷: 삭제 확인 완료.
- 원본 EC2·EBS·네트워크: 삭제하지 않았음. 당시 EC2 `running`, EBS `in-use`, 외부 HTTPS GET 200 확인.
- 과제용 IAM 정책: 이번 백업 작업에서 변경하지 않았음.
- 원본 과제 리소스·DNS 정리: 별도 미완료 작업. **임시 백업 정리가 원본 과제 자원 정리 완료를 뜻하지 않는다.**

이 문서는 위 시점의 확인 사실과 미래 복원 절차를 구분한 참고 문서다. 이후 AWS 상태가 그대로라고 가정하지 말고 복원·삭제 직전에 다시 확인한다.
