## 1. 이 계획의 학습 목표

B3-1의 핵심 목표는 단순히 클라우드 콘솔에서 클릭 몇 번으로 서버 한 대를 띄우고 끝내는 것이 아닙니다. 웹 브라우저에서 서버까지 이어지는 네트워크 요청 경로를 직접 구성하고, 각 구간이 왜 필요한지 설명하며, 문제가 생겼을 때 증거를 바탕으로 해결하고, 실습이 끝나면 비용이 나오지 않도록 안전하게 정리하는 전 과정을 익히는 것입니다.

```text
외부 브라우저
  → Public IP : 80
  → VPC / Public Subnet
  → Route Table / Internet Gateway
  → EC2 네트워크 인터페이스 / Security Group
  → EC2 운영체제 / Nginx : 80
  → B1-1 정적 파일
  → HTTP 응답
```

학습이 끝났을 때 아래 내용을 스스로 설명할 수 있어야 합니다.

- **네트워크와 웹 요청의 기본**:
  - **Public IP(공인 IP)**: 전 세계 인터넷 어디서나 찾아올 수 있도록 공개된 컴퓨터의 고유 주소입니다.
  - **포트(Port)**: 한 대의 컴퓨터 안에서 웹 서버, 원격 접속 등 여러 프로그램 중 어느 프로그램으로 찾아갈지 구분하는 출입문 번호입니다.
  - **HTTP(HyperText Transfer Protocol)**: 웹 브라우저와 웹 서버가 웹페이지 문서와 데이터를 주고받기 위해 사용하는 표준 통신 규칙입니다.
  - **라우팅(Routing)**: 네트워크 패킷이 출발지에서 목적지까지 올바른 길을 찾아가도록 안내하는 과정입니다.
- **클라우드 네트워크의 뼈대**:
  - **VPC(Virtual Private Cloud)**: AWS 클라우드 내에 나만을 위해 독립적으로 격리해 놓은 가상 네트워크 공간입니다.
  - **Subnet(서브넷)**: 큰 VPC 네트워크 공간을 용도나 구역에 맞게 잘게 쪼갠 하위 네트워크 구역입니다.
  - **Route Table(라우팅 테이블)**: 네트워크 트래픽이 어디로 가야 하는지 목적지와 출구를 적어 둔 이정표 목록입니다.
  - **Internet Gateway(인터넷 게이트웨이, IGW)**: VPC 내부와 외부 인터넷을 연결해 주는 공식 관문 통로입니다.
- **실제 접속을 결정하는 조건**: 단순히 서브넷 이름을 '퍼블릭'이라고 짓는다고 접속되는 것이 아니라, 실제로 인터넷 게이트웨이로 이어지는 경로와 공인 IP, 방화벽 규칙이 연결되어야 외부에서 접속할 수 있다는 점을 이해합니다.
- **계층별 보안과 역할 분담**:
  - **Security Group(보안 그룹)**: 가상 서버로 들어오고 나가는 네트워크 트래픽을 허용할지 검사하는 가상 방화벽입니다.
  - **IAM(Identity and Access Management)**: 누가 AWS 서비스를 만들고 지울 수 있는지 관리 권한을 제어하는 시스템입니다.
  - **SSH(Secure Shell)**: 원격에 있는 서버 컴퓨터에 안전하게 암호화 통신으로 접속하여 명령을 내리는 프로토콜입니다.
  - **EC2(Elastic Compute Cloud)**: AWS에서 빌려 쓰는 가상 서버 컴퓨터입니다.
  - **Nginx(엔진엑스)**: 사용자의 웹 요청을 받아 HTML/CSS 파일 같은 웹 문서를 빠르게 전달해 주는 웹 서버 프로그램입니다.
  - 각 보안 장치와 소프트웨어가 서로 다른 계층에서 작동하는 이유를 설명합니다.
- **서버 상태와 서비스 상태의 차이**: EC2 가상 서버 컴퓨터가 켜져 있는 것과, 그 안에서 Nginx 웹 서버 프로그램이 80번 포트로 웹페이지를 정상 응답하는 것은 서로 다른 문제라는 점을 이해합니다.
- **내부와 외부 검증의 분리**: 서버 컴퓨터 안에서 테스트한 **localhost(자기 자신 컴퓨터를 가리키는 내부 주소)** 성공과, 외부 인터넷 브라우저에서 실제로 접속해 성공한 것을 각각 별도의 증거로 확인합니다.
- **트러블슈팅 문서화**: 장애가 생겼을 때 '증상 → 원인 가설 → 검증 방법 → 조치 내용 → 결과 → 재발 방지'의 체계적인 형식으로 기록합니다.
- **비용 관리와 완전한 삭제**: 실습 후 비용이 청구될 수 있는 자원 목록을 추적하고, 모든 실습 자원을 삭제한 뒤 남은 것이 없는지 철저히 확인합니다.

## 2. 안전 경계와 학습 운영 규칙

### 2.1 AWS 작업 전제 및 안전 규칙

- **계획 우선**: 현재 단계에서는 실제 AWS 자원을 생성하지 않습니다.
- **사전 정보 확인**: AWS 계정 상태, 작업 리전(서울 `ap-northeast-2`), **프리 티어(AWS가 무료로 제공하는 기본 혜택 범위)**, **크레딧(비용 결제 시 사용할 수 있는 프로모션 잔액)**을 먼저 확인합니다.
- **명시적 승인 필수**: 가상 서버 생성, 보안 그룹 변경, SSH 포트 설정, 자원 삭제 등 모든 인프라 변경 작업은 **사용자의 명시적 확인과 승인**을 받은 뒤에만 실행합니다.
- **권한 남용 금지**:
  - **Root 계정**: AWS 계정의 모든 권한을 가진 최고 관리자 계정입니다.
  - **최소권한 원칙(Principle of Least Privilege)**: 보안을 위해 작업에 꼭 필요한 최소한의 권한만 부여하는 원칙입니다.
  - 단순히 에러를 피하려고 모든 권한(`AdministratorAccess`)이나 최고 계정을 남용하지 않습니다.
- **비밀 정보 보호**: 비밀번호, AWS 액세스 키, SSH 개인 키, 인증 토큰은 절대로 문서, 채팅, Git 저장소에 기록하지 않습니다.
- **불필요한 자원 차단**: 이번 실습의 최소 구성에 필요하지 않은 포트, 권한, 고비용 서비스(NAT Gateway, ALB, RDS 등)를 임의로 만들지 않습니다.

### 2.2 한 단계에서 반복할 8단계 루프

1. **예측**: 이번 설정이나 요청이 어디까지 도달하고 어디서 멈출지 먼저 예측해 봅니다.
2. **개념**: 이번 단계에 꼭 필요한 클라우드/네트워크 용어 하나를 배웁니다.
3. **읽기 확인**: 비용이나 위험이 없는 콘솔 메뉴, 설정 파일, 로그 조회를 먼저 해봅니다.
4. **작은 실행**: 승인을 받은 경우에만 딱 하나의 리소스 또는 한 줄의 규칙을 변경합니다.
5. **관찰**: 서버 내부 상태, 외부 접속 상태, 네트워크 로그를 나누어 확인합니다.
6. **설명**: 이 설정이 왜 꼭 필요한지 자신의 언어로 설명합니다.
7. **변형**: 하나의 조건만 바꾸어 보고 결과가 어떻게 달라지는지 예측합니다.
8. **복구·정리**: 실습을 마친 뒤 즉시 원래 상태로 되돌리고, 비용이나 보안 위험이 남지 않았는지 확인합니다.

### 2.3 AI 활용 규칙

AI에게 다음 사항을 질문하고 점검받을 수 있습니다.

- 웹 요청 흐름을 계층별(네트워크, 방화벽, 서버, 웹서버)로 나누어 점검하기.
- 특정 에러가 났을 때 어느 로그 파일과 상태를 먼저 조회해야 하는지 위치 좁히기.
- 보안 그룹 인바운드 규칙과 권한 정책에서 빠진 부분이 없는지 검토하기.
- 작성한 아키텍처 다이어그램과 트러블슈팅 보고서의 논리적 허점 찾기.
- 실제 AWS를 건드리지 않고 원리를 연습할 수 있는 가상 장애 퀴즈 요청하기.

AI가 추천해 준 AWS CLI 명령어나 설정을 그대로 실행하지 않습니다. 조회를 하는 '읽기' 명령어인지 인프라를 바꾸는 '변경' 명령어인지, 비용이 발생하는지, 문제가 생기면 되돌릴 수 있는지 먼저 꼼꼼히 확인합니다.

## 3. 단계별 전체 순서

각 단계의 `통과 기준`을 만족해야 다음 단계로 나아갈 수 있습니다. 문제가 발생하면 새 자원을 더 만들지 말고 현재 계층을 먼저 집중적으로 점검합니다.

### 0단계. 과제 범위와 안전 계획 확인 [필수]

- **목표**: 이번 실습에서 만들 것과 절대 만들지 말아야 할 자원을 명확히 고정합니다.
- **배울 내용**:
  - `instruction.md`에 명시된 필수 요구사항, 아키텍처 구성 요건, 선택 보너스 항목.
  - B1-1에서 만든 포트폴리오 웹사이트를 B3-1의 EC2 웹 서버에 올리는 연결 구조.
  - 서울 리전(`ap-northeast-2`), Public Subnet, 웹 접속용 HTTP 80번 공개, 원격 관리용 SSH 22번 개인 IP 제한.
  - 시간당 비용이 발생할 수 있는 주요 서비스들(EC2 인스턴스, EBS 디스크, 미사용 탄력적 IP, NAT Gateway 등).
  - 자원을 만들 계획과 삭제할 계획을 처음부터 한 문서에 함께 작성해야 하는 이유.
- **작은 활동**:
  1. 과제의 공식 필수 조건, 선택 조건, 나중에 공부할 내용을 세 그룹으로 분류합니다.
  2. 이번 실습에 필요한 최소 구성도를 종이나 툴로 그려봅니다.
  3. 만들 예정인 자원의 이름, 태그, 예상 비용, 실습 종료 후 삭제 방법을 표로 정리합니다.
  4. 현재 시점에서는 실제 AWS 리소스가 전혀 생성되지 않았음을 명확히 기록합니다.
- **통과 기준**:
  - 이번 실습의 최소 구성(VPC 1개, 서브넷 1개, IGW 1개, 라우팅 테이블 1개, EC2 1개)을 말로 설명할 수 있습니다.
  - 예상 비용과 실습 종료 후 삭제 순서를 설명할 수 있습니다.
  - 사용자의 명시적 승인 없이는 어떠한 자원 생성도 진행되지 않는다는 점을 인지합니다.
- **실패 처리 / 안전 점검**: 만들 자원 목록 중에 과제 요구사항에 없는 고비용 서비스(예: NAT Gateway, ALB, RDS)가 들어 있다면 즉시 제외합니다.

### 1단계. 외부 웹 요청 전체 흐름 파악 [필수]

- **목표**: AWS 콘솔 화면을 열기 전에, 브라우저에서 서버로 이어지는 전체 통신 흐름을 머릿속에 그립니다.
- **배울 내용**:
  - 웹 브라우저(클라이언트)와 서버 컴퓨터의 역할.
  - HTTP 요청과 서버 응답, 그리고 상태 코드(성공 200, 없음 404, 오류 500 등).
  - IP 주소, 통신 포트 번호, 그리고 자기 자신을 뜻하는 `localhost`의 차이.
  - GitHub Pages는 인프라 관리를 대신해 주지만, EC2 배포는 네트워크, 방화벽, 웹 서버를 내가 직접 관리해야 하는 차이점.
- **작은 활동**:
  1. '외부 브라우저 → 공인 IP → 80번 포트 → Nginx 웹 서버 → HTML 문서 반환'의 전체 과정을 직접 그림으로 그려봅니다.
  2. 내 노트북에서 접속한 `localhost`와 서버 안에서 접속한 `localhost`가 서로 완전히 다른 컴퓨터를 가리킨다는 점을 설명해 봅니다.
  3. 주소를 잘못 친 DNS 에러, 문이 닫힌 포트 연결 거부 에러, 파일이 없는 HTTP 404 에러의 차이를 분류해 봅니다.
- **통과 기준**:
  - 누가 누구에게 몇 번 IP와 몇 번 포트로 요청을 보내는지 정확히 짚어낼 수 있습니다.
  - 웹페이지가 뜨지 않을 때 네트워크 연결 문제인지 웹 서버 프로그램 문제인지 가설을 세울 수 있습니다.

### 2단계. AWS 계정·리전·권한의 기본 [필수]

- **목표**: AWS 클라우드에서 누가, 어떤 자원을, 어느 지역에 만드는지 권한과 위치의 개념을 잡습니다.
- **배울 내용**:
  - **AWS 리전(Region)**: 전 세계 여러 국가에 분산되어 있는 AWS의 거점 데이터센터 지역입니다(서울 리전: `ap-northeast-2`).
  - **IAM 사용자, 역할(Role), 정책(Policy)**의 개념.
  - AWS 콘솔을 조작하는 권한(IAM)과 EC2 서버 컴퓨터 안에 로그인하는 리눅스 사용자 계정(`ubuntu` 등)의 차이점.
  - 최고 관리자(Root) 계정을 일상 실습에 쓰면 안 되는 이유와 최소권한 원칙.
- **작은 활동**:
  1. 콘솔 상단에서 리전 선택을 서울이 아닌 다른 곳으로 바꾸면 이전에 만든 자원이 보이지 않는 이유를 문서로 확인합니다(실제 자원 변경은 하지 않음).
  2. EC2 가상 서버를 만드는 AWS 권한과 만든 서버에 SSH로 로그인하는 권한이 왜 별개인지 설명해 봅니다.
  3. 이번 실습에 꼭 필요한 작업(생성, 조회, 태그 추가, 삭제)만 골라내 봅니다.
- **통과 기준**:
  - AWS 권한 오류(IAM 권한 부족)와 리눅스 서버 내부의 `Permission denied`(파일 권한 부족)를 혼동하지 않고 구분합니다.
  - 문제를 해결하겠다고 모든 권한(`AdministratorAccess`)을 무턱대고 주면 안 되는 이유를 설명할 수 있습니다.

### 3단계. VPC·Subnet·CIDR 네트워크 구조 [필수]

- **목표**: 가상 네트워크의 전체 영역과 그 안을 쪼개는 주소 범위를 이해합니다.
- **배울 내용**:
  - VPC가 클라우드 안에서 나만의 독립된 네트워크 영토라는 개념.
  - 서브넷(Subnet)이 VPC 영토를 구역별로 나눈 땅이라는 개념.
  - **CIDR(Classless Inter-Domain Routing)**: IP 주소 대역의 크기를 빗금 뒤의 비트 수로 표기하는 방식(예: `10.0.0.0/16`).
  - **Public Subnet(퍼블릭 서브넷)**과 **Private Subnet(프라이빗 서브넷)**의 차이.
  - 리전과 가용 영역(AZ, 독립된 전력/네트워크를 갖춘 데이터센터)의 관계.
- **작은 활동**:
  1. VPC 큰 네모 상자 안에 서브넷 작은 상자가 들어 있는 구조를 종이에 그려봅니다.
  2. VPC 대역(`10.0.0.0/16`, 약 65,536개 주소) 안에 서브넷 대역(`10.0.1.0/24`, 256개 주소)이 어떻게 들어가는지 확인합니다.
  3. 단 1개의 컴퓨터만 가리키는 `/32`와 전 세계 인터넷 전체를 가리키는 `0.0.0.0/0`의 차이를 비교합니다.
  4. 서브넷 이름표에 'Public'이라고 적어두어도 인터넷 관문(IGW)이 없으면 외부와 연결되지 않는 이유를 적어봅니다.
- **통과 기준**:
  - VPC와 서브넷의 포함 관계를 명확히 설명할 수 있습니다.
  - 주소 대역을 나누는 것과 실제로 인터넷에 연결되는 것은 서로 다른 설정임을 이해합니다.
  - 아직 실제 자원을 생성하지 않고도 구성도를 논리적으로 설명할 수 있습니다.

---

### 4단계. Route Table과 Internet Gateway [필수]

- **목표**: 웹 브라우저의 요청과 서버의 응답이 어느 출구를 통해 오가는지 길안내 규칙을 이해합니다.
- **배울 내용**:
  - 목적지 주소(Destination)와 찾아갈 대상(Target)으로 구성된 라우팅 테이블(Route Table).
  - 인터넷 전체를 뜻하는 기본 경로 `0.0.0.0/0`.
  - 서브넷과 라우팅 테이블의 연결(Association).
  - VPC를 외부 인터넷 바깥세상과 연결해 주는 유일한 출입구인 인터넷 게이트웨이(IGW).
  - IGW가 달려 있어도 라우팅 테이블에 출구 등록이 없거나, 서버에 공인 IP가 없으면 외부 통신이 불가능한 이유.
  - 나가는 요청 경로뿐 아니라 돌아오는 응답 경로도 열려 있어야 통신이 완성된다는 점.
- **작은 활동**:
  1. `외부 브라우저 ↔ IGW ↔ 라우팅 테이블 ↔ 서브넷 ↔ EC2`로 이어지는 양방향 길을 그려봅니다.
  2. 인터넷 게이트웨이만 만들고 라우팅 테이블에 등록하지 않았을 때 어떤 일이 일어날지 예측합니다.
  3. `0.0.0.0/0 → igw-xxxx`라는 규칙이 "모든 알 수 없는 외부 인터넷 요청은 이 게이트웨이 출구로 보내라"는 뜻임을 설명해 봅니다.
- **통과 기준**:
  - 진짜 퍼블릭 서브넷은 이름이 아니라 '기본 경로가 인터넷 게이트웨이로 연결된 서브넷'임을 설명할 수 있습니다.
  - 패킷이 다니는 '길의 문제(라우팅)'와 '문을 열어줄지의 문제(방화벽)'를 명확히 구분합니다.
  - 비용이 많이 드는 NAT Gateway는 외부에서 접속을 받아야 하는 이번 웹 서버 실습에 불필요하다는 점을 이해합니다.

### 5단계. Security Group·SSH·운영체제 보안 [필수]

- **목표**: 가상 방화벽 규칙과 서버 로그인 인증 절차를 분리하여 철저한 보안 원칙을 세웁니다.
- **배울 내용**:
  - **인바운드(Inbound)**: 외부에서 서버로 들어오는 트래픽 규칙입니다.
  - **아웃바운드(Outbound)**: 서버에서 외부 인터넷으로 나가는 트래픽 규칙입니다.
  - 웹 서비스용 HTTP 80번 포트는 전 세계 누구나 볼 수 있게 `0.0.0.0/0`으로 열어두어야 합니다.
  - 원격 관리용 SSH 22번 포트는 해킹 공격을 막기 위해 반드시 **내 개인 컴퓨터 IP(`/32`)**로만 좁혀 열어야 합니다.
  - **SSH 키페어(Key Pair)**: 공개 키는 서버에 두고, 비밀 개인 키(`.pem`)는 내 컴퓨터에만 안전하게 보관하여 접속을 증명하는 인증 도구입니다.
  - 클라우드의 보안 그룹, 리눅스 자체 방화벽(ufw), 그리고 Nginx 프로그램이 80번 포트를 열고 기다리는 소켓(Socket)은 각자 다른 층위라는 점.
  - 포트 전체(`0-65535`)를 누구나 들어오게 열어버리는 행위가 매우 위험한 이유.
- **작은 활동**:
  1. 일반 방문객에게 열어줄 포트(80)와 나 혼자만 접속해야 하는 관리 포트(22)를 표로 구분합니다.
  2. 내 현재 IP(`/32`)로 제한하는 것과 모든 사람(`0.0.0.0/0`)에게 열어주는 것의 보안 차이를 설명합니다.
  3. SSH 개인 키(`.pem`) 파일을 채팅창, 블로그, Git 저장소에 절대 올리지 않는다는 규칙을 확인합니다.
  4. '보안 그룹에서 80번 포트를 열어준 것'과 '실제 서버 안에서 Nginx 프로그램이 실행 중인 것'의 차이를 적어봅니다.
- **통과 기준**:
  - SSH 접속이 안 될 때 네트워크 방화벽 차단인지, 키 파일 문제인지, 리눅스 계정 문제인지 나누어 점검할 수 있습니다.
  - HTTP와 SSH의 접근 허용 범위가 왜 완전히 달라야 하는지 명확히 설명할 수 있습니다.
  - 접속이 안 된다고 모든 포트와 IP를 다 열어버리는 무책임한 해결책을 쓰지 않습니다.

### 6단계. 비용·생성·삭제 계획 최종 승인 [필수 / 승인 필수]

- **목표**: 실제 클라우드 자원을 단 하나라도 만들기 전에, 발생 가능한 비용과 삭제 절차를 완벽히 숙지하고 확인을 받습니다.
- **배울 내용**:
  - 프리 티어 혜택은 가입 기간이나 사용량에 따라 제한이 있으며, 방심하면 요금이 청구될 수 있다는 점.
  - **EC2 중지(Stop)**: 컴퓨터 전원만 끄는 것으로 디스크(EBS) 비용은 계속 발생합니다.
  - **EC2 종료(Terminate)**: 가상 컴퓨터와 기본 연결 디스크를 완전히 영구 삭제하는 것입니다.
  - **EBS(Elastic Block Store)**: 가상 서버에 외장 하드처럼 붙는 가상 디스크로, 서버가 꺼져 있어도 용량만큼 비용이 청구됩니다.
  - **Elastic IP(탄력적 IP)**: 고정 공인 IP로, 만들어 두고 실행 중인 서버에 연결해 두지 않으면 시간당 비용이 부과됩니다.
  - 자원을 만든 순서의 정반대 순서로 삭제해야(의존성 해제) 오류 없이 깔끔하게 지워진다는 점.
- **작은 활동**:
  1. 만들 예정인 각 리소스(EC2, EBS, VPC 등)의 예상 비용, 삭제 방법, 삭제 확인 화면을 표로 작성합니다.
  2. 정리 순서: `EC2 종료 → EBS 삭제 확인 → 탄력적 IP 해제/반환 → IGW 분리 및 삭제 → 서브넷/라우팅 테이블 삭제 → VPC 삭제` 흐름을 머릿속으로 시뮬레이션합니다.
  3. 콘솔의 결제 대시보드(Billing)를 주기적으로 확인하는 습관을 계획에 넣습니다.
  4. 사용자에게 생성할 자원의 범위와 예상되는 비용/위험을 설명하고 **명시적 승인**을 받기 전까지는 작업을 멈춥니다.
- **통과 기준**:
  - 무엇을 만들고 무엇을 절대 만들지 않을지 스스로 명확하게 말할 수 있습니다.
  - 실습이 끝난 뒤 남아 있는 유료 자원이 있는지 확인하는 방법을 설명할 수 있습니다.
  - 비용과 위험 확인 없이는 절대 생성 버튼이나 CLI 명령을 실행하지 않습니다.

---

### 7단계. 최소 VPC 네트워크 만들기 [필수 / 승인 필수]

- **목표**: 사용자의 승인 아래, 웹 트래픽이 오갈 수 있는 최소한의 가상 네트워크 길을 하나씩 구축합니다.
- **실행 순서**:
  1. 서울 리전(`ap-northeast-2`)에 VPC 1개를 생성합니다(예: `10.0.0.0/16`).
  2. 해당 VPC 안에 Public Subnet 1개를 생성합니다(예: `10.0.1.0/24`).
  3. Internet Gateway(IGW) 1개를 생성하여 해당 VPC에 연결(Attach)합니다.
  4. 라우팅 테이블(Route Table)을 열고 인터넷 전체 경로(`0.0.0.0/0 → IGW`)를 추가합니다.
  5. 이 라우팅 테이블을 방금 만든 Public Subnet에 명시적으로 연결(Associate)합니다.
  6. 만들어진 각 자원의 고유 ID(vpc-xxx, subnet-xxx, igw-xxx, rtb-xxx)와 태그 이름을 기록합니다.
- **작업 전 4대 안전 체크리스트**:
  - 현재 선택된 지역이 서울 리전인가?
  - 생성하려는 자원이 사전 계획표에 적힌 최소 자원인가?
  - 불필요한 비용 발생 요소가 없는가?
  - 실패했을 때 즉시 삭제하고 되돌릴 방법이 준비되어 있는가?
- **통과 기준**:
  - AWS 콘솔에서 서브넷과 라우팅 테이블이 정상적으로 연결된 상태를 눈으로 확인합니다.
  - 내가 그린 네트워크 설계도와 실제 생성된 리소스 ID가 정확히 1:1로 일치합니다.
  - 아직 서버 컴퓨터(EC2)를 만들지 않은 상태에서도 완성된 네트워크 길의 흐름을 설명할 수 있습니다.
- **실패 처리**: 서브넷을 만들었는데 인터넷과 연결되지 않는다면 라우팅 테이블에 `0.0.0.0/0 → IGW` 규칙이 제대로 들어갔는지 확인합니다.

---

### 8단계. EC2 가상 서버와 보안 그룹 생성 [필수 / 승인 필수]

- **목표**: 웹 서버를 설치할 가상 컴퓨터를 생성하고 안전한 방화벽 규칙을 적용합니다.
- **실행 순서**:
  1. 프리 티어가 지원되는 micro급 인스턴스(t2.micro 또는 t3.micro)와 안정적인 리눅스 OS(Ubuntu LTS 또는 Amazon Linux 2023)를 선택합니다.
  2. 7단계에서 만든 Public Subnet을 지정하고, '퍼블릭 IP 자동 할당'을 활성화합니다.
  3. 새 SSH 키페어를 생성하여 내 로컬 컴퓨터의 안전한 폴더에 내려받습니다(권한 설정 `chmod 400`). 키 파일의 내용은 절대 어디에도 공유하지 않습니다.
  4. 보안 그룹(Security Group) 인바운드 규칙을 설정합니다:
     - HTTP(80번 포트): 모든 인터넷 허용(`0.0.0.0/0`)
     - SSH(22번 포트): 반드시 **내 현재 IP(`/32`)**만 허용
  5. EC2 인스턴스를 시작하고, 발급된 퍼블릭 IP, 인스턴스 ID, 보안 그룹 ID를 꼼꼼히 기록합니다.
- **통과 기준**:
  - EC2 가상 컴퓨터가 켜진 상태(Running)와 그 안에서 웹 서비스가 응답하는 상태를 구분할 줄 압니다.
  - 보안 그룹에서 22번 포트가 전 세계(`0.0.0.0/0`)로 열려 있지 않고 내 IP로 안전하게 잠겨 있는지 확인합니다.
  - SSH 비밀 키가 안전하게 보관되어 있고 분실 위험이 없음을 확인합니다.
- **실패 처리**: 인스턴스를 만들었는데 퍼블릭 IP가 부여되지 않았다면 서브넷 설정에서 '퍼블릭 IPv4 주소 자동 할당'이 꺼져 있었는지 확인합니다.

---

### 9단계. SSH 접속과 서버 내부 탐색 [필수]

- **목표**: 내 컴퓨터에서 원격 가상 서버 컴퓨터 안으로 안전하게 터미널로 접속하여 환경을 점검합니다.
- **작은 활동**:
  1. 터미널에서 SSH 명령어로 서버에 접속합니다:
     `ssh -i <내키파일.pem> ubuntu@<서버퍼블릭IP>`
  2. 현재 로그인한 리눅스 사용자 이름(`whoami`)과 현재 작업 위치(`pwd`)를 확인합니다.
  3. 서버 안에서 외부 인터넷으로 요청(예: `curl -I https://www.google.com`)을 날려 아웃바운드 인터넷이 잘 연결되는지 확인합니다.
  4. 현재 서버에서 열려 있는 포트 목록(`ss -tulpn` 등)을 확인하여 아직 80번 포트를 쓰는 웹 서버가 없음을 관찰합니다.
  5. 만약 SSH 접속이 실패한다면 '퍼블릭 IP 오타 → 22번 포트 방화벽 차단 → 키 파일 권한 에러 → 리눅스 유저 이름 오류' 순서로 원인을 좁혀갑니다.
- **통과 기준**:
  - SSH로 서버에 로그인할 수 있다고 해서 웹사이트가 밖에서 보이는 것은 아니라는 점을 설명할 수 있습니다.
  - 내 노트북 터미널에서 실행하는 `localhost`와 서버 터미널 안에서 실행하는 `localhost`의 대상이 완전히 다르다는 점을 이해합니다.
  - 어떠한 경우에도 비밀 키 파일이나 비밀번호를 화면에 노출하지 않습니다.
- **실패 처리**: `Permissions 0644 for 'key.pem' are too open` 오류가 발생하면 내 컴퓨터 터미널에서 키 파일 권한을 나만 읽을 수 있게 변경(`chmod 400 key.pem`)합니다.

### 10단계. Nginx 웹 서버 설치와 로컬 검증 [필수]

- **목표**: 웹 서버 소프트웨어를 설치하고, 서버 컴퓨터 내부에서 80번 포트로 기본 웹페이지가 응답하는지 확인합니다.
- **작은 활동**:
  1. 리눅스 패키지 관리자로 Nginx를 설치하고 서비스가 실행 중인지 확인합니다:
     `sudo apt update && sudo apt install -y nginx`
     `sudo systemctl status nginx`
  2. Nginx가 웹 문서를 보관하는 기본 폴더 위치(`/var/www/html`)와 설정 파일 위치(`/etc/nginx/`)를 눈으로 확인합니다.
  3. 서버 터미널 내부에서 자기 자신에게 웹 요청을 보내봅니다:
     `curl -I http://localhost`
  4. 화면에 `HTTP/1.1 200 OK` 응답이 오는지, Nginx 기본 접속 로그(`/var/log/nginx/access.log`)에 한 줄이 찍히는지 확인합니다.
  5. Nginx 서비스를 잠시 멈추었을 때(`sudo systemctl stop nginx`) curl 요청이 어떻게 거부되는지 관찰해 봅니다.
- **통과 기준**:
  - EC2 서버 하드웨어가 켜진 것과 Nginx 소프트웨어가 80번 포트에서 요청을 기다리는 것을 구분하여 설명할 수 있습니다.
  - 서버 내부의 `curl http://localhost` 200 성공은 내부 테스트일 뿐, 외부 인터넷 사용자가 접속할 수 있다는 증거는 아직 아니라는 점을 명확히 압니다.
  - Nginx 설정을 바꿀 때는 반드시 한 번에 하나씩만 수정하고 전후를 기록합니다.
- **실패 처리**: Nginx 설치 후에도 `curl http://localhost`가 실패한다면 `systemctl status nginx`를 통해 프로그램이 죽지 않고 정상 실행(active/running) 중인지 확인합니다.

### 11단계. B1-1 포트폴리오 웹사이트 배포 [필수]

- **목표**: 앞서 완성하고 검증을 끝낸 B1-1 웹사이트의 파일들을 EC2 서버의 웹 폴더로 옮겨 서비스할 수 있게 만듭니다.
- **사전 필수 전제**:
  - B1-1의 모든 필수 기능과 로컬 브라우저 검증이 완전히 끝나 있어야 합니다.
  - 배포할 B1-1 소스 코드의 정확한 버전과 파일 목록(HTML, CSS, JS, 이미지 등)을 명시합니다.
  - GitHub Pages 배포와 이번 EC2 배포는 별개의 독립적인 환경임을 인지합니다.
- **작은 활동**:
  1. B1-1의 `index.html`, `css/`, `js/`, `assets/` 파일 목록을 확인합니다.
  2. SCP 명령어 등을 이용해 해당 정적 파일들을 EC2 서버의 Nginx 웹 루트 폴더(`/var/www/html/`)로 복사합니다.
  3. 파일 권한이 웹 서버가 읽을 수 있는 권한(일반 읽기 권한)으로 잘 설정되었는지 확인합니다.
  4. 서버 터미널에서 `curl http://localhost`를 실행하여 내가 만든 B1-1의 HTML 문서 내용이 출력되는지 확인합니다.
  5. 상대 경로로 연결된 CSS, JS 파일도 서버 내부에서 curl로 요청하여 정상 200 응답이 오는지 확인합니다.
- **통과 기준**:
  - HTML 파일 하나가 200으로 응답했다고 해서 전체 사이트가 정상이라고 섣불리 단정하지 않습니다.
  - HTML 본문, 스타일시트, 자바스크립트, 이미지 파일의 경로와 권한이 각각 올바른지 점검합니다.
  - 배포에 사용한 B1-1의 소스 코드 버전 정보를 문서에 기록으로 남깁니다.
- **실패 처리**: HTML 글자는 나오는데 CSS 스타일이나 이미지가 깨진다면 상대 경로가 틀렸거나 대소문자 구분이 다른지(리눅스는 대소문자를 엄격히 구분함) 확인합니다.

### 12단계. 외부 인터넷 접속 검증 [필수]

- **목표**: 서버 내부에서의 성공을 넘어, 전 세계 인터넷 사용자가 실제로 웹사이트를 볼 수 있는지 외부에서 접속하여 증명합니다.
- **과제 공식 검증 방식 (택 1)**:
  - **방식 A**: 외부 PC나 스마트폰 브라우저에서 `http://<서버퍼블릭IP>` 주소로 직접 접속하여 사이트가 완벽히 뜨는지 확인.
  - **방식 B**: 외부 터미널에서 `curl -I http://<서버퍼블릭IP>/health`를 호출하여 200 OK 응답과 준비된 텍스트가 오는지 확인.
- **학습 활동 순서**:
  1. EC2 서버와 전혀 무관한 외부 네트워크(내 노트북 브라우저, 스마트폰 LTE 데이터 등)에서 요청을 보냅니다.
  2. 요청이 '공인 IP → 보안 그룹 80번 포트 → 인터넷 게이트웨이 → 라우팅 테이블 → Nginx' 경로를 타고 들어오는지 확인합니다.
  3. 브라우저 화면의 렌더링 결과와 개발자 도구 Network 탭의 200 응답 스크린샷을 증빙으로 저장합니다.
  4. 앞서 서버 내부에서 확인한 `localhost` 결과와 외부 접속 결과를 나란히 비교합니다.
  5. 검증에 사용한 방식(A 또는 B)과 접속 주소, 검증 시점을 문서에 명확히 기록합니다.
- **통과 기준**:
  - 외부 브라우저나 외부 네트워크에서 실제로 웹페이지를 성공적으로 불러왔다는 명확한 증거(스크린샷, 상태 코드)가 있습니다.
  - 내부 `localhost` 성공만 가지고 외부 접속도 성공했을 것이라고 지레짐작하지 않습니다.
  - 실제 IP 주소를 보고서에 남길 때 개인정보나 보안상 주의할 점이 없는지 검토합니다.
- **실패 처리**: 서버 안에서는 잘 되는데 외부 브라우저에서 접속 시 '응답 시간이 초과되었습니다'가 뜬다면 보안 그룹의 인바운드 80번 포트가 전 세계(`0.0.0.0/0`)로 열려 있는지, 라우팅 테이블에 IGW가 연결되어 있는지 점검합니다.

### 13단계. 체계적인 트러블슈팅 보고서 1건 작성 [필수]

- **목표**: 에러가 났을 때 감으로 때려맞추지 않고, 공학적인 가설과 증거를 바탕으로 문제를 해결하는 역량을 증명합니다.
- **8대 문제 영역 분류**:
  1. 주소 및 오타 문제 (IP 오타 등)
  2. TCP 포트 연결 거부 또는 시간 초과 (방화벽 또는 라우팅 문제)
  3. VPC 라우팅 테이블 및 인터넷 게이트웨이 누락 문제
  4. 보안 그룹(Security Group) 또는 OS 방화벽(ufw) 차단 문제
  5. EC2 서버 부팅 실패 또는 Nginx 웹 서버 프로그램 중지 문제
  6. 웹 폴더 경로(`/var/www/html`) 또는 파일 읽기 권한 문제
  7. HTML은 뜨는데 CSS/JS/이미지 또는 GitHub API 호출이 실패하는 문제
  8. AWS 콘솔 관리 권한(IAM) 문제와 서버 터미널 권한(`sudo`) 문제
- **표준 보고서 필수 형식**:
  ```text
  증상: (어떤 환경에서 어떤 에러 메시지가 떴는가)
  원인 가설: (어느 계층의 어떤 설정이 문제라고 추측했는가)
  검증 방법과 관찰 결과: (어떤 로그나 설정을 확인하여 가설을 증명했는가)
  조치: (정확히 어떤 설정을 어떻게 변경했는가)
  조치 후 결과: (문제가 어떻게 해결되었음을 확인했는가)
  재발 방지: (앞으로 같은 실수를 막기 위해 무엇을 주의해야 하는가)
  ```
- **통제된 실험 안내**: 실습 중 자연스러운 오류가 발생하지 않았다면, 사용자의 사전 승인을 받고 안전한 통제 실험(예: 잠시 보안 그룹 80번 포트를 닫아보고 증상을 관찰한 뒤 즉시 복구)을 진행할 수 있습니다. 단, 이를 실제 장애인 것처럼 꾸며 쓰지 않고 의도된 학습 실험임을 명시합니다. SSH 포트는 절대 닫지 않습니다.
- **통과 기준**:
  - 문제를 해결하겠다고 한 번에 여러 설정을 동시에 바꾸지 않고 하나씩 검증합니다.
  - 눈에 보이는 '현상(증상)'과 근본적인 '원인'을 명확히 구분하여 서술합니다.
  - 변경 전과 변경 후의 실제 화면/로그 증거를 남깁니다.

- **목표**: 내가 만든 클라우드 인프라 구성을 다른 엔지니어가 보고 그대로 이해하고 재현할 수 있도록 깔끔하게 정리합니다.
- **필수 제출 산출물 목록**:

  4. `docs/cleanup-checklist.md`: 이번 실습에서 만든 모든 리소스 목록과 종료/삭제한 증빙 내역.
- **통과 기준**:

  - 계획서의 내용, 예시 데이터, 실제 검증 결과가 문서 안에서 명확히 구분되어 있습니다.
  - 실습에서 만들지 않은 자원은 '미생성'으로 솔직하고 명확하게 표기합니다.
  - 비밀 키, 비밀번호, 민감한 보안 정보가 문서에 단 한 줄도 포함되지 않았음을 확인합니다.

### 15단계. 클라우드 리소스 완전 삭제와 비용 확인 [필수 / 승인 필수]

- **목표**: 실습이 끝난 후 불필요한 클라우드 자원을 100% 삭제하여 예상치 못한 비용이 1원도 청구되지 않도록 마무리를 짓습니다.
- **정리 시작 전 필수 작업**:
  1. 과제 제출에 필요한 외부 접속 스크린샷과 로그 증빙이 빠짐없이 로컬에 저장되었는지 확인합니다.
  2. 실제 생성한 리소스 목록과 삭제 계획표를 대조합니다.
  3. 사용자에게 자원을 삭제해도 되는지 **최종 삭제 승인**을 받습니다.
- **철저한 자원 삭제 순서**:
  1. EC2 가상 서버 인스턴스를 **종료(Terminate)**합니다 (중지 Stop이 아님에 주의).
  2. EC2에 연결되어 있던 EBS 볼륨 디스크가 함께 삭제되었는지 확인하고, 남아 있다면 수동으로 삭제합니다.
  3. 생성했거나 할당한 탄력적 IP(Elastic IP)가 있다면 연결을 해제하고 AWS에 반환(Release)합니다.
  4. 인터넷 게이트웨이(IGW)를 VPC에서 분리(Detach)한 뒤 완전히 삭제(Delete)합니다.
  5. 추가로 생성했던 서브넷과 라우팅 테이블을 삭제합니다.
  6. 최종적으로 VPC를 삭제합니다.
  7. AWS 결제 대시보드(Billing)를 열어 추가 과금 요소가 남아 있는지 최종 점검합니다.
- **통과 기준**:
  - 인스턴스 중지(Stop)와 종료(Terminate)의 차이점과 디스크 비용 발생 원리를 완벽히 설명할 수 있습니다.
  - 콘솔의 각 서비스 메뉴를 직접 돌며 모든 자원이 깨끗이 삭제되었음을 눈으로 확인합니다.
  - 결제 대시보드는 실시간 반영에 몇 시간의 지연이 있을 수 있다는 점을 이해하고, 현재 0원이라고 방심하지 않고 자원 목록 자체를 꼼꼼히 대조합니다.

### 16단계. 선택 보너스 과제와 독립 변형 연습 [선택]

- **목표**: 필수 요구사항을 완벽히 소화하고 정리를 마친 뒤에만, 더 깊은 클라우드 엔지니어링 주제에 도전합니다.
- **진행 원칙**:
  - 필수 네트워크, EC2, Nginx, 외부 검증, 트러블슈팅, 자원 정리가 모두 끝난 뒤에만 시작합니다.
  - 기존 필수 제출물과 증빙 문서는 안전하게 따로 백업해 둡니다.
  - HTTPS 보안 인증서(Let's Encrypt / Certbot) 적용 또는 Docker 컨테이너 환경 배포 중 **딱 하나만** 골라 도전합니다.
  - 도전하기 전에 필요한 포트(예: HTTPS용 443번 포트), 도메인 필요 여부, 추가 삭제 계획을 먼저 수립합니다.
  - 보너스 결과물은 필수 결과물과 명확히 분리하여 기록합니다.
- **스스로 풀어보는 5가지 독립 변형 퀴즈**:
  1. 인터넷 게이트웨이는 연결되어 있는데 라우팅 테이블에 `0.0.0.0/0` 규칙이 빠져 있다면, 외부 접속 시 어떤 증상이 나타나고 어떻게 고쳐야 하는가?
  2. 서버 안에서 `curl localhost`는 200이 잘 뜨는데 외부 브라우저에서는 접속 시간 초과가 뜬다면 의심할 수 있는 네트워크 원인 세 가지는?
  3. 보안 그룹에서 80번 포트를 열어주었는데도 외부 접속이 안 될 때, 서버 내부에서 Nginx가 죽어 있는지 확인하는 명령어는?
  4. EC2 가상 서버를 종료(Terminate)했는데도 다음 달에 몇천 원의 요금이 청구될 수 있는 원인은 무엇인가?
  5. AWS 콘솔에서 리소스를 못 만드는 에러와, 리눅스 터미널에서 파일을 못 쓰는 에러는 각각 어느 계층의 권한 문제인가?
- **통과 기준**:
  - 새로운 에러가 닥쳤을 때 당황하지 않고 네트워크, 서버, 소프트웨어 중 어느 계층의 문제인지 스스로 범위를 좁힐 수 있습니다.
  - 새로운 서비스를 무작정 추가하기보다 이미 배운 기본 원리를 활용해 해결합니다.

## 4. B1-1과 B3-1의 이상적인 연결 일정

B1-1(프론트엔드 포트폴리오 제작)과 B3-1(AWS 인프라 및 배포)은 아래 일정으로 진행하는 것을 권장합니다.

1. **B1-1 기본 완성**: HTML, CSS, JavaScript 순서대로 B1-1의 핵심 기능을 먼저 공부하고 만듭니다.
2. **B3-1 이론 병행**: B1-1 코딩을 하는 동안에도, B3-1의 1~6단계 네트워크 개념, 아키텍처 다이어그램, 비용 안전 수칙은 미리 공부하고 그림으로 익혀둡니다.
3. **B1-1 로컬 검증 완료**: B1-1의 모든 필수 기능과 브라우저 검증을 끝냅니다.
4. **배포 버전 고정**: EC2에 올릴 B1-1 소스 코드의 최종 버전을 딱 고정합니다.
5. **승인 후 B3-1 인프라 생성**: 사용자의 명시적 승인을 받은 뒤 B3-1의 실제 AWS 네트워크와 EC2를 만듭니다.
6. **서버 내부 Nginx 검증**: EC2 안에서 Nginx 웹 서버가 정상 작동하는지 먼저 확인합니다.
7. **B1-1 배포 및 외부 검증**: 준비된 B1-1 정적 파일들을 서버로 옮겨 외부 인터넷 접속을 성공시킵니다.
8. **증빙 저장 및 완전 삭제**: 보고서용 스크린샷과 로그를 로컬에 저장하고, 실습 자원을 100% 삭제합니다.
9. **GitHub Pages 유지**: B1-1 과제에서 배포한 GitHub Pages는 그대로 유지하며, EC2 배포와 서로 간섭하지 않음을 확인합니다.

*주의: B1-1 코딩 작업과 B3-1의 실제 클라우드 인프라 변경 작업을 같은 세션에서 동시에 뒤섞어 진행하지 마십시오. 문제가 생겼을 때 프론트엔드 코드 때문인지 클라우드 네트워크 때문인지 원인을 찾기 어려워집니다.*

## 5. 학습 세션 운영 단위 (권장 시간표)

한 번의 학습 세션(약 1시간~1시간 30분)은 다음 시간표를 권장합니다.

```text
[10분] 지난 시간에 배운 네트워크·인프라 내용 복습
[15분] 이번 시간에 배울 핵심 클라우드/보안 개념 하나 설명 듣기
[20분] 구성도 그리기, 콘솔 조회, 또는 승인된 작은 변경 작업 실행하기
[15분] 서버 내부 응답, 외부 접속, 네트워크 로그 증거 꼼꼼히 확인하기
[10분] 장애 상황 가설 세우기 및 회고 기록 남기기
```

비용이 발생하거나 외부 인터넷에 문을 열어야 하는 민감한 단계는 세션 시간이 끝났다고 해서 자동으로 진행하지 않습니다. 사용자의 확인과 승인, 복구 계획이 완벽히 갖춰지지 않았다면 다음 세션으로 과감히 미룹니다.

## 6. 이 계획의 사전 검토 질문

실제 AWS 콘솔을 열거나 명령어를 입력하기 전에 아래 질문을 먼저 점검합니다.

1. B1-1 사이트 완성을 B3-1 시작의 필수 전제로 둘 것인가요, 아니면 개념 공부만 먼저 병행할 것인가요?
2. AWS 리소스를 만들기 전에 계정 상태, 리전(서울), 프리 티어, 예상 비용을 어떤 방식으로 먼저 확인할 것인가요?
3. AWS 콘솔(웹 화면)과 AWS CLI(터미널) 중 어느 방법으로 실습할 것인가요?
4. 외부 인터넷 검증 방식은 방식 A(웹 브라우저 접속)와 방식 B(`/health` 확인) 중 무엇을 선택할 것인가요?
5. 실제 오류가 발생하지 않았을 때 안전한 통제 실험을 해볼 것인가요, 아니면 가상 시나리오를 바탕으로 문서화할 것인가요?
6. 실습 증빙을 다 저장하고 자원을 삭제할 시점을 언제로 잡을 것인가요?
7. 보너스 과제(HTTPS/Docker)는 생략하고 핵심에 집중할 것인가요, 아니면 필수 완료 후 하나만 도전할 것인가요?
8. 각 단계의 통과 기준을 콘솔 화면, 서버 로그, 말로 된 설명으로 명확히 확인할 수 있나요?

위 검토 질문들에 대해 충분한 논의가 끝나고, 자원 생성 범위와 비용 계획이 완전히 승인된 뒤에 0단계부터 차근차근 학습을 시작합니다.
