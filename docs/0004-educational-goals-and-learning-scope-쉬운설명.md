# B3-1 교육 목표와 적정 학습 범위 (쉬운 설명판)

[과제 요구사항 요약](0051-requirements-and-review-reference.md) · [필수 조건](0002-required-checklist-and-extension-rules-쉬운설명.md) (원문: [0002-required-checklist-and-extension-rules.md](0002-required-checklist-and-extension-rules.md)) · [확장 지도](0003-cloud-foundations-beyond-assignment-쉬운설명.md) (원문: [0003-cloud-foundations-beyond-assignment.md](0003-cloud-foundations-beyond-assignment.md))

> 공식 과제 소개, 목표, 요구사항으로부터 교육적 의도를 알기 쉽게 해석한 안내서입니다. 교육 기관의 별도 교수설계나 공식 세부 평가표는 아직 확인되지 않았습니다. 아래 정리된 학습 깊이는 사수(선배 엔지니어) 관점의 권장 기준이며, 현재 실제로 리소스를 생성하거나 평가를 완료한 상태가 아닙니다.

---

## 1. 핵심: 서버 한 대를 안전하게 공개하고, 동작을 설명하며, 비용 없이 깔끔하게 정리하기

이 과제는 단순히 웹사이트 파일 몇 개를 인터넷에 올려보는 연습이 아닙니다. **가상 네트워크, 가상 서버(컴퓨트), 접근 통제 방화벽을 하나로 연결해 실제 외부 인터넷 요청을 성공시키고, 접속이 실패했을 때 그 원인을 명확한 증거로 좁혀내며, 실습이 끝난 뒤 요금이 남지 않도록 자원을 깔끔하게 정리하는 클라우드 기본 실습**입니다.

과제 명세는 다음 핵심 개념들의 역할을 직접 설명하도록 요구합니다.
- 가상 사설망(VPC, Virtual Private Cloud): 다른 사용자와 격리된 나만의 안전한 클라우드 네트워크 영토.
- 하위 네트워크 구역(Subnet, 서브넷): 가상망의 IP 주소 대역을 용도에 맞게 나누어 둔 구역.
- 경로 안내표(Route Table, 라우트 테이블): 데이터 패킷이 목적지로 가기 위해 거쳐야 할 경로 이정표.
- 인터넷 출입구(Internet Gateway, IGW): 가상 네트워크와 바깥 인터넷 세상을 이어주는 공식 관문.
- 가상 방화벽인 보안 그룹(Security Group, SG)과 권한 관리 체계인 IAM(Identity and Access Management)의 차이.
- 외부 인터넷 접속을 성립시키는 구체적 조건, 오류 분석(트러블슈팅), 비용 통제와 자원 정리 방법.

따라서 웹 콘솔 화면에서 버튼을 클릭하는 순서만 외우거나, 단순히 '웹 화면이 떴다'는 결과 하나만으로 학습 목표를 달성했다고 볼 수 없습니다.

반대로 수십 대의 서버를 묶는 대규모 상용 인프라, 무중단 고가용성(HA, High Availability), 컨테이너 관리 도구인 쿠버네티스(Kubernetes), 완성형 자동 배포(CI/CD) 파이프라인까지 한 번에 만들라는 과제도 결코 아닙니다. 명세에서 요구하는 최소 구성은 가상 사설망(VPC 1개), 공개 서브넷(Public Subnet 1개), 가상 서버(EC2 인스턴스 1대)입니다.

## 2. 요구사항이 가르치는 사고 방식

| 과제 요구 항목 | 교육 목적 | 이 단계에서 설명할 수 있어야 하는 수준 |
| --- | --- | --- |
| VPC · 서브넷(Subnet) | 네트워크 범위와 격리 구역의 이해 | 가상 서버가 어떤 사설 IP 주소 범위에 속해 있는지 설명 |
| 라우팅 테이블(Route Table) · 인터넷 게이트웨이(IGW) | 데이터 트래픽의 이동 경로 이해 | 내가 만든 서브넷이 인터넷으로 나가기 위해 어느 경로를 사용하는지 설명 |
| 퍼블릭 IP(공인 IP) | 외부에서 서버로 도달할 수 있는 주소 | 공인 IP 주소만 있다고 해서 무조건 접속이 성립되는 것은 아닌 이유 설명 |
| EC2 · 웹 서버(Nginx) | 가상 컴퓨터와 프로그램 서비스의 구분 | 가상 컴퓨터가 켜져 있는 것과 웹 서버 프로그램이 실행 중인 것의 차이 설명 |
| 원격 접속(SSH) | 제한된 관리자 전용 접속 경로 | 포트 번호(22), 접속 허용 IP, 암호화 키, 운영체제 사용자 계정의 역할 구분 |
| 보안 그룹(Security Group, SG) | 필요한 네트워크 통신만 안전하게 노출 | 웹 접속(HTTP 80)은 전체 공개하고 원격 접속(SSH 22)은 개인 IP로 좁히는 이유 설명 |
| 권한 관리(IAM) | 클라우드 관리 작업의 최소권한 원칙 | 누가(어떤 사람이나 프로그램이) AWS 클라우드 자원을 만들거나 지울 수 있는지 설명 |
| 내부 검증 · 외부 검증 | 통신 실패 구간의 논리적 분리 | 서버 안에서 `localhost`로 성공하는 것과 바깥 인터넷에서 성공하는 것의 차이 설명 |
| 오류 분석 보고서 | 가설 검증 기반의 문제 해결 능력 | 관찰(증상) → 가설 → 검증 → 변경 조치 → 결과 재확인의 흐름으로 오류 분석 |
| 자원 정리 | 클라우드 자원의 수명 주기와 비용 책임 | 서버 일시 중지(Stop)와 완전 삭제(Terminate)의 차이, 서버 종료 후 남는 유료 자원 구분 |
| 아키텍처 다이어그램 | 실제 인프라 구성을 시각적으로 설명 | 내가 그린 구조도와 실제 AWS 콘솔 설정이 정확히 일치하는지 대조 설명 |

## 3. 세 층으로 나누는 학습 범위

### A. 지금 직접 이해하고 수행할 핵심 기본기

- 인터넷 주소(IP), 출입문 번호(포트), 웹 통신 규약(HTTP 요청과 응답), 내 컴퓨터를 가리키는 주소(`localhost`)의 기본 의미.
- 지정된 클라우드 네트워크 연결 구성과 가상 서버(EC2)가 외부 인터넷과 통신하기 위한 필수 조건.
- 가상 방화벽인 보안 그룹(SG)의 출발지 IP/포트 규칙과, AWS 클라우드 자원을 다루는 IAM 관리 권한의 명확한 구분.
- 암호화 원격 접속(SSH), Nginx 웹 서버 실행, 기본 웹 파일 위치, 실행 중인 프로세스 및 백그라운드 서비스 상태, 시스템 로그 확인.
- 서버 내부(`localhost`)에서의 정상 응답 검증과 바깥 인터넷에서의 응답 검증 분리, 최소 1건 이상의 실제 문제 분석 및 해결 기록 작성.
- 대한민국 서울 리전(`ap-northeast-2`), 계정 조건 및 요금 발생 요인 사전 점검, 실습 후 자원 완전 삭제와 공식 제출 근거 준비.

이 단계의 학습 깊이는 **각 설정이 왜 필요한지 그 이유를 설명할 수 있고, 눈에 보이는 오류를 네트워크 구간별로 분리해 낼 수 있으며, 똑같은 작은 구성을 처음부터 다시 재현해 낼 수 있는 정도**입니다.

### B. 다음 단계: 짧게 곁들이면 오해를 막아주는 지식

- IP 주소 범위를 표기하는 CIDR 표기법, 내 개인 IP 1개만 뜻하는 `/32`와 전 세계 모든 인터넷 주소를 뜻하는 `0.0.0.0/0`의 의미. (복잡한 이진수 서브넷 계산 훈련을 필수로 하지 않습니다.)
- 콘솔에서 서브넷 이름을 'Public Subnet'이라고 붙여두었다고 해서 저절로 인터넷 접속이 되는 것은 아니라는 점.
- AWS 자원을 관리하는 IAM 사용자와 가상 서버 리눅스(Linux) OS 내부의 시스템 사용자 계정은 완전히 다른 신원이라는 점.
- AWS 가상 방화벽(보안 그룹)과 리눅스 운영체제 자체 방화벽, 그리고 웹 서버 프로그램이 특정 포트에서 대기(Listen)하는 것은 서로 다른 층이라는 점.
- 도메인 주소를 찾지 못한 DNS 오류, 서버와 연결조차 맺지 못한 TCP 접속 오류, 서버는 만났지만 파일이 없다는 HTTP 404 오류는 전혀 다른 성격의 실패라는 점.
- 상태 점검 주소(`/health`)에서 고정된 200 응답이 정상적으로 반환된다고 해서 웹사이트 화면 전체가 정상 동작함을 보장하는 것은 아니라는 점.
- SSH 원격 접속 키 파일을 분실했을 때 키를 새로 발급받는다고 해서 기존 서버에 자동으로 접속 권한이 복구되는 것은 아니라는 점.
- 무료 체험(프리 티어)이나 예산 알림 기능이 무조건 100% 무료를 보장하거나 초과 요금을 자동으로 차단해 주는 것은 아니라는 점.
- 콘솔 화면에서 자원을 삭제한 시점과 요금 대시보드 화면에 반영되는 시점 사이에 시간 차이가 존재할 수 있다는 점.

### C. 이후 심화: 후속 과제로 미루어 둘 지식

- 여러 데이터센터에 서버를 나누어 두는 다중 가용 영역(Multi-AZ) 고가용성 설계, 서버 자동 증설(Auto Scaling), 부하 분산기(ALB, Application Load Balancer), 재해 복구(DR) 체계.
- 외부 인터넷과 단절된 비공개 서브넷(Private Subnet), 인터넷 아웃바운드 전용 NAT 게이트웨이, AWS 내부 전용 VPC 엔드포인트를 결합한 복잡한 다계층 네트워크.
- 컨테이너 운영 관리 플랫폼인 쿠버네티스(Kubernetes).
- 인프라를 코드로 관리하는 테라폼(Terraform)이나 AWS CDK, 대기업 규모의 조직 단위 IAM 권한 거버넌스, 고도화된 모니터링 체계.
- 심도 있는 네트워크 패킷 단위 분석, 암호학, 대규모 트래픽 용량 계획, 기업용 장기 할인 비용 최적화 상품.

이러한 고급 기술들을 미리 알아두는 것은 유익하지만, B3-1의 기본 성공 경로와 원리를 이해하기 위한 필수 선수 조건은 아닙니다.

| 장애 분석 (Troubleshooting) | 통신 실패 구간을 가설로 좁히고 변경 조치 후 재검증 | 대규모 분산 추적 모니터링 플랫폼 구축 |
| 클라우드 비용 (Cost) | 내가 만든 자원을 꼼꼼히 추적하고, 완전히 삭제하여 정리 | 기업 전사 단위 클라우드 재무 관리(FinOps) 체계 도입 |

## 5. 이전 미션(B1-1)과 달라지는 학습 책임

- **B1-1 웹 포트폴리오 미션:** 사용자 브라우저 화면 안에서 일어나는 이벤트 → 상태 변화 → 화면 갱신(DOM) 흐름이 중심이었습니다.
- **B3-1 클라우드 인프라 미션:** 바깥 인터넷에서 출발한 외부 요청 → 클라우드 네트워크 경로 → 가상 서버 운영체제 및 프로세스 → 웹 응답 흐름이 중심입니다.

B3-1에서는 콘솔에서 누른 버튼 하나가 매달 요금이 청구되는 유료 자원 생성으로 이어지거나, 보안상 위험한 외부 노출로 이어질 수 있습니다. 따라서 **비용 통제, 보안 설정, 자원 정리는 실습이 다 끝난 뒤에나 챙기는 선택적 심화 과정이 아니라, 처음 시작할 때부터 반드시 함께 배우는 기본 필수기**입니다.

B1-1에서 아무리 멋진 웹사이트 코드를 완성해 두었더라도 클라우드 인프라의 동작 원리는 완전히 별도로 이해해야 합니다. 반대로 웹 서버가 단순한 기본 환영 페이지만 띄워주어도 외부 접속 검증 조건(A 또는 B)은 완벽히 만족할 수 있으므로, 이번 인프라 실습을 위해 웹 프론트엔드 기능을 무리하게 새로 추가할 필요는 없습니다.

## 6. 사수(선배 엔지니어)가 이해도를 점검할 질문 목록

다음 항목들은 학습자가 인프라를 제대로 이해했는지 확인하기 위한 점검 질문입니다. 공식 평가표가 아니며 실제 이해도 확인을 진행하기 전이므로 모두 미체크(`[ ]`) 상태입니다.

- [ ] 웹 브라우저에서 요청을 보냈을 때부터 Nginx 웹 서버에 도달하기까지 거치는 필수 클라우드 설정을 순서대로 설명할 수 있는가?
- [ ] 인터넷 게이트웨이(IGW), 라우팅 테이블(Route Table), 보안 그룹(SG)이 각각 어떤 문제를 해결하는 부품인지 구분할 수 있는가?
- [ ] AWS 콘솔에서 EC2 생성 권한이 없어 거절당하는 오류와, 내 컴퓨터 터미널에서 SSH 접속 인증이 실패하는 오류의 차이를 명확히 구분하는가?
- [ ] 서버 내부에서 `localhost` 접속은 성공하는데 바깥 인터넷에서 접속이 실패할 때, 확인해야 할 원인 후보를 단계별로 좁힐 수 있는가?
- [ ] 명확한 근거와 이해 없이 보안 그룹의 모든 포트를 열거나 최고 관리자 권한을 부여하여 보안 범위를 위험하게 확대하지 않는가?
- [ ] 내가 어떤 클라우드 자원들을 만들었으며, 실습이 끝난 뒤 어떤 순서로 안전하게 삭제해야 하는지 설명할 수 있는가?
- [ ] 가상 서버 종료 및 자원 삭제 후, 계정에 방치되어 요금이 발생할 수 있는 남은 자원이 없는지 직접 확인하였는가?
- [ ] 실습 종료 후 자원 정리를 마쳤기 때문에 외부 접속이 끊어진 시점과, 그 이전에 외부 접속 성공을 검증했던 증빙 자료를 논리적으로 구분하여 제시할 수 있는가?

## 7. 핵심 학습 원칙

**작은 인프라 구성을 정확하게 설명하고 안전하게 정리하여 끝마치는 것이, 동작 원리도 모른 채 수많은 클라우드 서비스를 잔뜩 붙여놓는 것보다 본 교육 목표에 훨씬 가깝습니다.**

확장 학습 문서는 앞으로 나아갈 길을 보여주는 지도입니다. 현재 단계에서는 필수 구현 조건과 증빙 요구사항을 철저히 지키며, 주변 개념들은 오해를 방지하고 문제를 논리적으로 해결하는 데 꼭 필요한 적정 깊이까지만 학습합니다.
