# B3-1의 교육 목표와 적정 학습 범위

[과제 요구사항 요약](0051-requirements-and-review-reference.md) · [필수 조건](0002-required-checklist-and-extension-rules.md) · [확장 지도](0003-cloud-foundations-beyond-assignment.md)

> 공식 소개·과제 목표·요구사항으로부터 교육 의도를 해석한다. 기관의 별도 교수설계·평가표는 미확인이다. 아래 학습 깊이는 사수 관점의 권장 기준이다.

## 1. 핵심: 서버 한 대를 안전하게 공개하고 설명하며 정리하기

이 과제는 단순히 웹사이트를 업로드하는 연습이 아니다. **네트워크·컴퓨트·접근 제어를 연결해 실제 요청을 통과시키고, 실패 원인을 증거로 좁힌 뒤 비용을 남기지 않도록 정리하는 클라우드 기초 실습**이다.

명세는 VPC/Subnet/Route Table/IGW의 역할, SG와 IAM의 차이, 외부 접속 조건, 트러블슈팅, 비용과 정리를 직접 설명하도록 요구한다. 그러므로 콘솔 클릭 절차를 외우거나 ‘화면이 떴다’는 결과만으로 학습 목표가 달성됐다고 할 수 없다.

반대로 대규모 상용 인프라·고가용성·Kubernetes·완성형 CI/CD까지 만들라는 과제도 아니다. 명세의 최소 구성은 VPC·Public Subnet·EC2 각 하나다.

## 2. 요구사항이 가르치는 사고

| 요구 | 교육 목적 | 이 단계의 설명 수준 |
| --- | --- | --- |
| VPC·Subnet | 네트워크 범위와 구역 | 어느 주소 범위에 서버가 있는지 |
| Route Table·IGW | 트래픽 경로 | 어느 Subnet이 어떤 경로를 쓰는지 |
| 퍼블릭 IP | 외부 도달 주소 | 주소만 있어도 접속되는 것은 아닌 이유 |
| EC2·웹 서버 | 컴퓨터와 서비스의 구분 | 인스턴스 실행과 웹 서버 실행의 차이 |
| SSH | 제한된 관리 접속 | 포트·소스 IP·키·사용자의 역할 |
| SG | 필요한 통신만 노출 | HTTP 공개와 SSH 제한의 이유 |
| IAM | 관리 작업의 최소권한 | 누가 AWS에서 무엇을 할 수 있는지 |
| 내부·외부 검증 | 실패 구간 분리 | localhost 성공과 외부 성공의 차이 |
| 오류 보고서 | 가설 검증 | 관찰→가설→검증→변경→재확인 |
| 정리 | 자원의 수명·비용 책임 | Stop/Terminate와 남는 자원 구분 |
| 다이어그램 | 실제 구성을 설명 | 그림과 실제 연결이 일치하는지 |

## 3. 세 층으로 나누는 학습 범위

### A. 직접 이해하고 수행할 핵심

- IP·포트·HTTP 요청/응답·localhost의 기본 의미.
- 지정된 네트워크 구성과 EC2의 외부 통신 조건.
- SG의 소스/포트와 IAM의 관리 권한 구분.
- SSH 접속, 웹 서버 실행, 기본 파일·서비스·로그 확인.
- 내부·외부 응답 검증과 최소 한 건의 실제 분석 기록.
- 리전·계정 조건·비용 요인 확인, 실제 자원 정리와 제출 근거.

깊이는 **각 설정이 필요한 이유를 설명하고, 관찰 가능한 오류를 분리하며, 동일한 작은 구성을 다시 만들 수 있는 정도**다.

### B. 짧게 곁들이면 오해를 막는 지식

- CIDR과 /32·0.0.0.0/0의 의미. 복잡한 서브넷 계산을 선행 시험으로 삼지 않는다.
- Public Subnet 이름만으로 접속되는 것은 아니라는 점.
- IAM 사용자와 Linux 사용자는 다른 신원이라는 점.
- SG와 OS 방화벽·서비스 리스닝은 다른 층이라는 점.
- 외부 DNS 조회·TCP 연결·HTTP 응답의 실패가 다르다는 점.
- /health 고정 200이 앱 전체 건강을 보장하지 않는다는 점.
- 키를 잃었을 때 재발급과 접속 복구가 같은 의미는 아니라는 점.
- 프리티어·예산 알림이 무조건 무료·자동 차단을 뜻하지 않는다는 점.
- 삭제 화면과 비용 표시의 반영 시점이 다를 수 있다는 점.

### C. 후속으로 미룰 지식

- 다중 AZ 고가용성·Auto Scaling·ALB·장애복구 설계.
- Private Subnet·NAT·VPC Endpoint를 포함한 다계층 서비스.
- Kubernetes·컨테이너 운영 플랫폼.
- Terraform/CDK·조직 단위 IAM·서비스 운영 지표·자동화 체계.
- 깊은 TCP 분석·암호학·용량 계획·비용 최적화 상품.

이 기술들을 알아두는 것은 좋지만 기본 성공 경로를 이해하기 위한 필수 선수조건은 아니다.

## 4. 여기까지면 충분하다

| 주제 | 지금 충분한 이해 | 과도한 선행 요구 |
| --- | --- | --- |
| VPC | 범위·Subnet·라우팅 연결 설명 | 기업 네트워크 전체 설계 |
| IAM | 필요한 작업을 제한하고 거절 이유 확인 | 조직·크로스계정 정책 전체 설계 |
| Linux | 필요한 파일·프로세스·서비스·로그 확인 | OS 내부·커널 튜닝 전문화 |
| Nginx | 정적 파일 제공·포트·로그·200 확인 | 고성능 리버스 프록시 운영 체계 |
| 장애 분석 | 실패 구간을 가설로 좁히고 재검증 | 분산 추적 플랫폼 구축 |
| 비용 | 만든 자원을 추적·정리·확인 | FinOps 체계 도입 |

## 5. B1-1과 달라지는 학습 책임

B1-1은 화면의 이벤트→상태→DOM 흐름, B3-1은 외부 요청→네트워크→프로세스→응답 흐름이 중심이다. B3-1은 버튼 하나가 유료 리소스 생성이나 접근 공개로 이어질 수 있다. 비용·보안·정리는 마지막 선택 심화가 아니라 처음부터 배우는 기본이다.

B1-1의 아름다운 사이트를 재사용해도 인프라 이해는 별도로 필요하다. 반대로 단순한 정상 응답만으로 외부 검증 조건을 충족할 수 있으므로 새 웹 기능을 대량 추가할 필요는 없다.

## 6. 사수가 이해를 확인할 질문

- [ ] 브라우저 요청부터 Nginx까지 필요한 설정을 순서대로 설명한다.
- [ ] IGW·Route Table·SG가 각각 해결하는 문제를 구분한다.
- [ ] EC2 생성 권한 오류와 SSH 인증 오류를 구분한다.
- [ ] localhost 성공/외부 실패에서 확인할 후보를 좁힌다.
- [ ] 증거 없이 보안 범위를 확대하지 않는다.
- [ ] 무엇이 생성됐고 어떤 순서로 지울지 설명한다.
- [ ] 종료/삭제 후 남은 자원을 실제로 확인한다.
- [ ] 정리 때문에 외부 접속이 중단된 시점과 이전 검증 증거를 구분한다.

공식 평가표가 아니며 실제 이해를 확인하지 않아 모두 미체크다.

## 7. 학습 원칙

**작은 구성을 정확히 설명하고 안전하게 끝내는 것이, 많은 서비스를 붙여 놓고 이유를 모르는 것보다 교육 목표에 가깝다.**

확장 문서는 미래의 지도다. 현재 필수 구현·증빙은 지키고, 주변 개념은 오해 방지와 문제 해결에 필요한 깊이만 더한다.
