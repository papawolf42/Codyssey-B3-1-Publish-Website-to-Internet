## 프로젝트부터 시작하되, 인프라 이해로 끝내기

> 이 문서는 42, 문제 기반 학습(PBL, Problem-Based Learning), 탑다운(Top-down) 학습, PRIMM 학습 모형에 관한 교육 원칙을 B3-1 AWS 클라우드 실습에 알기 쉽게 적용한 제안서입니다. 42의 공식 규칙이나 Codyssey의 공식 세부 평가표를 그대로 옮긴 문서가 아닙니다. 현재 시점에서는 어떠한 AWS 클라우드 자원도 생성하지 않았으며 실제 평가를 진행하지 않았습니다.

## 1. B3-1에서 실제로 배우려는 역량

겉으로 보이는 결과물은 '인터넷 브라우저에서 내 웹사이트가 열린다'이지만, 본 과제가 추구하는 진짜 교육 목표는 다음 역량들을 갖추는 것입니다.

- 외부 인터넷 요청이 IP 주소, 포트 번호, 라우팅 경로, 가상 방화벽, 웹 서버 프로그램을 거쳐 응답으로 돌아오는 전체 흐름을 막힘없이 설명할 수 있다.
- 가상 사설망(VPC), 하위 구역(Subnet), 경로 안내표(Route Table), 인터넷 관문(Internet Gateway)의 역할을 논리적으로 구분할 수 있다.
- 가상 방화벽인 보안 그룹(Security Group)과 AWS 관리 권한 체계인 IAM, 그리고 리눅스 운영체제 자체의 SSH 접속 인증을 서로 다른 층위의 보안 장치로 구분한다.
- 가상 컴퓨터 본체가 켜져 있다는 것과 웹 서버 프로그램이 요청을 정상 처리하고 있다는 것의 차이를 구분한다.
- 서버 내부에서의 접속 성공과 외부 인터넷에서의 접속 실패를 서로 다른 증거로 나누어 문제의 원인을 좁힐 수 있다.
- 필요한 최소한의 권한만 부여하고, 꼭 필요한 포트만 열어주며, 관리 접속은 개인 IP로만 좁히는 보안 원칙을 실제 인프라에 적용한다.
- 내가 만든 클라우드 자원의 수명 주기와 비용 요인을 파악하고, 실습이 끝난 뒤 완벽하게 삭제하여 정리할 수 있다.
- 구조 다이어그램, 접속 증빙 스크린샷, 오류 분석 보고서를 통해 다른 사람도 똑같이 재현할 수 있도록 내 인프라를 논리적으로 설명한다.

따라서 AWS 콘솔 화면에서 버튼을 클릭해 자원을 만들었다는 사실만으로 학습이 끝난 것으로 보지 않습니다. 반대로 AWS의 방대한 서비스들을 처음부터 모두 공부해야만 실습을 시작할 수 있는 것도 아닙니다.

## 2. 효과적인 학습 전략과 B3-1 적용 방식

B3-1 과제에는 검증된 현대적 학습 전략들을 유기적으로 결합합니다.

| 학습 전략 | 의미 | B3-1 과제에서의 구체적 적용 |
| --- | --- | --- |
| 탑다운 (Top-down) | 전체 큰 그림부터 먼저 보고 세부 부품으로 내려가는 방식 | 외부 인터넷 브라우저에서 웹사이트를 열어보는 전체 요청 흐름도부터 먼저 확인 |
| 문제 기반 학습 (PBL) | 마주친 구체적 문제를 해결하며 원리를 배우는 방식 | 접속 실패나 권한 거절 오류를 문제로 삼아 꼭 필요한 인프라 지식을 능동적으로 탐구 |
| 프로젝트 기반 학습 (PjBL) | 하나의 완성된 프로젝트를 제작하며 통합 역량을 쌓는 방식 | 네트워크, 가상 서버, 보안, 공식 문서, 자원 정리를 하나의 온전한 배포 결과물로 통합 |
| 적시 학습 (Just-in-time) | 필요한 순간에 꼭 필요한 지식만 집중해서 배우는 방식 | 현재 실패가 일어난 네트워크 계층에 필요한 IP, 라우팅, 방화벽, Nginx 지식만 먼저 학습 |
| 의도적 수련 (Deliberate practice) | 핵심 취약점을 겨냥해 난이도를 조절하며 연습하는 방식 | 정상 접속, 내부 성공, 외부 실패, 권한 거절 등 조건을 하나씩 바꾸며 결과를 비교 관찰 |
| PRIMM 모형 | 예측 → 실행 → 조사 → 수정 → 독립 제작 단계적 학습법 | 구성 예측(Predict) → 작은 실행(Run) → 로그 조사(Investigate) → 조건 변경(Modify) → 독립 진단(Make) |

이것은 '클라우드에 대해 아무것도 모른 채 콘솔에서 주먹구구식으로 버튼을 누른다'는 뜻이 결코 아닙니다. 클라우드는 비용 발생과 보안 사고의 위험이 따르므로, **요청 흐름과 안전 경계를 먼저 종이에 그리고 설명한 뒤, 학습자가 승인한 아주 작은 단위의 자원만 안전하게 생성**합니다.

## 3. 10가지 학습 원칙의 B3-1 적용

### 원칙 1. 겉보기 기능보다 실제 인프라 역량을 먼저 정한다

| 겉으로 보이는 콘솔 작업 | 실제로 훈련하는 핵심 인프라 역량 |
| --- | --- |
| 가상 사설망(VPC) 만들기 | 클라우드 내부의 네트워크 주소 범위와 다른 환경 간의 격리 원리 설명 |
| 공개 서브넷(Public Subnet) 만들기 | IP 주소 구역을 나누고 외부 인터넷으로 나갈 수 있는 구역의 조건 구분 |
| 인터넷 게이트웨이(IGW)와 라우팅 테이블 연결 | 데이터 패킷이 외부로 나가고 들어오는 구체적 이동 경로 추적 |
| 가상 서버(EC2) 실행 | 가상 컴퓨터 하드웨어 자원과 운영체제 위에서 도는 프로그램 서비스의 구분 |
| 웹 서비스(HTTP 80) 포트 열기 | 꼭 필요한 서비스만 외부에 노출한다는 기본 원칙 적용 |
| 원격 접속(SSH 22) 포트 제한 | 관리자 전용 통로를 전 세계에 노출하지 않고 내 개인 IP로 철저히 제한 |
| IAM 실습 사용자 또는 역할 만들기 | AWS 클라우드 자원을 다루는 관리 작업의 최소권한 설계 |
| Nginx 웹 서버 설치 및 실행 | 파일 저장 경로, 백그라운드 프로세스 동작, 포트 대기, 시스템 로그 관찰 |
| 외부 인터넷 접속 증명 | 서버 내부에서의 로컬 검증과 외부 인터넷에서의 원격 검증을 명확히 분리 |
| 자원 정리 체크리스트 작성 | 클라우드 자원의 수명 주기, 과금 요인, 실습 후 운영 책임 완수 |

생성한 리소스의 개수나 콘솔 캡처 사진의 장수보다, **각 설정을 왜 그렇게 했는지 이유를 설명하고 문제가 생겼을 때 어디를 살펴봐야 하는지 짚어내는 능력**이 훨씬 중요합니다.

### 원칙 2. 최종 요청 흐름은 먼저 보여주고 내부 구성은 융통성을 둔다

학습을 시작할 때 최종적으로 완성될 데이터 이동 흐름을 먼저 머릿속에 담습니다.

```text
외부 브라우저 또는 curl 요청
        ↓
공인 IP (Public IP) : 80번 포트
        ↓
가상 사설망(VPC) → 공개 서브넷(Public Subnet) → 라우팅 테이블(Route Table) → 인터넷 출입구(IGW)
        ↓
가상 서버(EC2)의 네트워크 카드와 가상 방화벽(보안 그룹, Security Group)
        ↓
가상 서버 내부에서 대기 중인 Nginx 웹 서버 : 80번 포트
        ↓
HTML 문서 또는 B1-1 포트폴리오 웹페이지 응답 반환
```

반드시 고정되어야 하는 필수 조건과 검증 기준은 다음과 같습니다.
- 외부에서 어떤 IP 주소나 URL로 접속하는가.
- 정상 응답(HTTP 200 OK 또는 정상 웹 화면)을 어떻게 확인하는가.
- 서버 내부 `localhost` 테스트와 바깥 인터넷 접속 테스트를 어떻게 구분하는가.
- HTTP 80 포트는 전체 공개되고 SSH 22 포트는 개인 IP로 안전하게 제한되었는가.
- 어떤 클라우드 자원을 만들었고 실습 후 어떻게 완전히 삭제했는가.

반면 다음 세부 항목들은 학습자가 자율적으로 선택할 수 있습니다.
- 리눅스 운영체제 선택 (Ubuntu LTS 또는 Amazon Linux 중 명세 범위 내 선택).
- Nginx 웹 서버의 설정 파일을 작성하고 편집하는 방식.
- 외부 접속 검증 방식 (웹 브라우저 화면 검증 방식 A 또는 `/health` 상태 점검 방식 B 중 하나).
- 아키텍처 다이어그램을 그리는 도구와 시각적 배치 방식.
- 문제 분석 보고서에서 사용할 구체적인 리눅스 관찰 명령어와 기록 서식.

### 원칙 3. 자기주도 학습과 단순 방치를 엄격히 구분한다

학습자에게 콘솔 메뉴 위치만 툭 던져주고 혼자 알아서 하라고 방치하지 않습니다. 사수는 다음 순서로 체계적인 가이드를 제공합니다.

1. 전체 요청 흐름도에서 지금 확인해야 할 네트워크 계층이 어디인지 짚어준다.
2. 터미널 명령어, AWS 콘솔 화면, 시스템 로그 파일 중 어디를 관찰해야 하는지 위치를 좁혀준다.
3. 관찰한 결과가 무엇을 뜻하는지 질문을 던져 스스로 해석하게 돕는다.
4. 문제를 해결하는 데 꼭 필요한 최소한의 개념만 간결하게 설명한다.
5. 설정을 바꿀 때는 한 번에 딱 한 가지만 바꾸도록 제한한다.
6. 복구 방법, 추가 요금 위험, 보안 위험을 먼저 확인한 뒤에 실행하도록 안내한다.
7. 문제가 해결된 뒤, 도움 없이 스스로 풀어볼 수 있는 비슷한 작은 진단 문제를 제시한다.

실제 클라우드 환경에서는 비용 발생과 보안 사고 위험이 있으므로, '자율성'이라는 핑계로 무제한 실행 권한을 주어서는 안 됩니다. 자원 생성, 삭제, 방화벽 개방은 항상 사전 확인을 거칩니다.

### 원칙 4. 안전하게 작동하는 아주 작은 인프라 성공을 단계별로 반복한다

처음부터 도커(Docker), HTTPS 암호화, 로드밸런서(ALB) 같은 고급 기능을 한꺼번에 붙이지 않습니다.

1. 종이에 외부 브라우저 요청부터 Nginx 웹 서버까지 데이터 이동 흐름을 직접 그린다.
2. 가상 서버(EC2) 내부에서 기본 Nginx 환영 페이지의 `localhost` 200 OK 응답을 먼저 확인한다.
3. VPC, 서브넷, 인터넷 게이트웨이, 라우팅 테이블이 실제로 올바르게 연결되어 있는지 확인한다.
4. 보안 그룹에서 웹 포트(HTTP 80)는 전체 공개하고, 원격 접속(SSH 22)은 개인 IP로 안전하게 제한한다.
5. 외부 인터넷 환경에서 서버의 공인 IP로 접속하여 정상 응답을 확인한다.
6. 이전 미션(B1-1)의 웹사이트 파일들을 서버로 복사 배포하고, 브라우저에서 화면 스타일과 이미지가 잘 뜨는지 확인한다.
7. 사전에 승인된 1건의 접속 오류를 관찰하고 원인을 분석하여 기록한다.
8. 외부 접속 증빙 스크린샷을 안전하게 확보한 뒤, 생성했던 모든 클라우드 자원을 깔끔하게 정리한다.

각 단계는 앞 단계의 성공을 바탕으로 진행하되, 만약 실패하더라도 그 원인이 오직 해당 단계 안에서만 발생하도록 범위를 철저히 제한합니다.

### 원칙 5. 자율적 선택권과 필수 학습 제약을 명확히 구분한다

새로운 제약을 둘 때마다 '이 제약을 통해 학습자가 무엇을 배우는가?'를 점검합니다.

- 서울 리전(`ap-northeast-2`), 공개 서브넷, EC2 가상 서버, SSH 원격 접속은 공식 학습 범위입니다.
- HTTP 80 공개와 SSH 22 개인 IP 제한은 보안의 핵심 원칙을 몸소 익히기 위한 필수 제약입니다.
- 보안 그룹의 모든 포트를 통째로 열어버리거나 최고 관리자 권한(`AdministratorAccess`)을 부여하는 것은 공부를 쉽게 하려는 위험한 편법일 뿐, 올바른 학습 방법이 아닙니다.
- 새 서비스를 많이 붙인다고 해서 무조건 훌륭한 엔지니어링이 아닙니다. 필수 요구사항이 아닌 NAT 게이트웨이, 로드밸런서(ALB), 데이터베이스(RDS) 등은 매달 큰 비용을 발생시키고 기본 네트워크 학습의 초점을 흐릴 뿐입니다.

### 원칙 6. 단순한 정상 접속 성공보다 실패가 일어나는 네트워크 구간을 발견한다

브라우저에 웹 화면이 한 번 떴다는 사실은 수많은 네트워크 과정 중 하나가 성공했음을 보여주는 단서일 뿐입니다. 문제가 발생했을 때 다음 구간들 중 어디에서 실패했는지 분리해 낼 수 있어야 합니다.

- 도메인 주소의 IP를 찾지 못한 DNS 오류.
- 서버 컴퓨터 문앞까지 도달하지 못해 발생하는 TCP 연결 거부나 시간 초과.
- 가상 방화벽인 보안 그룹(SG)에서 패킷이 차단된 경우.
- 라우팅 테이블, 인터넷 게이트웨이, 또는 서버의 공인 IP 조건이 누락된 경우.
- 가상 컴퓨터(EC2) 본체는 켜져 있으나 안쪽의 Nginx 웹 서버 프로그램이 꺼져 있는 경우.
- 웹 서버는 켜져 있으나 서비스 포트나 파일 경로 설정이 잘못되어 404 오류가 나는 경우.
- HTML 문서는 잘 받아왔으나 스타일시트(CSS), 자바스크립트, 외부 API 호출이 실패해 화면이 깨지는 경우.
- IAM 관리 권한이 모자라 AWS 콘솔 작업이 거절당하는 경우.
- SSH 네트워크 접속과 리눅스 운영체제 사용자 키 인증이 실패하는 경우.

오류를 마주치면 **증상 → 가설 → 검증 → 조치 → 결과 → 재발 방지**의 순서로 침착하게 기록합니다. 만약 실습 중 자연스러운 오류가 발생하지 않았다면, 사수와 상의하여 안전하고 복구 가능한 1건의 통제된 실험을 수행해 보되, 가짜 장애를 실제 일어난 것처럼 꾸며내지 않습니다.

### 원칙 7. 평가를 단순 검사가 아니라 설명·진단·대안을 나누는 성장의 시간으로 만든다

스스로를 점검하거나 동료 평가를 진행할 때 다음 질문들을 활용합니다.

1. 왜 내가 만든 서브넷이 '공개 서브넷(Public Subnet)'인가? 어떤 조건 때문에 외부와 통신할 수 있는가?
2. 인터넷 게이트웨이(IGW)와 라우팅 테이블(Route Table)은 각각 어떤 문제를 해결해 주는 부품인가?
3. 일반 웹 접속(HTTP 80)과 관리자 접속(SSH 22)의 방화벽 공개 범위를 왜 다르게 설정했는가?
4. AWS 콘솔에서 EC2 생성을 거절당하는 오류와, 내 컴퓨터 터미널에서 SSH 접속 인증이 실패하는 오류는 각각 어느 층위의 문제인가?
5. 서버 내부에서 `localhost` 테스트는 성공하는데 바깥 인터넷에서 접속이 안 된다면 무엇부터 의심해야 하는가?
6. Nginx가 200 정상 응답을 주었다고 해서 웹사이트 전체 기능이 완벽히 정상이라고 단정할 수 없는 이유는 무엇인가?
7. 이 인프라 구성을 다른 사람이 처음부터 똑같이 재현하려면 어떤 자원 ID, 방화벽 규칙, 작업 순서가 필요한가?
8. 더 안전하거나 단순한 대안은 무엇이며, 왜 이번 과제에서는 지금의 구성을 선택했는가?

### 원칙 8. 협업은 부품을 조각내는 것보다 전체 데이터 경로를 함께 이해하는 것이다

만약 동료와 함께 공부하더라도, 한 사람은 네트워크만 맡고 다른 사람은 Nginx만 맡는 식으로 역할을 완전히 쪼개어 고립시키지 않습니다.

- 네트워크를 주로 맡은 사람도 Nginx의 `localhost` 로컬 검증 원리를 설명할 수 있어야 합니다.
- 서버를 주로 다룬 사람도 보안 그룹과 라우팅 테이블의 경로 조건을 설명할 수 있어야 합니다.
- 문서를 정리하는 사람도 실제 클라우드 자원 목록과 삭제 순서를 직접 검증할 수 있어야 합니다.
- 한 사람이 의도적으로 작은 설정 오류를 만들면 다른 사람이 로그와 설정을 단서로 진단해 봅니다.
- 구조도를 그린 사람이 실제 AWS 콘솔 설정과 1:1로 일치하는지 함께 대조합니다.

혼자 공부할 때도 마찬가지로, 머릿속으로 각 역할의 입장이 되어 전체 경로를 말로 설명해 보는 연습을 합니다.

### 원칙 9. AI를 클라우드 개인 튜터로 활용하되 실행 권한과 최종 판단을 맡기지 않는다

인공지능(AI)에게는 다음과 같은 도움을 적극적으로 요청할 수 있습니다.
- 헷갈리는 클라우드 네트워크 및 보안 용어 비교 설명.
- 상태를 안전하게 살펴볼 수 있는 읽기 전용 콘솔 확인 위치나 리눅스 조회 명령어 추천.
- 시스템 로그 파일에서 의심해 볼 만한 네트워크 계층 분석.
- 아키텍처 다이어그램이나 공식 제출 보고서에서 빠진 항목이 없는지 점검.
- 내 이해도를 테스트해 볼 수 있는 새로운 작은 트러블슈팅 퀴즈 출제.

하지만 **AI가 작성해 준 명령어, IAM 정책 코드, 인프라 스크립트를 원리도 모른 채 그대로 복사해서 실행해서는 절대로 안 됩니다.** 명령어를 실행하기 전에 반드시 다음 사항들을 스스로 점검합니다.
1. 대한민국 서울 리전(`ap-northeast-2`)에 올바르게 적용되는 명령어인가?
2. 명령어가 가리키는 대상 리소스가 정확히 내가 만든 자원이 맞는가?
3. 단순히 상태를 조회하는 '읽기 전용' 명령인가, 아니면 설정을 바꾸거나 새로 만들거나 삭제하는 명령인가?
4. 이 명령으로 인해 추가 요금이 발생할 가능성이 있는가?
5. 보안 그룹이나 접근 권한을 위험하게 넓혀버리는 명령은 아닌가?
6. 실행한 뒤 문제가 생겼을 때 이전 상태로 안전하게 되돌릴 방법(복구 계획)이 있는가?

#### AI 없이 스스로 머릿속으로 점검해 볼 변형 퀴즈
- 인터넷 게이트웨이(IGW)는 VPC에 정상 연결되어 있는데, 라우팅 테이블에 `0.0.0.0/0` 기본 경로를 적지 않았을 때 통신이 어디서 막히는지 설명할 수 있는가?
- Nginx 웹 서버 내부 테스트(`curl localhost`)는 200으로 성공하는데 외부 인터넷 접속이 안 될 때 의심해야 할 3가지 후보 계층은 무엇인가?
- 보안 그룹에는 HTTP 80번 포트가 활짝 열려 있는데 브라우저에서 '사이트에 연결할 수 없음'이 뜰 때 무엇부터 확인해야 하는가?
- 가상 서버(EC2)를 분명히 삭제(Terminate)했는데도 계정에 남아 요금을 발생시킬 수 있는 고아 자원은 무엇이 있는가?
- AWS 콘솔의 IAM 권한 오류와 리눅스 터미널의 `Permission denied` 오류의 차이를 설명할 수 있는가?

### 원칙 10. 한 번의 성공으로 끝내지 않고 새로운 장애와 변형 상황으로 응용력을 넓힌다

한 번 성공한 구성을 그대로 외워서 똑같이 누르는 것만으로는 응용력이 생기지 않습니다. 다음과 같이 작은 조건을 변형해 가며 이해를 확장합니다.

- Nginx 기본 환영 페이지를 내 B1-1 포트폴리오 웹사이트 파일로 안전하게 교체해 보기.
- 헬스체크 주소(`/health`)를 추가하고, 전체 웹 브라우저 검증과 헬스체크 검증의 목적 차이를 비교해 보기.
- 웹 문서는 정상 응답을 유지한 채 특정 스타일시트(CSS) 파일 경로만 의도적으로 틀어보고, 브라우저 개발자 도구의 네트워크 탭에서 찾아보기.
- 서버 내부 `localhost` 성공 / 외부 인터넷 접속 실패 상황의 점검 순서를 동료에게 말로 설명해 보기.
- 내 컴퓨터의 인터넷 IP 주소가 바뀌었을 때, 보안 그룹의 SSH 22번 포트 허용 규칙을 안전하게 갱신하는 계획 세워보기.
- 자원 정리 체크리스트에서 내가 실제로 만들었던 자원과 만들지 않은 자원을 목록으로 완벽히 대조해 보기.

## 4. PRIMM 학습 모형의 B3-1 구체적 적용

| PRIMM 단계 | 학습자 행동 | B3-1 과제에서의 구체적 예시 |
| --- | --- | --- |
| **Predict (예측하기)** | 명령이나 설정을 바꾸기 전에 일어날 결과를 먼저 예상해 봅니다. | \"라우팅 테이블에 인터넷 출구가 등록되어 있지 않다면, 외부에서 들어온 요청이 네트워크의 어느 지점에서 막힐까?\" |
| **Run (작은 실행)** | 사용자 승인 아래 안전하게 격리된 최소 단위를 실행합니다. | 가상 서버 내부에서 `curl http://localhost`를 실행해 보거나, 읽기 전용 상태 조회 명령을 칩니다. |
| **Investigate (조사하기)** | 실제 설정, 시스템 로그, 네트워크 경로를 꼼꼼히 조사합니다. | 보안 그룹 규칙, 라우팅 테이블 경로, Nginx 서비스 상태(`systemctl status`)와 접속 로그를 대조합니다. |
| **Modify (수정하기)** | 여러 설정을 한 번에 바꾸지 않고 한 번에 딱 한 가지 조건만 변경합니다. | 방화벽 규칙 1개, 파일 경로 1개, 웹 서버 설정 1개 중 의심되는 한 가지만 조정한 뒤 결과를 다시 봅니다. |
| **Make (독립 제작)** | 도움 없이 비슷한 구성이나 새로운 장애 진단을 직접 수행합니다. | 완전히 새로운 외부 접속 실패 시나리오를 마주쳤을 때 스스로 점검 가설을 세우고 해결합니다. |

## 5. B3-1 실습의 전체 실행 루프

### 단계 0. 전체 큰 그림과 안전 경계 확인 (사전 준비)
- 공식 제출물 목록(구조도, README, 트러블슈팅 보고서, 정리 체크리스트)과 최소 네트워크 아키텍처를 확인합니다.
- 내 AWS 계정의 프리 티어 남은 혜택, 보유 크레딧, IAM 사용자 권한, 서울 리전(`ap-northeast-2`) 설정을 확인합니다.
- 앞으로 만들 자원 목록, 요금이 발생할 수 있는 유료 항목, 실습 종료 후 삭제할 순서를 미리 계획합니다.
- 이 단계에서는 실제 AWS 자원을 단 하나도 만들지 않으며, 종이에 데이터 요청 흐름도와 구조도 초안을 먼저 그립니다.

### 단계 1. 서버 내부에서의 작은 성공
- 가상 컴퓨터(EC2)와 리눅스 운영체제의 역할을 이해합니다.
- Nginx 웹 서버가 어떤 원리로 웹 문서를 서비스하는지 이해합니다.
- 서버 안에서 `curl http://localhost`로 200 OK 응답을 확인하고 프로세스 및 서비스 상태를 점검합니다.
- 서버 내부 로컬 테스트의 성공을 바깥 인터넷에서의 성공과 혼동하지 않습니다.

### 단계 2. 네트워크 길목의 작은 성공
- 가상 사설망(VPC), 공개 서브넷, 인터넷 게이트웨이(IGW), 라우팅 테이블의 실제 연결 관계를 확인합니다.
- 사설 IP 주소와 공인 IP 주소, 그리고 데이터 이동 경로를 실제 콘솔 설정과 다이어그램 그림에 1:1로 대응시킵니다.
- 일반 웹 통신(HTTP 80)과 관리자 접속(SSH 22)의 목적과 허용 IP 범위를 엄격히 분리합니다.

### 단계 3. 바깥 인터넷에서의 응답 검증
- 외부 인터넷 브라우저에서 공인 IP로 접속(방식 A)하거나, `/health` 상태 점검(방식 B) 중 하나를 선택해 검증합니다.
- 서버 내부에서의 성공 증거와 바깥 인터넷에서의 성공 증거를 별도의 스크린샷으로 남깁니다.
- B1-1 포트폴리오 웹사이트 파일을 배포했다면 HTML, CSS, JS, 이미지, 외부 API 호출이 각각 정상 작동하는지 브라우저 개발자 도구에서 확인합니다.

### 단계 4. 장애 관찰 · 수정 · 보고서 작성
- 실습 중 마주친 단 1건의 접속 오류를 주의 깊게 관찰합니다.
- 의심되는 네트워크 계층을 나누고, 가장 부담 없는 읽기 전용 확인(상태 확인, 로그 확인)부터 시작합니다.
- 한 번에 딱 한 가지 조치만 적용하고 결과를 다시 테스트합니다.
- 변경 전후의 화면과 해결 과정을 공식 트러블슈팅 보고서 서식에 기록합니다.

### 단계 5. 자원 정리 · 학습 회고 · 응용력 확장
- 외부 접속 성공 스크린샷 증빙을 안전하게 먼저 저장합니다. (자원을 지우고 나면 당연히 접속이 끊어집니다.)
- 실제로 생성했던 클라우드 자원 목록과 체크리스트를 하나씩 대조합니다.
- 사용자의 최종 승인을 받은 뒤 정해진 순서대로 자원을 완전히 삭제하고, 남겨진 디스크나 고정 IP가 없는지 확인합니다.
- 다음 날 똑같은 요청 흐름을 다른 사람에게 말로 설명해 보고, 일주일 뒤 작은 장애 시나리오를 스스로 진단해 봅니다.

| --- | --- | --- | --- |
| 요청 흐름도 | 외부 브라우저 → 공인 IP → 포트 → Nginx 흐름도 스케치 | 각 계층과 부품의 역할 설명 | 데이터 경로의 어느 부품이 빠지면 어디서 멈출지 표시해 보기 |
| 네트워크 구성 | 라우팅 테이블에 인터넷 게이트웨이(IGW) 연결 확인 | 사설망 주소 대역과 외부 경로의 차이 설명 | 이름만 'Public Subnet'이고 라우팅 경로가 없을 때의 증상 추론 |
| 접근 제어 | HTTP 80은 전체 공개, SSH 22는 내 개인 IP로 제한 | 가상 방화벽(SG), IAM 권한, SSH 인증의 차이 | 각각의 오류가 났을 때 살펴봐야 할 보안 장치 선택 |
| 가상 서버 | 가상 서버 내부에서 `curl localhost` 200 OK 확인 | 가상 컴퓨터 본체와 내부 서비스 프로그램 구분 | 웹 서버 프로세스를 껐을 때와 켰을 때의 터미널 상태 비교 |
| 외부 접속 검증 | 외부 브라우저에서 공인 IP로 접속하여 정상 화면 확인 | 내부 검증 증거와 외부 검증 증거의 분리 | 외부 접속이 안 될 때 방화벽/경로/웹서버 가설 순서 세우기 |
| 웹사이트 배포 | B1-1 포트폴리오 파일 배포 및 화면 리소스 로딩 확인 | 웹 서버의 파일 제공과 브라우저의 화면 렌더링 분리 | CSS 파일 경로를 일부러 틀리게 한 뒤 개발자 도구에서 찾기 |
| 오류 분석 | 공식 트러블슈팅 보고서 1건 작성 완료 | 증거에 기반한 체계적 원인 분석과 조치 | 다른 가상의 접속 장애 시나리오에 대한 조사 계획서 작성 |
| 자원 정리 | 실습에 사용한 모든 자원의 완전 삭제 및 0원 확인 | 클라우드 자원의 수명 주기와 비용 책임 완수 | 콘솔에서 방치된 미사용 EBS 볼륨이나 고정 IP 직접 찾아내기 |

## 7. 학습자의 수준에 맞춰 지원을 줄여가는 기준

| 학습자 수준 | 사수 또는 AI가 제공하는 도움의 범위 | 다음 단계로 넘어가기 위한 조건 |
| --- | --- | --- |
| **입문 수준** | 전체 요청 흐름도, 기본 용어 풀이, 안전한 상태 조회 위치를 상세히 안내 | 서버 내부 성공과 바깥 인터넷 성공의 본질적 차이를 스스로 질문할 수 있음 |
| **초급 수준** | 콘솔의 메뉴 위치, 명령어의 구체적 쓰임새, 의심되는 오류 후보군을 제시 | 한 네트워크 계층의 상태를 직접 확인하고 그 결과의 의미를 해석할 수 있음 |
| **중급 수준** | 공식 AWS 설명서 링크, 최종 검증 기준, 핵심 힌트 위주로 제공 | 오류를 만났을 때 원인 후보를 두세 군데의 네트워크 계층으로 스스로 좁힐 수 있음 |
| **숙련 전환** | 증상, 보안 제약 조건, 최종 완료 기준만 제시하고 개입을 최소화 | 처음 보는 새로운 인프라 구성이나 접속 오류를 도움 없이 독립적으로 진단할 수 있음 |

학습자의 지원량은 다루는 개념에 따라 얼마든지 다를 수 있습니다. 프론트엔드 개발(B1-1)을 아주 잘하는 사람이라도 클라우드 가상망(VPC)은 처음 접하는 입문자일 수 있습니다.

## 8. B3-1 과제를 종합적으로 평가한다면 던질 핵심 질문들

이 표는 공식 배점표가 아니며, 학습자의 종합적인 이해를 돕기 위한 교육적 확인 기준입니다.

| 평가 영역 | 사수의 핵심 확인 질문 |
| --- | --- |
| **기본 동작 검증** | 서버 내부(`localhost`) 검증과 바깥 인터넷 검증을 명세가 요구한 방식대로 각각 명확히 증명하였는가? |
| **설계 논리 설명** | 가상망, 서브넷, 인터넷 출입구, 방화벽 규칙을 왜 그렇게 만들었는지 그 이유를 설명할 수 있는가? |
| **보안 원칙 준수** | 모든 포트를 열어버리거나 최고 관리자 권한을 남용하지 않고, 최소권한과 포트 격리 원칙을 지켰는가? |
| **체계적 문제 진단** | 접속 오류가 발생했을 때 주먹구구식이 아닌 객관적 화면과 로그 증거를 바탕으로 원인을 좁혔는가? |
| **독립적 응용 역량** | 처음 마주치는 접속 실패, 권한 거절, 자원 정리 변형 상황을 자신의 말로 설명할 수 있는가? |
| **비용 및 자원 관리** | 요금이 발생할 수 있는 요인을 사전에 파악하고, 실습 후 남겨진 자원이 없도록 완벽히 삭제했는가? |
| **문서 작성 충실도** | 구조도, README, 트러블슈팅 보고서, 정리 체크리스트가 실제 클라우드 구성 상태와 정확히 일치하는가? |
| **학습 회고와 계획** | 이번 실습을 통해 무엇을 완벽히 이해했고, 앞으로 어떤 클라우드 영역을 더 배울 것인지 정리했는가? |

단순히 브라우저 정상 화면 캡처 하나만 내밀거나 콘솔 화면을 복사해 붙여넣는 방식으로는 본 과제가 요구하는 인프라 역량을 증명할 수 없습니다.

## 9. 실패와 성공 뒤에 남길 회고 기록 양식

작은 인프라 구성에 성공했거나 오류를 해결했을 때마다 아래 서식에 맞춰 짧은 회고를 남깁니다.

```text
이번에 정상 작동한 요청 경로:
내가 직접 확인한 자원 ID, 방화벽 규칙, 시스템 로그:
처음에 세웠던 가설과 실제 관찰된 결과:
내가 변경한 설정 내용과 이전으로 안전하게 되돌리는 방법:
다음에 도움 없이 혼자서 진단해 볼 수 있는 변형 문제:
아직 다른 사람에게 명쾌하게 설명하지 못하는 부족한 부분:
```

> **주의:** SSH 원격 접속 비밀 키 내용, AWS 계정의 비밀 토큰, 타인에게 노출되면 안 되는 민감한 정보는 회고 문서에 절대로 기록하지 않습니다. IP 주소나 자원 식별 번호도 필요한 경우 예시값으로 바꾸어 안전하게 보관합니다.

## 10. 이번 과제에서 적용하지 않을 주의 사항

- 추가 요금이 발생할 수 있거나 외부 인터넷에 위험하게 포트를 개방하는 작업을 맹목적으로 반복하지 않습니다.
- 실제 발생하지도 않은 가짜 장애를 과제 제출물을 채우기 위해 실제 사고인 것처럼 꾸며내지 않습니다.
- 명세에 요구되지 않은 수많은 AWS 서비스를 잔뜩 붙여놓는 것을 엔지니어링 실력이나 학습 성과로 포장하지 않습니다.
- AI가 추천해 준 IAM 보안 정책이나 터미널 삭제 명령어를 원리 검토 없이 무작정 실행하지 않습니다.
- 인프라 자동화 도구를 썼다고 해서 네트워크, 보안, 자원 수명 주기에 대한 기초 원리를 이해한 것으로 착각하지 않습니다.
- 개인적인 경험담이나 특정 사설 부트캠프의 홍보 문구를 B3-1 과제의 공식 평가 기준으로 삼지 않습니다.

## 11. B3-1 학습의 본질을 한 문장으로 요약하기

> **AWS 클라우드에 먼저 안전한 작은 요청 길목을 하나 완성하고, 필요한 네트워크·서버 개념을 역추적하여 이해한 뒤, 접속 실패를 증거로 진단하며, AI의 도움을 점차 줄여나가 마지막에는 새로운 장애와 자원 정리 문제를 스스로 해결합니다.**
