# AMI를 내 PC에 보관하고 나중에 업로드해 복원할 수 있나?

[AMI 백업 기본 설명](0045-ami-backup-restore-선택지.md) · [정리 체크리스트](cleanup-checklist.md)

## 결론

가능한 방식이 있다. AWS의 AMI Store/Restore 기능으로 AMI를 S3의 단일 객체로 보관하고, 그 파일을 PC에 다운로드했다가 나중에 S3로 다시 올려 AMI를 복원할 수 있다. AWS 공식 문서도 노트북 등 중간 호스트에 다운로드하고 다시 업로드하는 과정을 예시로 든다.

이 방식은 AWS에 원본 AMI·스냅샷을 계속 유지해야만 하는 방식과 다르다. 백업의 무결성·복원 가능성을 확인한 뒤 관련 AWS 자원을 실제로 모두 정리하고 PC 파일만 보유하는 상태를 만들 수 있다. 다만 현재 서버의 최종 지원 조건·IAM·비용은 별도 점검 전이며, 파일이나 AWS 자원 생성·다운로드·삭제를 실행한 것은 아니다.

## 1. 전체 흐름

1. 현재 설정된 EC2에서 자기 계정 소유의 비공개 EBS-backed AMI를 생성한다. 공개 Amazon Linux 기본 AMI를 그대로 보관하는 것과 다르다.
2. `CreateStoreImageTask`로 이 AMI를 비공개 S3 버킷의 단일 보관 객체로 만든다.
3. 작업 완료를 확인하고 객체를 PC의 안전한 백업 위치로 다운로드한다.
4. 무결성과 복원 가능성을 검증한다. 다운로드가 끝났다는 이유만으로 원본을 바로 지우지 않는다.
5. 보존 방침에 따라 EC2·EBS·네트워크뿐 아니라 원본 AMI·스냅샷·임시 S3 객체와 작업 전용 버킷까지 실제 정리한다.
6. 필요할 때 파일을 같은 복원 리전의 비공개 S3 버킷에 업로드한다.
7. `CreateRestoreImageTask`로 새 AMI와 관련 스냅샷을 복원한다.
8. 새 AMI로 EC2를 생성하고 네트워크·보안·DNS를 연결한 뒤 SSH·HTTP·HTTPS를 재검증한다.
9. 복원 과정에서 다시 만든 임시·실습 자원도 나중에 정리한다.

AMI 보관 파일은 예를 들어 `.bin` 객체로 다루는 AWS 형식이다. 임의의 ISO나 VMware 이미지 파일을 같은 API에 올리면 복구되는 것은 아니다. 일반 VM Import/Export는 별도 기능이며 OS·커널·암호화 등 지원 조건이 다르므로 혼동하지 않는다.

## 2. 콘솔만으로 끝나는 간단한 다운로드 버튼은 아니다

공식 문서상 AMI Store/Restore API는 AWS CLI·SDK·EC2 API로 사용하며 EC2 콘솔의 Store/Restore 작업으로 지원되는 것은 아니다. S3 파일 업로드·다운로드 자체와 AMI 변환·복원 API 작업을 구분해야 한다.

현재 과제용 IAM 정책에는 필요한 Store/Restore·S3·EBS Direct API 권한이 준비돼 있지 않다. 임시 버킷·객체·리전·작업 범위를 좁힌 별도 권한 검토가 필요하다. 이를 이유로 AdministratorAccess나 S3 전체 권한을 붙이지 않는다. 과제 기본 구성 밖의 백업 확장 작업임을 구분한다.

## 3. 지원 조건과 비용

- EBS-backed AMI이며 소유 또는 직접 공유 조건을 충족해야 한다. 공개 공유만 된 AMI는 보관 대상이 아니다.
- PV AMI는 지원하지 않는다. 용량·동시 작업 한도도 있다.
- 보관 작업이 진행되는 동안 원본 스냅샷과 접근 권한을 유지해야 한다.
- 복원되는 AMI ID는 원본과 달라진다. 새 EC2 IP도 다시 확인한다.
- S3 저장·요청·데이터 전송과 EBS Direct API 등 사용 서비스에 비용이 발생할 수 있다. PC로 내려받는 과정까지 전부 무료라고 보장할 수 없다.
- PC 파일만 남기고 AWS 관련 자원을 모두 지운 뒤에는 그 로컬 파일 자체에 AWS 저장료가 붙는 것은 아니다. 다시 업로드·복원·실행할 때 비용이 다시 발생할 수 있다.

## 4. 이미지 안의 민감 정보

현재 서버에는 TLS 개인키와 Certbot 계정 정보가 있다. 이미지에도 포함될 수 있으므로 사실상 민감한 백업 파일로 취급한다.

- 비공개 S3, 적절한 객체 암호화·접근 제어를 사용한다.
- 공식 안내는 암호화된 스냅샷도 보관 작업 과정에서 복호화된다고 명시한다. EBS 암호화가 그대로 외부 보관 파일을 보호한다고 가정하지 않는다.
- PC에서는 Git 밖의 사용자 지정 백업 위치에 암호화해 보관한다. 프로젝트나 공개 자료에 넣지 않는다.
- 이미지 내용이나 개인키를 채팅·문서·스크린샷에 풀어 보여주지 않는다.
- PC의 SSH 개인키 파일은 EC2 밖에 있으므로 별도 안전 보관 대상이다.

## 5. 전체 환경이 통째로 자동 복원되는 것은 아니다

소프트웨어·서버 내부 파일이 보존되더라도 VPC·Subnet·IGW·라우팅·SG·DNS 등은 따로 준비한다. AMI 복원만 하면 바로 도메인 서비스가 원래대로 된다고 생각하면 안 된다.

인증서를 이미지에 보존해도 만료일이 연장되지 않는다. 지금 확인된 인증서 만료일은 2027-01-17이고 자동 갱신 설정은 생략했다. 복원 시 유효 기간·키·설정·실제 TLS 동작을 다시 확인한다.

## 6. 과제에서의 판단

복원 준비를 위해 AWS에 파일·스냅샷을 계속 남기지 않고 PC에만 보관하는 것은 과금 자원 정리와 양립할 수 있다. 그러나 임시 S3 객체나 스냅샷이 남은 상태를 완전 정리라고 기록해서는 안 된다. 버전 관리 버킷이면 삭제 마커만이 아니라 실제 객체 버전과 잔존 데이터도 확인해야 한다. 다른 프로젝트가 쓰는 공유 버킷은 무작정 삭제하지 않는다.

파일 백업은 복구 편의를 위한 것이며, 과제의 실제 리소스 삭제·결과 확인·체크리스트를 대신하지 않는다. 현재 단계에서 검토할 것은 지원 조건·최소권한·임시 비용·보관 보안이고, 실행은 사용자 확인 후에만 진행한다.
