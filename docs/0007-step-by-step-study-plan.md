[실제 따라하기 교재](0008-complete-step-by-step-workbook.md)를 새로 추가했다. 이 문서는 전체 계획을 실제 행동 단위로 더 잘게 쪼갠 실행용 교재이며, 이 문서의 개요를 먼저 검토한 뒤 0008을 위에서부터 따라간다.

> 이 문서는 B3-1을 어떤 순서로 공부하고 실제 AWS 실습으로 연결할지 정리한 **검토용 계획**이다. 아직 이 문서의 단계를 완료했다는 뜻이 아니며, 이 문서를 작성하면서 AWS 리소스 생성·변경·삭제·배포를 실행하지 않았다.

## 1. 이 계획의 학습 목표

B3-1의 목표는 서버 한 대를 띄워 화면을 보여주는 데서 끝나지 않는다. 다음 요청 경로를 만들고, 각 구간이 왜 필요한지 설명하고, 실패하면 증거를 바탕으로 고치고, 끝나면 안전하게 정리하는 것이 핵심이다.

```text
외부 브라우저
  → Public IP : 80
  → VPC / Public Subnet
  → Route Table / Internet Gateway
  → EC2 네트워크 인터페이스 / Security Group
  → EC2 운영체제 / Nginx : 80
  → B1-1 정적 파일
  → HTTP 응답
```

학습이 끝났을 때 다음을 설명할 수 있어야 한다.

- IP·포트·HTTP·라우팅이 요청과 응답에서 어떤 역할을 하는가.
- VPC·Subnet·Route Table·Internet Gateway가 서로 어떻게 연결되는가.
- Public Subnet이라는 이름이 아니라 실제 경로·공인 IP·보안 규칙이 외부 접속을 결정하는 이유.
- Security Group, IAM, SSH 키, Linux 사용자, Nginx가 서로 다른 보안·운영 층에 있는 이유.
- EC2가 실행 중인 것과 Nginx가 HTTP 응답을 하는 것이 다른 이유.
- 내부 `localhost` 성공과 외부 접속 성공을 별도의 증거로 확인하는 방법.
- 실제 오류 또는 승인된 통제 실험을 증상·가설·검증·조치·결과·재발 방지로 기록하는 방법.
- 비용이 남을 수 있는 자원을 추적하고, 모든 리소스를 삭제한 뒤 남은 항목을 확인하는 방법.

## 2. 안전 경계와 학습 운영 규칙

### 2.1 AWS 작업 전제

- 현재 계획 단계에서는 AWS 리소스를 생성하지 않는다.
- 계정·리전·프리 티어·크레딧·예상 비용을 먼저 확인한다.
- 리소스 생성·보안 그룹 변경·SSH 규칙 변경·삭제는 사용자의 명시적 승인을 받은 범위에서만 실행한다.
- Root 계정과 `AdministratorAccess`로 문제를 우회하지 않는다.
- 비밀번호·액세스 키·SSH 개인 키·세션 토큰은 문서나 저장소에 기록하지 않는다.
- 실습에 필요한 범위보다 많은 포트·권한·서비스를 만들지 않는다.

### 2.2 한 단계에서 반복할 루프

1. **예측:** 이 요청이 어느 지점까지 도달할지 말한다.
2. **개념:** 현재 단계에 필요한 용어 하나 또는 관계 하나를 배운다.
3. **읽기 확인:** 콘솔·문서·로그·안전한 상태 조회 중 가장 작은 확인을 한다.
4. **작은 실행:** 승인된 경우에만 한 리소스 또는 한 규칙을 변경한다.
5. **관찰:** 내부·외부·로그·상태를 구분해 확인한다.
6. **설명:** 각 설정이 왜 필요한지 자기 말로 설명한다.
7. **변형:** 한 조건만 바꾸어 결과를 예측한다.
8. **복구·정리:** 되돌리고, 비용과 보안 영향을 확인한다.

### 2.3 AI 사용 규칙

AI에게 다음을 요청할 수 있다.

- 요청 경로를 계층별로 나누기.
- 특정 오류에서 읽어볼 로그·설정·상태 조회 위치 좁히기.
- IAM 정책·보안 그룹 규칙의 누락 점검.
- 보고서·다이어그램의 설명 누락 점검.
- AWS 리소스를 만들지 않는 가상 트러블슈팅 문제 출제.

AI가 제안한 AWS 명령을 곧바로 실행하지 않는다. 명령마다 읽기인지 변경인지, 대상 리전·리소스가 무엇인지, 비용·공개 범위를 넓히는지, 되돌릴 방법이 있는지 확인한다.

## 3. 단계별 전체 순서

각 단계의 `통과 기준`을 만족하면 다음 단계로 넘어간다. 실패하면 새 리소스를 더 만들지 말고 현재 계층을 먼저 진단한다.

### 0단계. 과제 범위와 안전 계획 확인

목표: 만들 것과 만들지 않을 것을 먼저 고정한다.

배울 내용:

- `instruction.md`의 공식 결과물·필수 구성·선택 보너스.
- B1-1 정적 사이트와 B3-1 EC2 배포의 관계.
- 서울 리전 `ap-northeast-2`, Public Subnet, HTTP 80 공개, SSH 22 개인 IP 제한.
- 비용이 발생할 수 있는 EC2·EBS·Elastic IP·NAT Gateway·ALB·RDS.
- 생성 목록과 삭제 목록을 같은 문서에서 추적하는 이유.

작은 활동:

1. 공식 필수·선택·후속 학습을 세 묶음으로 나눈다.
2. 최소 구성도를 그린다.
3. 각 리소스의 이름·태그·생성 여부·삭제 방법을 표로 만든다.
4. 현재 실제 AWS 리소스가 생성되지 않았음을 기준선으로 기록한다.

통과 기준:

- 이번 실습의 최소 아키텍처를 말할 수 있다.
- 예상 비용과 삭제 순서를 설명할 수 있다.
- 어떤 작업이 사용자 승인 없이는 실행되지 않는지 구분한다.

### 1단계. 외부 웹 요청 전체를 먼저 보기

목표: 콘솔 메뉴보다 요청 흐름을 먼저 이해한다.

배울 내용:

- 브라우저와 서버.
- HTTP 요청·응답과 상태 코드.
- IP 주소·포트·`localhost`.
- GitHub Pages가 대신 관리하는 부분과 EC2에서 직접 관리해야 하는 부분.

작은 활동:

1. 외부 브라우저 → Public IP → 80번 포트 → Nginx → HTML 응답을 그림으로 그린다.
2. 같은 `localhost`라도 노트북과 EC2 내부에서 서로 다른 컴퓨터를 가리킨다는 점을 설명한다.
3. DNS 실패·TCP 연결 실패·HTTP 404를 서로 다른 문제로 분류한다.

통과 기준:

- 어느 컴퓨터에서 어느 IP·포트로 요청했는지 말할 수 있다.
- 웹페이지가 보이지 않을 때 주소·연결·HTTP 응답 중 어느 단계가 실패했는지 가설을 세울 수 있다.

### 2단계. AWS 계정·리전·권한의 기본

목표: AWS에서 누가 어떤 리소스를 어느 지역에서 관리하는지 이해한다.

배울 내용:

- AWS 리전과 서울 리전 `ap-northeast-2`.
- IAM 사용자·역할·정책.
- AWS 관리 권한과 EC2 안의 Linux 사용자 계정의 차이.
- Root 계정과 최소권한 원칙.

작은 활동:

1. 실제 계정에서 리전 선택이 리소스 위치에 미치는 영향을 문서로 확인한다. 실제 변경은 하지 않는다.
2. EC2 생성 권한과 SSH 로그인 권한이 왜 다른지 설명한다.
3. 이번 실습에 필요한 관리 작업을 생성·조회·태그·연결·삭제로 나눈다.
4. 허용할 권한과 필요하지 않은 S3·RDS 등 권한을 구분한다.

통과 기준:

- IAM 권한 오류와 Linux `Permission denied`를 구분한다.
- `AdministratorAccess`가 안전한 학습 해법이 아닌 이유를 설명한다.
- 실제 정책을 만들기 전에 필요한 범위와 제한을 검토할 수 있다.

### 3단계. VPC·Subnet·CIDR

목표: 가상 네트워크의 범위와 구역을 이해한다.

배울 내용:

- VPC는 AWS 안에서 논리적으로 분리된 네트워크다.
- Subnet은 VPC 주소 범위를 나눈 구역이다.
- CIDR 표기법과 주소 범위.
- Public Subnet과 Private Subnet의 구분.
- 리전·가용 영역·서브넷의 관계.

작은 활동:

1. VPC와 Subnet을 종이에 중첩해서 그린다.
2. `10.0.0.0/16`과 예시 서브넷 대역의 관계를 확인한다.
3. `/32`와 `0.0.0.0/0`이 허용 범위를 어떻게 바꾸는지 설명한다.
4. 서브넷 이름만 Public으로 바꿔도 인터넷 연결이 되지 않는 이유를 적는다.

통과 기준:

- VPC와 Subnet을 혼동하지 않는다.
- 주소 구역과 외부 연결 경로를 별개의 문제로 설명한다.
- 이번 단계에서는 실제 리소스를 만들지 않고 구성도를 설명할 수 있다.

### 4단계. Route Table과 Internet Gateway

목표: 요청과 응답이 어느 출구를 통해 이동하는지 이해한다.

배울 내용:

- 목적지와 대상이 있는 Route Table.
- 기본 경로 `0.0.0.0/0`.
- Subnet과 Route Table association.
- VPC와 인터넷을 연결하는 Internet Gateway(IGW).
- IGW가 있어도 Route Table·Public IP·Security Group이 없으면 외부 접속이 되지 않는 이유.
- 나가는 경로와 돌아오는 응답 경로.

작은 활동:

1. `외부 ↔ IGW ↔ Route Table ↔ Subnet ↔ EC2` 양방향 흐름을 그린다.
2. IGW만 있는 경우, 기본 경로만 있는 경우, 공인 IP만 있는 경우에 무엇이 부족한지 예측한다.
3. `0.0.0.0/0 → IGW`가 어떤 뜻인지 설명한다.

통과 기준:

- Public Subnet을 이름이 아닌 실제 설정으로 판단한다.
- 경로 문제와 방화벽 문제를 구분한다.
- NAT Gateway가 이번 최소 구성에 기본으로 필요하지 않은 이유를 설명한다.

### 5단계. Security Group·SSH·운영체제 보안

목표: 네트워크 접근 제어와 서버 로그인 인증을 분리해 이해한다.

배울 내용:

- Security Group의 Inbound·Outbound·프로토콜·포트·소스.
- HTTP 80은 공개하고 SSH 22는 개인 IP로 제한하는 이유.
- SSH 키페어와 Linux 사용자 인증.
- 클라우드 Security Group, Linux 방화벽, 프로그램의 listening socket이 서로 다른 층이라는 점.
- 전체 포트 `0-65535` 공개가 위험한 이유.

작은 활동:

1. 외부 사용자가 필요한 포트와 관리자만 필요한 포트를 표로 나눈다.
2. 현재 IP `/32`와 `0.0.0.0/0`의 위험 차이를 설명한다.
3. SSH 개인 키를 문서·저장소에 넣지 않는 규칙을 확인한다.
4. `SG에서 허용됨`과 `Nginx가 실제로 80번 포트에서 대기함`이 다른 이유를 설명한다.

통과 기준:

- SSH 접속 실패를 네트워크 차단·키·Linux 사용자·서비스 문제로 나누어 조사할 수 있다.
- HTTP와 SSH의 공개 범위가 다른 이유를 설명한다.
- 모든 포트를 열어 문제를 우회하지 않는다.

### 6단계. 비용·생성·삭제 계획 승인

목표: 리소스를 만들기 전에 비용과 복구 책임을 이해한다.

배울 내용:

- 프리 티어·크레딧은 계정과 시점에 따라 달라질 수 있다.
- EC2 중지와 종료의 차이.
- EBS·Elastic IP처럼 서버가 꺼져도 남거나 과금될 수 있는 자원.
- NAT Gateway·ALB·RDS를 이번 필수 경로에 추가하지 않는 이유.
- 생성 순서와 삭제 순서가 서로 다른 이유.

작은 활동:

1. 각 예정 리소스에 예상 비용·삭제 방법·확인 방법을 기록한다.
2. `EC2 → EBS → EIP → IGW → Subnet/Route Table → VPC` 정리 흐름을 검토한다.
3. 실제 AWS 계정의 Billing·리전·프리 티어 정보를 확인할 필요를 목록화한다.
4. 사용자에게 생성 범위와 예상 위험을 설명하고 승인을 받기 전까지 멈춘다.

통과 기준:

- 무엇을 만들고 무엇을 만들지 않을지 설명한다.
- 실습 종료 후 남은 리소스를 확인하는 방법을 말할 수 있다.
- 비용 확인 전에는 생성 버튼이나 변경 명령을 실행하지 않는다.

### 7단계. 최소 VPC 구성 만들기

목표: 승인된 범위에서 네트워크의 최소 경로를 하나씩 만든다.

실행 순서:

1. VPC 1개.
2. Public Subnet 1개.
3. Internet Gateway 1개를 VPC에 연결.
4. Route Table에 `0.0.0.0/0 → IGW` 등록.
5. Route Table을 Public Subnet에 연결.
6. 각 리소스 ID·태그·연결 관계 기록.

각 변경 전 확인:

- 대상 리전이 서울인가?
- 생성할 리소스가 계획표에 있는가?
- 비용 가능성이 있는가?
- 실패 시 되돌리는 방법이 있는가?

통과 기준:

- 실제 Route Table과 Subnet association을 화면에서 확인한다.
- 구성도와 실제 리소스 ID가 일치한다.
- 아직 EC2를 만들지 않고도 네트워크 경로를 설명한다.

### 8단계. EC2·EBS·키페어·Security Group

목표: 가상 컴퓨터와 운영체제에 접속할 수 있는 최소 환경을 만든다.

실행 순서:

1. 승인된 micro급 인스턴스와 Ubuntu LTS 또는 Amazon Linux 계열을 선택한다.
2. Public Subnet과 EBS 용량을 확인한다.
3. SSH 키페어를 안전한 위치에 준비한다. 개인 키 값은 채팅·문서·저장소에 기록하지 않는다.
4. Security Group에서 HTTP 80은 `0.0.0.0/0`, SSH 22는 현재 개인 IP 또는 지정 대역만 허용한다.
5. EC2를 생성하고 Public IP·상태·연결된 Security Group을 기록한다.

통과 기준:

- EC2 실행 상태와 Nginx 실행 상태를 구분한다.
- Security Group의 실제 소스 범위를 확인한다.
- SSH 키의 위치와 보호 방법을 설명할 수 있다.

### 9단계. SSH 접속과 서버 내부 관찰

목표: 외부 네트워크와 서버 내부의 상태를 분리해 관찰한다.

작은 활동:

1. SSH로 EC2에 접속한다.
2. 운영체제 사용자와 현재 작업 위치를 확인한다.
3. 서버에서 외부 HTTPS 요청을 보내 아웃바운드 경로를 확인한다.
4. 서버의 실행 중 서비스·열린 포트·기본 로그를 관찰한다.
5. SSH 접속이 실패하면 IP·포트·Security Group·키·사용자 순서로 좁힌다.

통과 기준:

- SSH 성공이 HTTP 서비스 성공을 의미하지 않는다는 점을 설명한다.
- 서버 내부에서 실행한 `localhost` 요청과 노트북에서 실행한 요청의 목적지가 다르다는 점을 말한다.
- 비밀 키나 인증 정보를 출력·기록하지 않는다.

### 10단계. Nginx와 localhost 검증

목표: 웹 서버 프로그램이 파일을 HTTP로 제공하는 과정을 확인한다.

작은 활동:

1. Nginx를 설치하고 실행 상태를 확인한다.
2. 기본 문서 루트와 설정 파일 위치를 관찰한다.
3. 서버 내부에서 `curl http://localhost`를 실행한다.
4. HTTP 200 응답과 Nginx 로그를 확인한다.
5. 서비스가 중지되었거나 파일 경로가 틀렸을 때 어떤 증상이 생기는지 분류한다.

통과 기준:

- EC2가 켜진 것과 Nginx가 80번 포트에서 응답하는 것을 구분한다.
- `localhost` 200은 내부 검증이지 외부 접속 증명이 아니라는 점을 설명한다.
- Nginx 설정 변경은 한 번에 하나만 하고 변경 전후를 기록한다.

### 11단계. B1-1 사이트 배포

목표: 검증된 B1-1의 특정 소스 버전을 EC2의 정적 웹 루트에 배포한다.

전제:

- B1-1의 필수 기능과 로컬 검증이 끝나야 한다.
- 배포할 정확한 소스 버전과 파일 목록을 기록한다.
- GitHub Pages 배포와 EC2 배포는 서로 대체하지 않는다.

작은 활동:

1. B1-1의 HTML·CSS·JavaScript·이미지 파일 목록을 확인한다.
2. EC2의 Nginx 문서 루트에 파일을 배치한다.
3. 서버 내부에서 HTML 응답을 확인한다.
4. CSS·JS·이미지 요청이 올바른 상대 경로로 연결되는지 확인한다.
5. API 요청은 브라우저 Network에서 별도로 확인한다.

통과 기준:

- Nginx의 HTML 200만으로 전체 사이트가 정상이라고 판단하지 않는다.
- 파일 경로·권한·브라우저 자원 요청을 각각 확인한다.
- 배포 대상 버전을 README와 증빙에 명시한다.

### 12단계. 외부 접속 검증

목표: 서버 내부 성공과 외부 인터넷 성공을 별도로 증명한다.

공식 검증 방식 중 하나를 선택한다.

- **A:** 외부 브라우저에서 `http://<퍼블릭IP>` 접속.
- **B:** 외부에서 `GET http://<퍼블릭IP>/health` 호출 후 200과 고정 응답 확인.

학습 순서:

1. 외부 장치·네트워크에서 요청을 보낸다.
2. Public IP·80번 포트·Security Group·Route Table·IGW 경로를 확인한다.
3. 브라우저 화면과 Network 응답을 기록한다.
4. 내부 `localhost` 결과와 외부 결과를 나란히 비교한다.
5. 선택한 A/B 방식과 URL·검증 시점을 README에 적는다.

통과 기준:

- 외부 요청이 성공했다는 증거가 있다.
- 내부 성공만으로 외부 성공을 주장하지 않는다.
- 실제 주소를 공개 문서에 남길 때 개인정보·운영 보안 영향을 검토한다.

### 13단계. 트러블슈팅 한 건 완성

목표: 오류를 추측이 아니라 증거로 해결한다.

오류 분류 순서:

1. 주소·DNS 문제.
2. TCP 연결 거부·시간 초과.
3. Route Table·IGW·Public IP 문제.
4. Security Group·OS 방화벽 문제.
5. EC2 서비스·Nginx 프로세스 문제.
6. 문서 루트·파일 권한·상대 경로 문제.
7. HTML은 200이지만 CSS·JS·이미지·GitHub API가 실패하는 문제.
8. IAM 관리 권한 오류와 Linux 로그인 권한 오류.

보고서 형식:

```text
증상:
원인 가설:
검증 방법과 관찰 결과:
조치:
조치 후 결과:
재발 방지:
```

실제 오류가 없다면, 사용자의 별도 승인과 복구 계획 아래 HTTP 허용 규칙을 잠시 제거하는 등 통제된 실험을 선택할 수 있다. 이 경우 의도한 실험임을 명시하고 SSH 관리 경로를 잃지 않으며 즉시 원복한다. 실험을 실제 장애처럼 꾸미지 않는다.

통과 기준:

- 한 번에 여러 설정을 바꾸지 않는다.
- 증상과 원인을 구분한다.
- 변경 전후 증거와 복구 방법을 남긴다.

### 14단계. 제출물과 증빙 정리

목표: 다른 사람이 구성을 이해하고 재현할 수 있게 기록한다.

준비할 결과물:

- `docs/architecture.png` 또는 `docs/architecture.pdf`: 실제 VPC·Subnet·IGW·Route Table·EC2·Security Group과 요청 흐름.
- `README.md`: A/B 외부 검증 방식, URL 또는 IP, 검증 시점, 스크린샷 위치.
- `docs/troubleshooting.md` 또는 `.pdf`: 최소 한 건의 문제 해결 과정.
- `docs/cleanup-checklist.md`: 실제 생성 리소스와 종료·삭제 근거.

통과 기준:

- 다이어그램이 실제 콘솔 상태와 다르지 않다.
- 계획·예시·실제 결과가 문서에서 구분된다.
- 생성하지 않은 리소스는 `미생성`으로 기록한다.
- 개인 키·비밀번호·토큰을 문서에 넣지 않는다.

### 15단계. 리소스 정리와 비용 확인

목표: 실습 종료 후 불필요한 리소스와 비용을 남기지 않는다.

정리 전:

1. 외부 접속 증거와 로그를 먼저 저장한다.
2. 실제 생성 목록과 계획 목록을 비교한다.
3. 사용자의 삭제 승인을 확인한다.

정리 예시:

1. EC2를 `Terminated` 상태로 만든다.
2. 남은 EBS 볼륨과 스냅샷을 확인·삭제한다.
3. 할당한 Elastic IP가 있으면 해제·반환한다.
4. 추가 NAT Gateway·ALB·RDS가 있으면 삭제한다. 미생성은 미생성으로 기록한다.
5. Internet Gateway를 VPC에서 분리하고 삭제한다.
6. Subnet·사용자 Route Table을 정리한다.
7. VPC와 남은 의존 리소스를 확인한다.
8. Billing과 리소스 목록을 다시 확인한다.

통과 기준:

- Stop과 Terminate의 차이를 설명한다.
- 삭제된 것과 아직 남은 것을 리소스별로 증명한다.
- Billing 화면의 반영 지연 가능성을 알고 즉시 0원이라는 이유만으로 끝내지 않는다.

### 16단계. 선택 보너스와 독립 변형

목표: 필수 경로를 이해한 뒤에만 다음 기술로 확장한다.

선택 순서:

1. 필수 네트워크·EC2·Nginx·외부 접속·트러블슈팅·정리를 설명한다.
2. 원본 구성과 증빙을 보존한다.
3. HTTPS 또는 Docker 중 하나를 선택한다.
4. 추가 비용·포트·인증서·포트 매핑·삭제 대상을 먼저 검토한다.
5. 보너스 결과는 필수 결과와 분리해 기록한다.

독립 변형 문제:

- IGW는 연결됐지만 Route Table에 기본 경로가 없는 경우 조사 순서.
- Nginx는 `localhost` 200이지만 외부에서 시간 초과되는 경우 후보 세 가지.
- Security Group은 HTTP를 허용하지만 Nginx가 중지된 경우 확인 위치.
- EC2를 종료한 뒤 EBS·Elastic IP가 남았는지 확인하는 방법.
- IAM 권한 오류와 SSH·Linux 권한 오류를 구분하는 설명.

통과 기준:

- 새로운 오류의 계층을 스스로 좁힌다.
- 새 서비스를 추가하는 것보다 기존 원리를 재사용한다.
- 비용·보안·삭제 계획을 먼저 세운다.

## 4. B1-1과 B3-1 연결 일정

권장 순서는 다음과 같다.

1. B1-1의 HTML·CSS·JavaScript 핵심 단계를 순서대로 공부한다.
2. B1-1이 완성되기 전에도 B3-1의 1~6단계 개념·비용·보안은 문서와 그림으로 공부한다.
3. B1-1의 필수 기능과 로컬 검증을 끝낸다.
4. 배포할 B1-1 소스 버전을 고정한다.
5. 사용자 승인 후 B3-1의 실제 AWS 리소스를 작은 단위로 만든다.
6. EC2 내부 Nginx를 먼저 검증한다.
7. B1-1 정적 파일을 배포하고 외부 접속을 검증한다.
8. 증빙을 저장하고 리소스를 정리한다.
9. GitHub Pages는 그대로 유지하며 EC2 배포와 별도로 확인한다.

B1-1 구현과 B3-1 실제 인프라 변경을 같은 세션에 동시에 진행하지 않는다. 개념 학습은 병행할 수 있지만, 상태 변경의 원인은 한 번에 하나만 남긴다.

## 5. 학습 세션 운영 단위

한 번의 세션은 다음 범위로 제한한다.

```text
10분: 이전 단계 회상
15분: 네트워크·보안 개념 하나 설명
20분: 구성도·읽기 확인 또는 승인된 작은 변경
15분: 내부·외부·로그 증거 확인
10분: 장애 가설과 회고
```

비용과 외부 공개가 걸린 단계는 세션 시간이 끝났다고 자동 실행하지 않는다. 승인·복구·정리 조건이 확인되지 않으면 다음 세션으로 미룬다.

## 6. 이 계획의 검토 질문

실제 AWS 작업 전에 다음을 검토한다.

- B1-1 완료를 B3-1 시작의 필수 전제로 둘 것인가, 개념 학습만 먼저 병행할 것인가?
- AWS 리소스 생성 전에 계정·리전·프리 티어·비용 정보를 어떤 방식으로 확인할 것인가?
- 콘솔과 CLI 중 어느 방법으로 실습할 것인가? 그 선택으로 무엇을 더 배우는가?
- 외부 검증 방식은 A(브라우저)와 B(`/health`) 중 무엇을 선택할 것인가?
- 실제 오류가 없을 때 통제 실험을 할 것인가, 관찰 가능한 가상 시나리오만 문서화할 것인가?
- 삭제 승인과 증빙 저장 시점을 어떻게 정할 것인가?
- HTTPS와 Docker를 이번 과제에서 생략할지, 핵심 완료 후 하나만 선택할지?
- 각 단계의 통과 기준이 실제 화면·로그·설명으로 확인 가능한가?

이 계획에 대한 검토가 끝나고 생성 범위·비용·배포 시점을 승인한 뒤에만 0단계부터 실제 학습을 시작한다.
