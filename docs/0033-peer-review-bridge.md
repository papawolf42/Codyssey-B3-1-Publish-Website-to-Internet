> **2026-10-19 후속 안내:** 아래의 구축·동작 사실은 삭제 전 검증 당시 기록이다. 주요 실습 자원 정리는 후속 완료했으며 1-5에 반영했다. 다른 절의 향후 정리 절차는 당시 계획·일반 원리로 읽는다. 비용 예상 0.00을 무료 범위 준수·확정 청구 0으로 단정하지 않는다.

## 항목 1. 핵심 인프라 구축 및 기본 동작 검증

### 1-1. VPC, Public Subnet, Internet Gateway, Route Table(0.0.0.0/0 → IGW)이 구성되어 있는가?
* **현재 사실 (검증 완료)**:
  * 서울 리전(`ap-northeast-2`)에 전용 실습 VPC인 `b3-1-vpc` (`vpc-062ac6fd0606192ab`, `10.0.0.0/16`)를 직접 생성했습니다.
  * 단일 가용 영역 `ap-northeast-2a` 안에 퍼블릭 서브넷 `b3-1-public-subnet` (`subnet-08efa9b32e083838b`, `10.0.1.0/24`)을 생성하여 배치했습니다.
  * 인터넷 관문인 인터넷 게이트웨이 `b3-1-igw` (`igw-0453ef9ebcd131aad`)를 생성하여 해당 VPC에 연결(Attach)했습니다.
  * 서브넷에 연결된 라우팅 테이블 `rtb-0f08329ebc84d7fb5`에 VPC 내부 통신을 위한 기본 `10.0.0.0/16 -> local` 경로와 함께, 외부 인터넷으로 향하는 기본 경로인 `0.0.0.0/0 -> igw-0453ef9ebcd131aad` 규칙을 등록했습니다.
* **일반 원리**:
  * VPC는 논리적으로 완전히 격리된 가상 사설망입니다. 서브넷이 외부 인터넷과 양방향 통신을 하려면 VPC에 부착된 IGW가 존재해야 하며, 서브넷 라우팅 테이블에 알 수 없는 모든 외부 목적지(`0.0.0.0/0`)를 IGW로 넘겨주는 규칙이 반드시 정의되어야 '퍼블릭 서브넷'으로서 기능합니다.
* **향후 정리 계획**:
  * 실습 종료 시 EC2·볼륨·IP·네트워크 인터페이스 등 의존 자원을 먼저 확인·정리하고, IGW 디태치(Detach) 및 삭제, 서브넷·사용자 생성 네트워크 자원·VPC를 의존 관계에 맞춰 정리할 예정입니다. 기본 라우팅 테이블은 서브넷에 암시적으로 적용된 상태이므로 별도 명시적 연결 해제를 수행했다고 주장하지 않습니다.

### 1-2. EC2에 SSH로 접속 가능하며, 웹 서버가 실행 중인가?
* **현재 사실 (검증 완료)**:
  * 실습 서브넷 안에 Amazon Linux 2023 기반의 t3.micro 인스턴스 `b3-1-web` (`i-05d34639a30bbfb6a`) 1대를 정상 기동했습니다.
  * 로컬 환경(ttyd 웹 터미널)에서 Windows OpenSSH 클라이언트와 키 페어(`b3-1-key.pem`)를 사용하여 `ec2-user@13.125.99.141`로 SSH 원격 접속에 성공했습니다.
  * 원격 셸에서 Nginx 패키지를 설치한 후 `sudo systemctl enable --now nginx`를 실행하여 서비스 실행과 부팅 시 자동 시작 등록을 모두 마쳤습니다.
  * 인스턴스 내부 셸에서 `curl -I http://localhost`를 호출하여 `HTTP/1.1 200 OK` (Server: nginx) 응답을 직접 확인했습니다.
* **일반 원리**:
  * `systemctl enable --now`는 서비스를 현재 백그라운드 데몬으로 즉시 기동(`start`)함과 동시에, 부팅 시 해당 서비스가 자동으로 시작되도록 systemd target 의존 관계(`multi-user.target.wants`)에 심볼릭 링크를 등록하는 명령어입니다.
  * 다만 자동 시작 설정이 등록되었다고 해서 부팅 후 무조건적인 정상 실행을 보장하는 것은 아니며, 부팅 시점의 의존 환경이나 설정 파일의 결함 등에 따라 기동 실패가 발생할 수도 있습니다.

### 1-3. 보안 그룹 인바운드가 “필요 포트만” 허용하며, SSH(22)가 특정 IP로 제한되어 있는가?
* **현재 사실 (검증 완료)**:
  * 최종 저장된 인스턴스 보안 그룹 `b3-1-web-sg` (`sg-0c4336bb1e71eea36`)의 인바운드 규칙은 정확히 아래 2개만 존재합니다.
    1. **HTTP (TCP 80)**: 소스 `0.0.0.0/0` (전 세계 웹 사용자의 정상 접속 허용)
    2. **SSH (TCP 22)**: 소스 `학습자 본인의 공인 IPv4 /32` (단 1개의 IP만 허용하는 호스트 마스크)
  * 브라우저 기반 EC2 Instance Connect 테스트를 위해 AWS 서비스 IP 대역(`13.209.1.56/29`) 추가를 검토 및 시도했으나, 최종적으로는 이를 저장하지 않고 취소하여 **본인 공인 IP /32 단일 규칙**만 엄격하게 유지했습니다. 전체 포트(0-65535) 개방이나 SSH 0.0.0.0/0 규칙은 일절 생성하지 않았습니다.
* **일반 원리**:
  * 보안 그룹은 인바운드 규칙에 명시되지 않은 모든 트래픽을 기본 거부(Default Deny)합니다. SSH와 같은 관리자 포트를 `0.0.0.0/0`으로 열어두면 자동화된 접속 시도와 공격에 노출되는 범위가 커집니다. 이번 실습에서는 현재 관리자 공인 IP(`/32`)만 허용했습니다. IP 제한이 SSH 키 인증을 대신하지 않으며, 다른 환경에서는 승인된 지정 대역·VPN·Session Manager 등도 검토할 수 있습니다.

### 1-4. 외부 접속이 아래 방식 중 1개로 검증되는가?
* **선택한 검증 방식**: **(A) 브라우저 `http://<퍼블릭IP>` 접속**
* **현재 사실 (검증 완료)**:
  * 외부 PC의 웹 브라우저 주소창에 EC2의 공인 IP인 `http://13.125.99.141/`를 직접 입력하여 접속했습니다.
  * 브라우저 화면에 Nginx의 공식 기본 웰컴 페이지(**Welcome to nginx!**)가 정상적으로 렌더링되는 것을 확인하고 증빙 캡처(`0193-nginx-external-http-success.png`)를 확보했습니다.
  * 추가 검증으로 EC2 내부 셸에서 외부 인터넷으로 `curl -I --max-time 15 https://example.com`을 호출하여 `HTTP/2 200` 응답을 확인, 인스턴스의 아웃바운드 인터넷 통신도 정상임을 입증했습니다.
* **일반 원리**:
  * 외부 브라우저 접속 검증(A)은 외부 클라이언트 → 공용 인터넷 → VPC IGW → 서브넷 라우팅 → 보안 그룹(80) → EC2 OS의 Nginx 프로세스로 이어지는 인바운드 전체 네트워크 경로가 온전함을 증명합니다.

### 1-5. 리소스 정리 체크리스트에서 최소 5종(EC2/EBS/EIP/IGW/VPC) 정리 완료를 확인할 수 있는가?
* **후속 사실: 주요 실습 자원 정리 확인**
  * EC2 Terminated와 서울 EBS·EIP·ENI 없음, 실습 SG·Subnet·IGW·VPC 및 해당 기본 자원 부재를 확인했습니다.
  * [정리 체크리스트](cleanup-checklist.md)에 ID·확인일·완료/해당 없음·캡처를 남겼습니다. EIP는 전체 목록에 없어 Release 해당 없음입니다.
  * 기본 VPC와 무관한 자원은 보존했습니다. DNS A 레코드는 사용자 선택으로 유지하며 원래 IP를 현재 서비스 주소로 신뢰하지 않습니다.
* **자체 답변 준비 상태**: 동작·주요 자원 정리 증빙은 있고, 학습자 자기 설명·무료 범위·최종 청구 판정은 별도입니다.

## 항목 2. 아키텍처 설명 및 설계 근거

### 2-1. “외부 → IGW → Subnet → EC2”로 이어지는 네트워크 흐름을 다이어그램 기준으로 설명할 수 있는가?
* **다이어그램 상태 명시**:
  * 초안 작성 이후 Aside가 공식 제출 규격의 [docs/architecture.png](architecture.png)와 [Excalidraw 편집 원본](architecture.excalidraw)을 작성했습니다. 아래 ASCII 도식은 설명용 보조 자료이며 제출용 PNG와 대조해 설명을 연습합니다. 그림 작성이 학습자의 설명 능력 검증을 대신하지는 않습니다.

```text
[ 외부 클라이언트 브라우저 ]
          |
          | 1. HTTP 요청 (공인 IP 대상, 포트 80)
          v
[ Internet Gateway (b3-1-igw) ] (VPC 경계의 인터넷 출입 관문)
          |
          v (VPC 진입)
+--[ VPC: b3-1-vpc (10.0.0.0/16) ]----------------------------------------+
|                                                                          |
|   +--[ Public Subnet: 10.0.1.0/24 (b3-1-public-subnet) ]---------------+  |
|   |  - 서브넷 라우팅 규칙: 10.0.0.0/16 -> local, 0.0.0.0/0 -> IGW        |  |
|   |                                                                    |  |
|   |  [ 서브넷 경계: Network ACL ] (인바운드/아웃바운드 검사)            |  |
|   |         |                                                          |  |
|   |         v                                                          |  |
|   |   +--[ Network Interface (ENI) ]-------------------------------+   |  |
|   |   |  - 인스턴스 보안 그룹: b3-1-web-sg (Port 80 Inbound 허용)    |   |  |
|   |   |         |                                                  |   |  |
|   |   |         v                                                  |   |  |
|   |   |     [ EC2 Instance: b3-1-web ]                             |   |  |
|   |   |     - 사설 IP: 10.0.1.200 (내부 주소)                      |   |  |
|   |   |     - Nginx 웹 서버 (Port 80 수신 대기 및 응답 생성)       |   |  |
|   |   +------------------------------------------------------------+   |  |
|   +--------------------------------------------------------------------+  |
+--------------------------------------------------------------------------+
```

* **상세 패킷 흐름 해설**:
  1. 외부 클라이언트가 웹 브라우저를 통해 인스턴스에 부여된 퍼블릭 IPv4 주소(`13.125.99.141:80`)로 HTTP 연결을 요청합니다.
  2. VPC 경계에 부착된 **Internet Gateway(IGW)**가 이 패킷을 수신합니다. 클라우드 인프라의 주소 변환 원리에 따라, IGW는 패킷의 공인 IP를 VPC 내부의 해당 ENI 사설 IPv4 주소(`10.0.1.200`)로 1:1 NAT 매핑하여 VPC 내부로 트래픽을 전달합니다.
  3. 패킷이 서브넷으로 진입할 때 **서브넷 라우팅 테이블 규칙**(`10.0.0.0/16 -> local`)에 따라 목적지 주소를 식별하고, **서브넷 경계의 Network ACL**을 통과합니다.\
     *(주의: 일반적인 VPC 생성 시 모든 트래픽을 통과시키는 기본 ACL이 자동 연결되지만, 현재 실습에서 ACL 세부 규칙을 직접 조회하여 검증한 것은 아니므로 실제 규칙 내용은 실측이 아닌 미확인 상태로 구분합니다.)*
  4. 인스턴스의 가상 네트워크 카드(ENI) 앞단에서 **보안 그룹(Security Group)**이 인바운드 규칙을 검사합니다. 최종 확인된 규칙 중 HTTP TCP 80 (`0.0.0.0/0`) 허용 규칙과 일치하므로 패킷이 EC2 OS 내부로 전달됩니다.
  5. EC2 내부 Linux OS에서 실행 중인 Nginx 웹 서버 데몬이 요청을 받아 기본 HTML 응답을 생성합니다.
  6. 반환되는 응답 트래픽은 보안 그룹의 **Stateful(상태 추적)** 특성 덕분에 별도의 아웃바운드 검사 없이 통과되며, 서브넷에 적용된 라우팅 규칙(`0.0.0.0/0 -> IGW`)을 따라 IGW를 거쳐 원래 외부 클라이언트로 회신됩니다.

### 2-2. 보안 그룹 규칙을 어떤 기준으로 최소화했는지(허용/미허용 포트) 설명할 수 있는가?
* **최소화 기준 및 포트 선정 근거**:
  * **원칙**: "업무상 꼭 필요한 포트만 열고, 나머지는 모두 닫는다(Default Deny)."
  * **허용 포트**:
    * **HTTP (80)**: 웹 사이트를 전 세계 불특정 다수에게 공개하는 것이 미션 목표이므로 소스를 `0.0.0.0/0`으로 허용했습니다.
    * **SSH (22)**: 서버의 원격 유지보수를 위해 반드시 필요하지만 외부에 노출되면 위험하므로, `0.0.0.0/0`이 아닌 현재 접속 중인 학습자 개인 공인 IP 단 1개(`/32`)만 지정했습니다.
  * **미허용 포트**:
    * 0~65535 전체 개방 규칙은 보안상 치명적이므로 절대 생성하지 않았습니다.
    * 데이터베이스 포트(3306, 5432)나 내부 통신용 포트는 이번 단일 웹 서버 과제에 불필요하므로 일절 추가하지 않았습니다.
    * 브라우저 Instance Connect 서비스용 CIDR(`13.209.1.56/29`)도 검토했으나, 최종적으로는 공격 표면(Attack Surface)을 최소화하기 위해 개인 IP만 남기고 저장하지 않았습니다.

### 2-3. 외부 접속 검증을 A 또는 B 중 무엇으로 선택했고, 그 선택을 위해 무엇을 어떻게 구성했는지 설명할 수 있는가?
* **선택**: **방식 (A) 브라우저 접속 (`http://<퍼블릭IP>`)** 선택.
* **구성 내용 및 절차**:
  * Nginx 웹 서버 설치 및 기동: Amazon Linux 2023에 Nginx를 설치하고 `systemctl enable --now nginx`로 80번 포트를 리스닝하도록 구성했습니다.
  * 네트워크 경로 확보: 서브넷 라우팅 테이블에 IGW 경로(`0.0.0.0/0 -> IGW`)를 연동하고, EC2 생성 시 '퍼블릭 IP 자동 할당'을 활성화하여 외부 라우팅 가능한 공인 IPv4(`13.125.99.141`)를 부여받았습니다.
  * 인바운드 방화벽 개방: 보안 그룹 `b3-1-web-sg`에 HTTP TCP 80 (`0.0.0.0/0`) 인바운드 규칙을 연결했습니다.
  * 결과적으로 브라우저를 통해 직관적으로 HTML 페이지가 렌더링되는 시각적 증빙을 README와 캡처 파일에 확보했습니다.

### 2-4. 실습 리소스를 추적/정리하기 위해 어떤 기준(태그, 이름 규칙, 체크리스트)을 사용했는지 설명할 수 있는가?
* **이름 명명 규칙(Naming Convention)**:
  * 콘솔 화면 및 검증 과정에서 확인된 주요 실습 자원 예시(`b3-1-vpc`, `b3-1-public-subnet`, `b3-1-igw`, `b3-1-web-sg`, `b3-1-web`, `b3-1-key`)처럼 일관되게 `b3-1-` 접두사를 적용하여 기본 리소스와 구분했습니다.
* **태그(Tagging) 기준**:
  * IAM 정책(`B3ResourceLabels`)의 조건절(`aws:TagKeys`)에서 `Name`과 `Project` 태그 생성을 허용하도록 정의되어 있다는 사실을 확인했습니다. 다만 이것은 정책상 허용된 태그 키 목록일 뿐이며, 이번 실습에서 생성된 모든 리소스에 실제로 두 태그가 빠짐없이 부여되었는지 전수 검증한 것은 아닙니다.
* **체크리스트 기반 추적**:
  * 과금 위험 리소스(EC2 인스턴스, 루트 gp3 EBS 볼륨, 퍼블릭 IPv4 주소, IGW, VPC)를 식별해 두었으며, 이후 `docs/cleanup-checklist.md`에 순차 정리의 실제 결과와 캡처를 남겼습니다.
* **자체 답변 준비 상태**: **[설명 초안 있음 / 후속 작업으로 공식 PNG·편집 원본 작성 완료 / 학습자 설명 연습 필요]**.

## 항목 3. 핵심 원리 및 트러블슈팅 분석

### 3-1. Public Subnet Route Table의 기본 경로(0.0.0.0/0 → IGW)가 필요한 이유를 설명할 수 있는가?
* **네트워크 라우팅 원리**:
  * VPC를 생성하면 VPC 내부 대역(예: `10.0.0.0/16`)에 대한 `local` 라우트만 자동으로 생깁니다. 이 상태에서는 VPC 내부 인스턴스끼리는 통신할 수 있지만, 외부 인터넷 주소(예: 패키지 저장소, 클라이언트 PC 등)로 패킷을 어디로 보내야 할지 라우터가 알지 못합니다.
  * 따라서 "내부 대역(`10.0.0.0/16`) 외에 알 수 없는 모든 IP(`0.0.0.0/0`)"에 대해 **인터넷 게이트웨이(IGW)로 트래픽을 전달하라**는 기본 경로(Default Route)를 등록해야 합니다.
  * 라우터는 **최장 일치 원칙(Longest Prefix Match)**에 따라 목적지 주소와 가장 길게 일치하는 규칙을 우선하므로, 내부 통신은 `/16`인 `local`을 먼저 타고, 인터넷으로 나가는 트래픽만 `/0`인 IGW를 타게 됩니다.

### 3-2. Security Group과 IAM의 책임 범위 차이를 설명하고, “최소 권한”이 왜 필요한지 설명할 수 있는가?
* **책임 범위 차이**:
  * **보안 그룹 (Security Group)**: **네트워크 전송 계층(L3/L4)의 패킷 필터**입니다. 가상 네트워크 인터페이스(ENI) 레벨에서 동작하며, IP 주소와 포트 번호를 기준으로 실제 네트워크 통신 패킷의 유입과 유출을 차단하거나 허용합니다. (예: "22번 포트로 들어오는 SSH 패킷 허용")
  * **IAM (Identity and Access Management)**: **AWS 제어 평면(Control Plane)의 API 접근 통제 시스템**입니다. 사용자나 역할(신원)이 AWS 콘솔이나 CLI에서 수행하는 관리 작업(API 호출)을 통제합니다. (예: "EC2 인스턴스를 시작하거나 보안 그룹을 수정할 수 있는 권한")
* **최소 권한(Least Privilege)이 필요한 이유**:
  * 불필요하게 넓은 권한(예: `AdministratorAccess`)이나 포트(예: 전체 개방)를 열어두면, 단 한 번의 자격 증명 유출이나 서버 침해 사고로 인해 계정 전체가 삭제되거나 대규모 가상화폐 채굴 인스턴스가 생성되어 감당할 수 없는 과금 폭탄이 발생할 수 있습니다. 필요한 작업과 최소 출발지만 허용하는 것이 클라우드 보안의 제1원칙입니다.

### 3-3. SSH(22) 또는 DB 포트를 0.0.0.0/0 로 열면 안 되는 이유와 대안을 설명할 수 있는가?
* **0.0.0.0/0 개방이 위험한 이유**:
  * 공용 인터넷에는 전 세계의 취약한 서버를 탐색하는 자동화된 포트 스캐너와 봇넷이 상시 활동하고 있습니다. 22번이나 3306번 포트를 전체 공개하면 수만 건의 무차별 대입 공격(SSH Brute Force), 사전 공격(Dictionary Attack), 제로데이 취약점 익스플로잇의 직접적인 타깃이 됩니다.
* **현업 및 엔지니어링 대안**:
  1. **소스 IP 제한**: 현재 실습처럼 관리자 개인 IP나 사내 고정 IP(`/32`)만 허용.
  2. **AWS Systems Manager (SSM) Session Manager**: 인바운드 22번 포트를 완전히 닫아두고, 아웃바운드 HTTPS 통신 기반의 AWS SSM 에이전트를 통해 안전하게 브라우저/CLI 셸 접속.
  3. **배스천 호스트(Bastion Host) / VPN**: 사설 서브넷에 위치시키고, 인증된 사내 VPN이나 전용 점프 서버를 통해서만 접근하도록 다계층 방어 구축.

### 3-4. 트러블슈팅에서 “가설 → 검증” 순서를 유지한 이유와, 로그/근거를 어떻게 활용했는지 설명할 수 있는가?
* **가설 → 검증 순서를 유지한 이유**:
  * 문제가 발생했을 때 체계적인 원인 규명 없이 짐작만으로 보안 그룹을 전체 개방하거나 IAM 관리자 권한을 부여하면, 운 좋게 해결되더라도 정확한 원인을 알 수 없고 시스템의 보안 통제선이 완전히 무너집니다.
  * 반드시 **"증상 관찰 → 원인 가설 수립 → 읽기 전용 검증 → 최소 조치 → 결과 확인 → 재발 방지"**의 6단계를 지켜야 부작용 없이 근본 원인을 해결할 수 있습니다.
* **실제 실습에서의 로그/근거 활용 사례**:
  * **TS-001 (서울 EC2 조회 403 거부)**: 인스턴스가 없어서 안 뜨는 것으로 넘겨짚지 않고, 콘솔의 `explicit deny in a service control policy (p-l9spe88l)` 오류 문구를 확인하여 상위 조직 SCP가 서울 리전을 차단하고 있음을 명문화된 근거로 입증했습니다.
  * **TS-007 (브라우저 SSH 연결 실패 및 IAM 점진적 수정)**:
    * 단순 네트워크 장애로 단정하지 않고, `SendSSHPublicKey 실패` 에러 문구와 로컬 IAM 정책 JSON을 대조하여 API 권한 누락을 확인했습니다.
    * 이후 관리자 권한을 부여하지 않고 단계별로 필요한 권한을 보완했습니다:
      * **v1 → v2 변경**: 특정 실습 인스턴스 ID와 `ec2-user`, 서울 리전으로 한정한 `ec2-instance-connect:SendSSHPublicKey`와, 콘솔 주소 조회 경고 해소를 위한 `ec2:DescribeAddresses` **두 Action**을 추가.
      * **v2 → v3 변경**: 보안 그룹 편집 UI에서 발생한 규칙 조회 오류를 해소하기 위해 `ec2:DescribeSecurityGroupRules` **한 Action**을 추가.
    * v2 적용 후 브라우저 SSH에서 'SSH 연결을 설정하지 못했습니다' 오류를 확인했습니다. 이후 v3는 보안 그룹 규칙 조회를 복구한 변경이며, v3 적용 뒤 브라우저 SSH를 다시 시험한 결과는 기록하지 않았습니다. 따라서 브라우저 SSH 연결 성공은 검증되지 않았습니다.
    * 이에 따라 과제 명세의 SSH 접속 검증은 이미 성공한 **로컬 ttyd 및 Windows OpenSSH 환경을 최종 접속 경로로 채택**했습니다. (IAM v3에 추가된 권한들은 정책 롤백을 수행하지 않고 그대로 유지되어 있습니다.)
* **자체 답변 준비 상태**: **[개념 이해 및 트러블슈팅 답변 준비 완료]**.

## 항목 4. 심화 운영 및 장애 대응

### 4-1. 외부 접속이 안 될 때, 어떤 순서로(라우팅 → SG → 퍼블릭 IP/DNS → 서버 프로세스/로그) 점검하는지 설명할 수 있는가?
외부에서 웹 서비스 접속이 실패할 경우, 아래와 같이 바깥 인프라부터 안쪽 애플리케이션까지 계층별로 점검합니다.

1. **네트워크 라우팅 계층 (Route Table & IGW)**:
   * 서브넷 라우팅 테이블에 `0.0.0.0/0 -> igw-xxx` 기본 경로가 존재하는가?
   * 인터넷 게이트웨이가 VPC에 정상적으로 `Attached` 상태인가?
2. **방화벽 계층 (Security Group & Network ACL)**:
   * EC2 인스턴스 보안 그룹 인바운드에 TCP 80 포트가 `0.0.0.0/0`으로 열려 있는가?
   * 서브넷의 Network ACL 인바운드/아웃바운드 규칙에서 트래픽이 거부(Deny)되지 않았는가?
3. **주소 및 인스턴스 상태 계층 (Public IP & Status Check)**:
   * 인스턴스에 퍼블릭 IPv4가 정상 할당되어 있는가? (중지 후 재시작 시 IP가 변경되었을 수 있음)
   * EC2 콘솔에서 해당 인스턴스에 제공되는 모든 상태 검사가 정상 통과(Passed) 상태인지 확인합니다. 이 실습의 기록에는 3/3 통과가 있으며, 이를 브라우저 SSH 접속 성공과 혼동하지 않습니다.
4. **서버 내부 데몬 및 OS 로그 계층 (Process & Logs)**:
   * SSH로 인스턴스에 접속하여 Nginx 데몬이 실제로 실행 중인지 확인 (`systemctl status nginx`).
   * 내부에서 포트를 정상적으로 리스닝하고 있는지 확인 (`sudo ss -tulpn | grep 80` 또는 `curl -I http://localhost`).
   * 웹 서버 에러 로그 확인 (`/var/log/nginx/error.log`) 및 리눅스 시스템 로그 확인 (`journalctl -u nginx`).

### 4-2. IAM 권한이 부족해 작업이 실패했다면, “권한을 무작정 올리지 않고” 어떤 방식으로 필요한 최소 범위를 찾아갔는지 설명할 수 있는가?
* **최소 범위 도출 접근법**:
  1. **오류 메시지에서 정확한 API 작업명 추출**: AWS 에러 메시지(예: `User is not authorized to perform: ec2:DescribeSecurityGroupRules`)에서 거부된 정확한 `Action` 이름을 확인합니다.
  2. **공식 문서 기반 리소스 제약 확인**: 해당 Action이 특정 리소스 수준 권한을 지원하는지 AWS 문서를 확인합니다. 예를 들어 `ec2-instance-connect:SendSSHPublicKey`의 경우, 모든 서버(`*`)가 아니라 실습 서버의 ARN(`arn:aws:ec2:...:instance/i-05d34639a30bbfb6a`)으로만 한정합니다.
  3. **조건절(Condition) 적용**: `aws:RequestedRegion: ap-northeast-2`로 리전을 서울로 묶고, `ec2:osuser: ec2-user`로 리눅스 계정까지 제한하여 다른 용도로 도용되지 않도록 제약을 겁니다.
  4. **버전 관리 및 점진적 배포**: IAM 정책의 새 버전을 생성하여 기본값으로 적용한 뒤 실제 작업이 해결되는지 확인합니다.

### 4-3. 트래픽이 늘어 “인스턴스를 2대로 늘려야” 한다면, 현재 구조에서 무엇이 병목이며 어떤 구성요소(ALB 등)를 추가할지 설명할 수 있는가?
* **현재 단일 인스턴스 아키텍처의 한계**:
  * **단일 장애점 (SPOF, Single Point of Failure)**: EC2 1대에 웹 서버가 종속되어 있어, 인스턴스 장애나 프로세스 중단 시 서비스 전체가 영향을 받습니다.
  * **트래픽 부하 집중**: 단일 인스턴스의 CPU/메모리 및 네트워크 처리 한계를 넘어서는 트래픽이 몰리면 응답 지연이나 서비스 불능이 발생할 수 있습니다.
  * **직접 접근 구조**: 클라이언트가 인스턴스의 퍼블릭 IP로 직접 접속하므로, 보안 그룹으로 포트(80)를 제한하더라도 인터넷에서 허용된 서비스 포트로 직접 접근이 가능한 구조입니다.
* **향후 확장 아키텍처 (개선 계획)**:
  * **Application Load Balancer (ALB) 도입**: 외부에 단일 진입점(DNS)을 제공하고, 뒤단의 여러 EC2 인스턴스로 트래픽을 부하 분산(Round Robin 등)하며, 주기적인 헬스 체크로 비정상 인스턴스를 트래픽에서 자동 제외합니다.
  * **다중 가용 영역(Multi-AZ) 서브넷 확장**: 서브넷을 `ap-northeast-2a` 외에 `ap-northeast-2c` 등에 추가 생성하여 데이터센터 수준의 장애에 대비합니다.
  * **서버의 프라이빗 서브넷 격리**: EC2 인스턴스를 공인 IP가 없는 프라이빗 서브넷으로 이동시키고, 오직 ALB의 보안 그룹에서 들어오는 80 포트 트래픽만 허용하여 백엔드 인스턴스를 안전하게 보호합니다.
  * **Auto Scaling Group (ASG) 연동**: 트래픽 부하 지표(CPU 사용률 등)에 따라 인스턴스가 2대 이상으로 자동 증설·축소되도록 구성합니다.
  * *(주의: 위 내용은 향후 확장 설계에 대한 설명이며, 현재 실습 인프라에는 ALB나 다중 인스턴스가 구성되어 있지 않습니다.)*

### 4-4. Billing에 예상치 못한 비용이 찍혔다면, 어떤 리소스부터 의심하고 어떻게 추적/정리할지 설명할 수 있는가?
* **가장 먼저 의심해야 할 5대 리소스**:
  1. **실행 중인 EC2 인스턴스**: 실습 후 종료(Terminate)하지 않고 방치하여 시간당 인스턴스 요금이 지속 발생.
  2. **탄력적 IP (Elastic IP)**:
     * 사용 중이거나 유휴인 EIP 모두 공인 IPv4 비용 확인 대상입니다. 유휴 상태에만 별도 페널티가 붙는다고 가정하지 않고 실제 사용 유형·요금·혜택을 Billing에서 확인합니다. 아래 5번의 퍼블릭 IPv4와 동일 비용을 두 번 합산하지 않도록 구분합니다.
  3. **남아 있는 EBS 볼륨**: 인스턴스를 종료할 때 '종료 시 볼륨 삭제' 옵션이 꺼져 있었거나 별도로 생성해 방치된 고아 볼륨(GB-월당 스토리지 요금).
  4. **NAT Gateway 및 유료 엔드포인트**: VPC 실습 중 실수로 생성하여 시간당 요금 및 데이터 처리 요금이 지속 누적.
  5. **퍼블릭 IPv4 주소 요금**: AWS의 정책 변경으로 인스턴스에 할당된 모든 퍼블릭 IPv4 주소(자동 할당 IP 및 탄력적 IP)에 부과되는 시간당 요금 (2번 항목과 동일 범주의 IPv4 비용으로 집계될 수 있음).
* **추적 및 분석 방법**:
  * AWS 콘솔의 **AWS Cost Explorer**를 열어 날짜별, 서비스별(Usage Type별), 리전별 비용 청구 추이를 확인합니다.
  * **Billing 대시보드(청구서)**에서 서울 리전(`ap-northeast-2`)의 세부 항목(EC2-Instances, EC2-EBS 등)을 펼쳐 어떤 리소스 타입에서 비용이 올라가고 있는지 특정합니다.
* **조치 및 정리 절차 주의사항**:
  * 리소스를 무작정 삭제하기 전에, **해당 리소스가 본인 소유의 실습용 리소스가 맞는지, 다른 중요한 용도로 사용 중인 것은 아닌지 반드시 확인**한 뒤 삭제해야 합니다.
  * 리소스를 모두 종료·삭제했다고 해서 다음 날 청구서가 즉시 $0.00으로 표시되는 것은 아닙니다. AWS Billing 시스템의 **청구 반영 지연**이 존재하며, 실습 당월에 **이미 발생한 누적 사용 요금**은 사라지지 않기 때문입니다.
  * 따라서 청구 금액이 $0.00이 되는 것을 완료 판정 기준으로 삼지 않고, 콘솔의 각 리소스 목록(EC2, 볼륨, EIP, VPC 등)에서 **본인 실습의 정리 대상 자원이 삭제되었고 과금 가능 잔여 자원이 없는지 직접 확인하는 것**을 1차 완료 판정으로 삼고, 이후 Cost Explorer의 일별 사용량 추세를 모니터링해야 합니다.
* **자체 답변 준비 상태**: **[심화 운영 및 장애 대응 답변 준비 완료]**.
