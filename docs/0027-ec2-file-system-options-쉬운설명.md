# EC2 파일 시스템 선택지 4개 쉬운 설명

[EC2 실제 진행 기록](0025-ec2-deployment-walkthrough.md) · [SSH·키 페어](0026-ssh-keypair-openssh-putty-쉬운설명.md) · [과제 명세](0051-requirements-and-review-reference.md)

## 1. 먼저 결론: 이번 과제는 ‘없음’이 맞다

화면의 네 선택지는 **S3 파일 - 신규 / EFS / FSx / 없음**이다. 현재 없음이 선택되어 있다.

**없음 = 저장 공간이 없음이 아니라 ‘추가 공유 파일 시스템을 연결하지 않음’이다.** 바로 위에 있는 gp3 8 GiB 루트 EBS 볼륨은 그대로 사용한다. Amazon Linux, Nginx, 기본 웹 페이지·설정·로그는 그 디스크에 저장할 수 있다.

서버 한 대로 웹 응답을 검증하는 이번 과제에는 별도 공유 스토리지가 필수 요구사항이 아니다. S3 Files·EFS·FSx를 추가하면 비용, 네트워크, IAM 권한, 마운트와 정리 대상을 더 관리해야 한다. 지금 선택지를 배우는 것과 실제 서비스를 생성하는 것은 별개이며 학습 설명을 위해 선택·생성하지 않았다.

## 2. 실제 화면에서 어디를 볼까?

![스토리지의 8 GiB EBS와 파일 시스템 네 선택지](captures/0140-ec2-file-system-four-options.png)

1. ‘스토리지 구성’의 **8 GiB / gp3 / 루트 볼륨**: OS를 설치하고 부팅할 디스크다.
2. 아래 ‘파일 시스템’의 **S3 파일·EFS·FSx·없음**: 추가 공유 파일 저장소를 연결할지 고르는 영역이다.
3. ‘없음’이 선택돼 있어도 위의 EBS는 사라지지 않는다.

이 캡처는 인스턴스 생성 전 폼이다. 디스크가 이미 만들어졌다거나 외부 파일 시스템을 사용했다는 증거가 아니다.

## 3. 블록·파일·객체 저장소를 구분하자

### 블록 스토리지: EBS

가상 서버에 디스크 장치처럼 연결하는 저장소다. 운영체제가 그 위에 파일 시스템을 만들어 파일·폴더를 관리한다. 이번에는 AMI의 루트 볼륨에 OS와 프로그램이 놓인다.

EBS는 비유하면 서버의 SSD지만 물리적으로 서버 안에 붙은 로컬 디스크라는 뜻은 아니다. AWS의 네트워크 연결형 블록 스토리지이며 EC2 인스턴스 스토어와도 다르다. 이번 gp3 루트 볼륨을 여러 EC2가 함께 쓰는 공유 폴더처럼 다루지 않는다. 일부 다른 EBS 유형의 Multi-Attach 같은 고급 기능은 별개다.

### 파일 스토리지: 폴더 경로로 접근

공유 저장소를 서버의 특정 디렉터리에 연결하면 프로그램이 일반 파일처럼 읽고 쓸 수 있다. 저장소를 디렉터리 경로에 연결하는 일을 **마운트(mount)**라고 한다. 마운트가 항상 모든 데이터를 로컬 디스크에 복사한다는 뜻은 아니다.

### 객체 스토리지: 기본 S3

버킷에 객체 키와 데이터·메타데이터를 저장하고 API 등으로 접근한다. 폴더처럼 보이는 화면이 있어도 기본 S3 자체를 일반 디스크 파일 시스템과 완전히 같다고 생각하면 안 된다. 다만 지금 화면의 **S3 Files는 S3 데이터에 파일 시스템 접근을 제공하는 별도 기능**이므로 오래된 ‘S3에는 파일 접근이 없다’는 설명을 그대로 적용해서도 안 된다.

## 4. S3 파일 - 신규: S3 데이터를 파일·폴더처럼 다루기

### 무슨 기능인가?

Amazon S3 Files는 S3 버킷 또는 버킷의 특정 접두사에 연결되는 공유 파일 시스템이다. Linux 기반 컴퓨팅에서 마운트해 기존 파일 입출력 방식으로 데이터를 읽고 쓸 수 있다. AWS 공식 설명에 따르면 EFS 기술을 기반으로 구축되었고 파일 시스템과 S3 사이의 변경 동기화를 관리한다.

### 어떤 원리인가?

프로그램에는 파일·디렉터리 경로를 보여주고, 내부적으로 파일 작업을 S3 요청과 연결한다. 자주 쓰는 데이터와 메타데이터의 일부는 고성능 저장 계층에 놓고, 일부 읽기는 S3에서 직접 제공한다. 파일 시스템을 통한 쓰기와 S3 데이터는 동기화 과정을 거치므로 ‘항상 모든 데이터를 EBS에 복사해 두는 기능’이 아니다. 연결된 S3 데이터와 파일 시스템의 동시 수정·동기화 세부 규칙은 도입 전에 공식 문서로 확인해야 한다.

### 언제 유용할까?

- 원본 데이터는 S3에 있는데 기존 프로그램은 파일 경로로 데이터를 읽어야 할 때.
- AI·ML 전처리 코드나 여러 작업자가 같은 S3 데이터를 파일처럼 다뤄야 할 때.
- S3 API를 직접 호출하도록 프로그램을 크게 바꾸고 싶지 않을 때.

### 일반 S3·EFS와 무엇이 다른가?

일반 S3는 객체 저장소이고, S3 Files는 그 데이터를 파일 시스템으로 접근하게 하는 기능이다. EFS는 별도의 공유 파일 저장소를 제공하고, S3 Files는 연결된 S3 버킷 데이터와의 동기화를 중심으로 한다. 둘이 같은 내부 기술을 일부 사용한다고 동일한 서비스·과금 항목인 것은 아니다.

S3 Files를 오래된 s3fs 같은 도구나 Mountpoint for Amazon S3의 다른 이름으로 설명하지 않는다. 파일 시스템 기능·일관성·지원 동작이 도구마다 다르다. 화면의 ‘신규’는 이 기능이 새 옵션이라는 표시이지 클릭하면 즉시 새 버킷이 만들어진다는 뜻은 아니다.

### 비용과 설정 주의점

S3 자체의 저장·요청 비용 외에 S3 Files의 고성능 저장 계층, 파일 접근, 동기화에 관련된 비용을 고려해야 한다. 버킷·파일 시스템·마운트 대상·IAM 및 네트워크 설정도 필요하다. ‘S3는 저렴하니 체크해도 추가 비용이 없다’고 판단하지 않는다. 이번 기본 Nginx 페이지에는 필요 없다.

## 5. EFS: 여러 Linux 서버가 함께 쓰는 공유 폴더

**Amazon Elastic File System**이다. 서버 여러 대가 같은 파일을 읽고 쓰는 관리형 공유 파일 스토리지로, NFS(Network File System) 계열 프로토콜을 사용한다.

### 왜 필요할까?

웹 서버가 두 대 있다고 하자. 사용자 사진을 서버 A의 자체 디스크에만 저장하면 서버 B는 그 파일을 바로 볼 수 없다. 두 서버가 EFS의 같은 공유 경로를 사용하면 같은 파일 저장소에 접근할 수 있다. 물론 충돌 없는 동시 수정은 프로그램과 파일 잠금 등도 고려해야 한다.

### 특징

- 별도의 파일 서버 OS를 직접 운영할 부담을 줄인다.
- 사용량에 맞게 저장 공간이 늘고 줄어드는 관리형 서비스다.
- Linux 기반 서비스·컨테이너·공유 콘텐츠 등에 적합하다.
- 일반적으로 S3 버킷을 원본으로 삼는 동기화 저장소가 아니라 독립된 공유 파일 시스템이다.
- EFS 파일 시스템, VPC 마운트 대상, NFS 접근 보안 규칙과 권한 등을 확인해야 한다. NFS를 인터넷 전체에 공개할 이유는 없다.

### 비용과 수명

저장 클래스·저장량·접근·처리량 구성 등에 따라 과금이 달라질 수 있다. 마운트한 EC2를 중지·종료해도 별도로 존재하는 EFS까지 자동 삭제된다고 가정하지 않는다. 파일을 유지하려면 비용이 계속될 수 있고 정리 시 파일 시스템·마운트 대상·관련 자원을 확인해야 한다.

지금은 서버 한 대라 공유 폴더 요구가 없다. EFS가 나쁘거나 느려서가 아니라 불필요해서 선택하지 않는다.

## 6. FSx: 특정 파일 시스템 요구에 맞춘 전문 저장소 제품군

FSx는 하나의 파일 형식 이름이 아니다. 특정 상용·오픈소스 파일 시스템을 AWS가 관리형 서비스로 제공하는 제품군이다.

### 대표적인 종류

- **FSx for Windows File Server**: Windows 애플리케이션·SMB 공유·Active Directory 통합 같은 요구에 대응한다.
- **FSx for Lustre**: HPC·대규모 연산·GPU 작업 등의 고성능 공유 파일 작업에 활용한다.
- **FSx for NetApp ONTAP**: NetApp 환경의 파일·데이터 관리 기능이 필요한 기업 워크로드 등에 활용한다.
- **FSx for OpenZFS**: ZFS 기반 공유 저장소·스냅샷·복제 같은 기능이 필요한 워크로드에 활용한다.

### 중요한 화면 범위

‘FSx를 누르면 위 네 종류가 모두 같은 방식으로 즉시 연결된다’는 뜻은 아니다. 확인한 EC2 공식 문서에서 생성 마법사의 자동 연결 대상으로 설명하는 것은 **FSx for NetApp ONTAP과 FSx for OpenZFS**다. **Windows File Server와 Lustre는 생성 후 수동 마운트가 필요**하다고 명시한다. 서비스 전체 기능과 이 화면이 자동화해 주는 범위를 구분한다. 실제 선택 목록은 열어보지 않았으므로 현재 계정에 어떤 FSx가 존재하는지는 미확인이다.

### 비용과 복잡도

종류에 따라 저장 용량·처리량·IOPS·백업 등 과금 구조가 다르다. 별도의 네트워크·보안 그룹·마운트·인증 요구도 생긴다. EC2 생성 마법사가 관련 보안 그룹이나 사용자 데이터를 자동 추가할 수 있어 기존 최소권한·기본 사용자 데이터 계획에도 영향을 줄 수 있다.

단순한 Nginx 서버 한 대에 필요한 기본 디스크를 얻기 위해 FSx를 고를 필요는 없다.

## 7. 없음: 추가 공유 저장소를 쓰지 않기

‘없음’은 EBS까지 없애거나 OS 안의 파일 시스템을 없애는 선택이 아니다. 추가 S3 Files·EFS·FSx를 연결하지 않는다는 의미다.

우리 구성에서 유지되는 것:

- OS가 부팅할 EBS gp3 8 GiB.
- OS 안의 파일·디렉터리 구조.
- Nginx 설치·설정·기본 웹 페이지·로그를 저장할 공간.

추가되지 않는 것:

- 공유 파일 시스템 연결.
- 그 연결을 위한 별도 서비스·마운트 설정.
- 그 서비스를 쓰기 위한 추가 권한과 과금·정리 대상.

단, ‘없음’을 고른다고 모든 비용이 무료가 되는 것은 아니다. EC2·EBS·퍼블릭 IPv4 등 기존 항목의 비용은 별개다. 8 GiB면 무한히 파일을 쌓을 수 있는 것도 아니므로 설치 후 여유 공간과 로그 사용량을 확인한다.

## 8. 우리 과제와 연결하기

명세는 EC2 한 대에서 SSH 접속·웹 서버 실행·내부 HTTP 200·외부 접속을 검증하고, 종료 후 과금 위험 자원을 정리하도록 요구한다. EFS·FSx·S3 Files는 필수로 요구하지 않는다. EBS는 명세의 8~10 GiB 시작 권장 범위에 맞춰 8 GiB로 유지한다.

기본 HTML 파일을 EBS에 두고 Nginx로 응답해도 과제의 웹 서버 동작을 검증할 수 있다. 외부 공유 저장소를 선택해야 ‘진짜 배포’가 되는 것은 아니다.

따라서 이번 선택은 **EBS: gp3 8 GiB / 추가 파일 시스템: 없음**이다.

## 9. 앞으로 선택해야 할 상황이 생기면

- 서버 한 대의 OS·프로그램·작은 웹 페이지를 저장한다: 우선 EBS.
- 여러 Linux 서버가 같은 폴더를 공유해야 한다: EFS 검토.
- S3에 있는 데이터를 파일 경로로 직접 다루고 싶다: S3 Files 검토.
- Windows 공유·NetApp·ZFS·HPC 등 특정 기능이 필요하다: 맞는 FSx 제품 검토.

이는 처음 방향을 잡는 기준이지 모든 성능·비용·지원 조건을 대신하는 정답표는 아니다. 실제 도입 때는 사용 지역·데이터 양·읽기/쓰기 패턴·공유 요구·보안·백업·삭제 계획을 함께 확인한다.

## 10. 자주 생기는 오해

- ‘없음이면 Nginx가 파일을 못 저장한다’: 위의 EBS에 저장할 수 있다.
- ‘EBS도 네트워크 기반이니 EFS와 같은 공유 폴더다’: 블록 장치와 공유 파일 시스템은 다르다.
- ‘S3 파일은 기존 S3 이름만 바꾼 것’: 파일 시스템 접근·고성능 계층·동기화를 제공하는 별도 기능이다.
- ‘EFS는 단순히 EBS의 더 큰 용량 버전’: 사용 방식과 공유 구조가 다르다.
- ‘FSx는 무조건 EFS보다 빠르다’: 제품 종류·구성·워크로드에 따라 비교가 달라진다.
- ‘EC2를 지우면 연결된 외부 저장소도 전부 지워진다’: 별도 자원은 별도로 확인·정리해야 한다.
- ‘추가 기능이 보이니 IAM 권한을 다 줘야 한다’: 과제에 필요하지 않으면 생성하지 않고 권한도 넓히지 않는다.
