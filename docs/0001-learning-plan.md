# B3-1 학습 계획

## 목표와 방식

인터넷 요청이 AWS의 웹 서버까지 도달하는 경로를 설명하고, 최소권한과 접근 제한을 적용한 뒤 실습 리소스를 안전하게 정리한다. 사이트를 한 번 띄우는 것만으로 완료하지 않는다.

개념 설명 → 사용자 이해 확인 → 승인된 작은 실습 → 관찰 결과 확인 순서로 진행한다. AWS 리소스를 미리 만들거나 명령을 일괄 실행하지 않는다. 아래 단계는 계획이며 완료 증빙이 아니다.

## 왜 이 순서인가

네트워크 흐름을 모르고 콘솔 버튼만 따라 누르면 접속 오류가 생겼을 때 원인을 구분하기 어렵다. HTTP/IP/포트를 먼저 배우고 VPC 구성 요소를 연결한 뒤 접근 제어를 배운다. 비용과 정리 방법은 리소스 생성 이전에 이해해야 한다. 마지막으로 실제 서버를 만들고 관찰 가능한 오류를 분석한다.

## 단계별 순서와 확인 기준

### 1. 웹 요청과 서버

- 브라우저와 서버, HTTP 요청/응답, IP 주소, 포트, localhost.
- GitHub Pages가 대신 해주는 호스팅과 EC2를 직접 관리하는 것의 차이.
- 확인: '내 컴퓨터 → 퍼블릭 IP의 80번 포트 → 웹 서버 → 응답'을 설명한다.
- B1-1을 완성하지 않아도 여기부터 개념 학습은 가능하다.

### 2. 네트워크 구성 요소

- VPC: AWS 안의 논리적으로 분리된 네트워크.
- Subnet: VPC의 주소 범위를 나눈 구역.
- Route Table: 목적지별로 트래픽을 어디로 보낼지 정하는 규칙.
- Internet Gateway: VPC와 인터넷의 통신을 연결하는 구성 요소.
- 퍼블릭 IP와 0.0.0.0/0 → IGW의 의미.
- 확인: Public Subnet이라는 이름만으로 인터넷 연결이 생기지 않는 이유를 설명한다.
- 아직 리소스는 생성하지 않고 종이에 요청 흐름을 그린다.

### 3. 두 종류의 접근 제어

- Security Group: 인스턴스에 도달하는 네트워크 통신의 허용 규칙.
- IAM: 누가 AWS에서 어떤 관리 작업을 수행할 수 있는지 정하는 권한.
- HTTP 80 전체 공개와 SSH 22 본인 IP 제한의 목적 차이.
- 확인: SSH 접속 차단과 EC2 생성 권한 부족을 서로 다른 문제로 구분한다.
- AdministratorAccess로 문제를 우회하지 않는다.

### 4. 계정·비용·정리 사전 확인

실제 AWS 접근은 사용자 승인 후 수행한다.

- 계정의 프리티어/크레딧 적용 조건과 현재 이용 상태를 확인한다. 무료라고 가정하지 않는다.
- 서울 리전, micro 인스턴스, OS, EBS 용량 및 공인 IPv4를 포함한 비용 요인을 확인한다.
- 실습용 IAM 사용자/Role의 필요한 생성·조회·태그·연결·정리 권한을 검토한다. 루트 계정으로 실습하지 않는다.
- EC2 종료와 중지의 차이, EBS·EIP 등 별도 비용 항목을 배운다.
- 생성할 리소스 이름과 정리 순서를 미리 정한다.
- 확인: '무엇을 만들고, 비용이 어디서 생기며, 언제 어떻게 없앨지' 설명한 뒤 생성 범위를 승인한다.
- NAT Gateway/ALB/RDS 등 필수가 아닌 자원은 생성하지 않는다.

### 5. 최소 네트워크 만들기

- 승인된 범위에서 VPC 1개 → Public Subnet 1개 → IGW 연결 → Route Table 연결.
- 단계마다 리소스 ID와 연결 관계를 기록한다.
- 확인: 실제 Route Table에 0.0.0.0/0 → IGW가 있고 해당 Subnet에 연결된 것을 확인한다.

### 6. EC2와 SSH

- 인스턴스/OS/EBS/키페어의 역할을 배운다.
- Public Subnet에 EC2 1대를 만들고 HTTP 80 공개, SSH 22 본인 IP 제한을 적용한다.
- SSH 개인 키는 안전하게 보관하며 문서·저장소에 넣지 않는다.
- 확인: SSH 실제 접속, 인스턴스에서 외부 HTTPS 요청 성공, 적용된 SG 소스 범위를 확인한다.

### 7. Nginx와 B1-1 사이트 배포

- Nginx는 HTTP 요청에 파일 또는 응답을 제공하는 웹 서버다.
- 서버 설치/실행, 정적 파일 위치와 서비스 상태를 배운다.
- 먼저 curl http://localhost 응답을 확인한 뒤 B1-1 소스의 특정 버전을 배포한다.
- B1-1이 아직 준비되지 않았다면 서버 기본 응답만 확인하고 포트폴리오 배포는 대기한다.
- 확인: 내부 200 응답과 파일 경로, 브라우저가 CSS/JS/이미지를 정상 로드하는지 확인한다.

### 8. 외부 검증과 오류 분석

- 외부에서 브라우저 접속(A) 또는 /health 200과 고정 문구(B) 중 하나를 선택한다.
- B1-1 사이트를 보여주는 A 방식을 우선 추천한다. /health는 필요할 때 추가한다.
- 오류를 IP/라우팅/SG/웹 서버/파일 경로로 나누어 가설을 세운다.
- 실제 문제가 생기면 증상 → 가설 → 검증 → 조치 → 결과 → 재발방지를 기록한다.
- 실제 오류가 없다면 사용자 승인 아래 HTTP 허용을 잠시 제거하는 등 복구 가능한 통제 실험 1건을 실시한다. 의도한 실험임을 명시하며 실제 장애처럼 꾸미지 않는다. SSH 접근은 유지한다.
- 확인: 내부 요청 성공과 외부 요청 성공을 각각 증명하고, 오류 원인을 증거로 설명한다.

### 9. 공식 제출물 정리

- docs/architecture.png 또는 .pdf: 실제 VPC/Subnet/IGW/EC2/SG와 트래픽 흐름.
- README: 선택한 외부 검증 방식 A/B, URL 또는 IP, 검증 시점과 결과 스크린샷 위치.
- docs/troubleshooting.md 또는 .pdf: 최소 1건의 재현·분석·조치·재발방지.
- docs/cleanup-checklist.md: 실제 생성한 리소스 목록과 정리 결과.
- 공식 지정 파일은 학습용 순번 규칙의 예외다.
- 별도 평가표는 아직 확보하지 않았으므로 추후 확인되면 공식 요구사항과 함께 대조한다.

### 10. 리소스 정리와 최종 검증

- 외부 접속 증빙부터 저장한다. 정리 후 AWS 주소가 접속 불가한 것은 예상 결과다.
- 삭제 대상과 순서를 확인하고 사용자 승인 후 진행한다.
- EC2 Terminated → 남은 EBS 확인/삭제 → EIP Release(할당했다면) → 네트워크 의존성 정리 → IGW Detach/삭제 → Subnet/사용자 Route Table/VPC 삭제.
- 기본 Route Table 등 VPC 기본 리소스는 별도 삭제 가능 여부와 VPC 삭제에 따른 처리를 구분한다.
- 실제 생성한 추가 리소스도 확인한다. 미생성은 '미생성'으로 기록한다.
- 남은 리소스와 Billing을 확인한다. 비용 표시는 지연될 수 있으므로 화면 즉시 0원만으로 정리 완료를 단정하지 않는다.
- 확인: 리소스별 종료/삭제 근거가 있고 미사용 볼륨·주소가 남아 있지 않다.

## 두 과제 연결 일정

1. B1-1의 HTML/CSS/JS를 순서대로 학습한다.
2. B3-1 1~4단계의 개념과 비용 점검은 필요할 때 병행한다.
3. B1-1 사이트와 GitHub Pages 검증을 끝낸 뒤 AWS 실제 배포를 진행한다.
4. AWS 증빙을 확보하고 리소스를 정리한다. GitHub Pages는 유지한다.

선택 과제인 HTTPS와 Docker는 필수 AWS 실습을 설명하고 검증할 수 있게 된 뒤 결정한다. 새 도구 때문에 기본 네트워크 흐름 학습이 가려지지 않게 한다.
