# Peer review 답변 초안: Aside

[평가 질문 요약](0051-requirements-and-review-reference.md) · [과제 명세](0051-requirements-and-review-reference.md)

작성: Aside. 학습자가 자신의 말로 설명하기 위해 검토할 답변 초안이다. 실제 평가자의 판정이나 사용자가 이미 이 내용을 모두 이해했다는 증명이 아니다. 구현 사실은 저장소의 실습 기록과 캡처에 근거하며, 확장 방안은 개념 계획이며 실습 자원 정리는 후속 실행 결과로 구분했다. 원본 평가표의 PASS 표시를 이번 답변의 평가 결과로 복사하지 않았다.

**후속 상태:** 아키텍처·[정리 체크리스트](cleanup-checklist.md)와 주요 실습 자원 정리 증빙을 갖췄다. 현재 예상 비용은 0.00이지만 EC2 사용료 미표시 원인·무료 범위·확정 청구는 미확인이다. 학습자 설명 검증과 평가 PASS를 이 초안이 대신하지 않는다.

## 항목 1. 실제 구성과 동작

### 1-1. VPC, Public Subnet, IGW, 기본 라우팅이 구성되어 있는가?

저는 서울 리전에 실습 VPC와 Public Subnet을 만들고 IGW를 VPC에 연결했습니다. 실습 서브넷은 VPC의 기본 Route Table을 암시적으로 사용하며, 그 테이블에 기존 VPC 내부 local 경로를 유지한 채 `0.0.0.0/0 → IGW` 경로를 추가했습니다. 단순히 이름을 Public으로 붙인 것이 아니라 IGW 경로가 적용되는 것을 확인했습니다.

근거: [네트워크 구축 및 라우팅 저장 기록](0019-vpc-network-walkthrough.md).

### 1-2. SSH 접속 및 웹 서버 실행이 가능한가?

저는 내 PC에서 실행한 OpenSSH로 EC2의 `ec2-user`에 로그인했습니다. Aside에 표시한 ttyd는 PC의 터미널을 보여주는 화면일 뿐, AWS Instance Connect로 접속한 것은 아닙니다. EC2에서 `sudo systemctl enable --now nginx`를 실행해 시작·자동 시작을 등록했고, `curl -I http://localhost`의 `HTTP/1.1 200 OK`를 확인했습니다.

근거: [SSH 및 Nginx 검증 기록](0025-ec2-deployment-walkthrough.md), [내부 HTTP 200 캡처](captures/0192-nginx-localhost-http-200.png).

### 1-3. 필요한 포트만 열고 SSH를 특정 IP로 제한했는가?

최종 저장된 인바운드는 HTTP TCP 80 / `0.0.0.0/0`, SSH TCP 22 / 학습자 공인 IP 한 개의 `/32` 두 규칙입니다. SSH 전체 공개나 DB 포트 개방은 하지 않았습니다. 검토 중이던 Instance Connect 서비스 대역 추가안은 최종 목록에 없습니다. 아웃바운드는 실습상 기본 허용 규칙을 사용했으므로, 모든 방향의 보안 정책을 가장 엄격하게 최소화했다고 주장하지는 않습니다.

근거: [최종 저장 규칙 캡처](captures/0195-final-security-group-my-ip-only.png), [최종 규칙 확인 기록 29절](0028-browser-ssh-troubleshooting.md).

### 1-4. 외부 접속을 A 또는 B로 검증했는가?

저는 **A, 외부 브라우저 HTTP 접속**을 선택했습니다. EC2의 퍼블릭 IPv4로 접속해 `Welcome to nginx!` 페이지가 표시되는 것을 확인했습니다. 선택 방식·주소·화면을 README에 기록했습니다. `/health` 구현이나 방식 B 검증을 했다고 주장하지 않습니다. 별도로 EC2에서 `https://example.com`에 요청해 `HTTP/2 200`을 받아 아웃바운드도 확인했습니다.

근거: [README](../README.md), [외부 페이지](captures/0193-nginx-external-http-success.png), [EC2 아웃바운드](captures/0194-ec2-outbound-https-200.png).

### 1-5. EC2/EBS/EIP/IGW/VPC 정리 완료를 확인할 수 있는가?

저는 배포·접속 검증 후 EC2를 Terminated로 종료했고 서울 EBS·EIP·ENI 목록이 비어 있는 것을 확인했습니다. 실습 SG·Subnet·IGW·VPC와 해당 기본 라우팅·ACL·SG의 정리도 실제 목록과 캡처로 확인했습니다. EIP는 미할당이라 Release 해당 없음입니다. [정리 체크리스트](cleanup-checklist.md)에 ID별 결과·확인일·근거를 남겼습니다. 이는 최종 청구액이 0임을 보장한다는 뜻은 아닙니다.

**항목 1 답변 준비 상태:** 구성·접속·주요 자원 정리 증빙 있음. 제약 조건의 미확인 사항과 실제 평가 판정은 별도입니다.

## 항목 2. 구조·규칙·검증 방법 설명

### 2-1. 외부 → IGW → Subnet → EC2 흐름을 설명할 수 있는가?

제 구성에서 방문자는 EC2의 퍼블릭 IPv4로 HTTP 요청을 보냅니다. VPC에 연결된 IGW와 Public Subnet의 인터넷 경로, EC2 네트워크 인터페이스에 적용된 SG의 TCP 80 허용을 통해 Nginx에 도달하고 응답을 받습니다. 이때 Route Table은 요청이 방문하는 별도 서버가 아니라 서브넷에 적용되는 경로 규칙이고, SG도 독립적인 중간 서버가 아닙니다.

후속 작업으로 **[제출용 다이어그램](architecture.png)**을 작성했습니다. VPC/서브넷 경계, IGW, EC2, SG 적용 범위와 HTTP·SSH·아웃바운드 화살표를 표현했습니다. 학습자가 그림을 짚으며 이 설명을 자신의 말로 연습해야 합니다.

### 2-2. 보안 그룹 규칙을 어떤 기준으로 최소화했는가?

웹 방문에 필요한 TCP 80만 인터넷에 공개하고, 관리용 TCP 22는 내 공인 IP `/32`로 제한했습니다. HTTPS를 구성하지 않았으므로 443을 미리 열지 않았고, 필요 없는 DB·RDP·전체 포트 규칙도 만들지 않았습니다. `/32`는 출발지 주소 범위 제한이지 사용자 신원 확인을 대신하는 장치는 아니어서, SSH 키 인증도 함께 필요합니다.

### 2-3. 외부 검증 방식 선택을 위해 무엇을 구성했는가?

저는 브라우저 화면으로 동작을 설명하기 쉬운 A를 선택했습니다. IGW 연결·인터넷 기본 경로·EC2 퍼블릭 IPv4·SG의 HTTP 80 허용·Nginx 실행을 준비하고 외부 브라우저로 접속했습니다. 내부 localhost 성공만으로 인터넷 접속 성공을 대신하지 않고 두 시험을 구분했습니다.

### 2-4. 어떤 기준으로 리소스를 추적하고 정리하는가?

저는 확인된 `b3-1-vpc`, `b3-1-public-subnet`, `b3-1-igw`, `b3-1-web`, `b3-1-web-sg` 등의 이름과 실제 리소스 ID·연결 관계를 실습 기록에 남겼습니다. 모든 자원에 `Project` 태그가 붙었다고 확인한 것은 아닙니다. 정리할 때는 이름만 믿지 않고 리전·VPC 소속·ID·연결 관계를 확인해 기본 VPC나 다른 과제 자원을 건드리지 않겠습니다. 이 기록을 [정리 체크리스트](cleanup-checklist.md)로 연결하고 실제 확인일·결과·근거 캡처를 남겼습니다.

근거: [네트워크 기록](0019-vpc-network-walkthrough.md), [EC2 기록](0025-ec2-deployment-walkthrough.md).

**항목 2 답변 준비 상태:** 설명 초안과 다이어그램 있음. 그림·정리 증빙과 대조한 학습자 설명 연습이 필요.

## 항목 3. 원리와 문제 해결 방식

### 3-1. Public Subnet에 기본 경로가 필요한 이유는?

VPC 내부 경로만 있으면 외부 인터넷 목적지로 나갈 길이 없습니다. `0.0.0.0/0 → IGW`는 더 구체적인 경로가 없는 IPv4 목적지를 IGW로 보내는 기본 경로입니다. VPC 내부의 더 구체적인 local 경로는 우선하므로, 모든 통신을 무조건 인터넷으로 보내는 뜻은 아닙니다. 이 라우트는 방화벽 허용이나 EC2 퍼블릭 IP 부여를 대신하지 않아서 각각 따로 준비해야 합니다.

### 3-2. SG와 IAM의 차이 및 최소권한의 이유는?

SG는 네트워크 패킷의 포트·프로토콜·출발지/목적지를 제어하고, IAM은 어떤 사용자나 역할이 어떤 AWS API 작업을 어떤 자원에 수행할지 제어합니다. 예를 들어 SSH 패킷 도달 허용과 `ec2-instance-connect:SendSSHPublicKey` API 허용은 다른 문제입니다. 저는 실패했다고 관리자 정책을 붙이는 대신 필요한 작업을 확인해 추가하고, 키 전송은 특정 인스턴스·`ec2-user`·서울로 제한했습니다. 조회 작업 일부는 `Resource: "*"`를 쓰되 서울 요청 리전 조건을 유지했습니다. 모든 기존 작업이 인스턴스 한 대에만 제한된 것은 아니므로 완벽한 최소권한이라고 과장하지 않습니다.

근거: [현재 보관 정책](policies/b3-1-ec2-seoul-policy.json), [정책 읽기](0030-iam-policy-reading-쉬운설명.md).

### 3-3. SSH 또는 DB 포트를 전체 공개하면 왜 위험하며 대안은?

관리 포트를 전체 인터넷에 열면 자동 스캔과 로그인 공격에 노출되는 범위가 커집니다. 저는 SSH를 개인 IP `/32`와 키 인증으로 제한했습니다. 다른 운영 환경이라면 VPN·배스천·조건에 맞는 Session Manager 또는 Instance Connect Endpoint 등도 검토할 수 있지만, 이번에 구성했다고 말하지는 않습니다. DB가 필요해지면 인터넷 공개 대신 사설 네트워크와 필요한 애플리케이션 SG만 허용하는 방안을 우선 검토하겠습니다.

### 3-4. 왜 가설 → 검증 순서를 지켰는가?

같은 ‘연결 실패’라도 IAM API 권한, 네트워크 차단, 키 인증, 서버 프로세스 문제는 원인이 다르기 때문입니다. 저는 실제 오류 문구와 캡처를 남기고 그 가설에 필요한 범위만 확인했습니다. localhost 80 연결 실패에서는 외부 SG를 넓히지 않고 Nginx를 시작한 뒤 같은 curl 시험에서 200으로 바뀐 것을 확인했습니다. 반면 브라우저 SSH의 일반 연결 오류는 서비스 대역을 추가해 해결했다고 주장하지 않고, 성공이 확인된 로컬 OpenSSH를 최종 접속 경로로 사용했습니다.

근거: [트러블슈팅 보고서](troubleshooting.md), [브라우저 SSH의 미해결 범위 및 최종 경로](0028-browser-ssh-troubleshooting.md), [Nginx 전후 결과](0025-ec2-deployment-walkthrough.md).

**항목 3 답변 준비 상태:** 실제 경험에 근거한 설명 초안 있음. 학습자가 각 구분을 자신의 말로 설명하는 연습 필요.

## 항목 4. 장애·권한·확장·비용 상황 대응

### 4-1. 외부 접속 장애 시 어떤 순서로 점검하는가?

저는 평가 질문의 순서에 맞춰 ① 서브넷에 적용된 라우팅 테이블의 IGW 경로와 IGW 연결, ② SG의 대상 포트·소스·인스턴스 연결, ③ 현재 퍼블릭 IP와 필요 시 DNS 레코드, ④ 서버 프로세스·리스닝 포트·로그를 확인하겠습니다. NACL과 응답 경로도 필요하면 확인합니다. 서버에서는 `systemctl status nginx`, `ss -lnt`, `curl -I http://localhost`, 서비스 로그를 사용해 범위를 좁힐 수 있습니다. 다만 localhost 자체가 실패한다는 증거가 있으면 서버 프로세스를 먼저 살펴보는 등 증거에 따라 우선순위를 조정합니다. 이 명령을 모두 실행한 이력이라고 주장하는 것은 아닙니다.

### 4-2. IAM 실패 시 최소 범위를 어떻게 찾았는가?

저는 실패 메시지에 나온 정확한 Action과 실제 연결 정책을 비교했습니다. `DescribeSecurityGroupRules` 누락 때 편집 화면에서도 같은 오류가 나는 것을 확인한 뒤 서울 제한을 유지하며 조회 작업 하나를 추가했고, 정책 저장·기본 버전과 실제 화면 조회 복구까지 확인했습니다. `DescribeAddresses`는 주소 조회 보완이지 SSH 키 전송의 필수 종속 권한으로 단정하지 않았습니다. 권한 변경 전후 JSON을 비교해 불필요한 작업이 추가되지 않았는지도 확인했습니다. 기존 관리자 역할은 정책 관리에 사용했으며 과제 사용자에게 AdministratorAccess를 연결하지 않았습니다.

근거: [정책 전체 대조·버전 3·조회 복구 기록](0028-browser-ssh-troubleshooting.md).

### 4-3. 인스턴스를 2대로 늘린다면 병목과 추가 구성은?

현재 EC2 한 대는 요청 처리와 장애 대응이 한곳에 집중되는 지점입니다. 실제 CPU·메모리·네트워크·접속량을 측정하지 않았으므로 구체적인 성능 병목이 무엇이라고 확정하지는 않겠습니다. 확장 설계에서는 ALB로 두 인스턴스에 요청을 분산하고, 가능하면 서로 다른 AZ에 배치해 한 AZ의 장애 위험을 줄이겠습니다. ASG·헬스체크·동일한 배포 설정과 세션/파일 공유 방식도 검토하겠습니다. 이때 인스턴스의 웹 포트는 ALB SG에서만 받도록 바꾸는 설계가 가능합니다. **이것은 향후 설계 답변이며 현재 구현은 EC2 한 대이고 ALB는 없습니다.** 비용도 새로 검토해야 합니다.

### 4-4. 예상 밖 비용을 어떻게 추적하고 정리하는가?

저는 먼저 Billing에서 서비스·리전·사용량 항목을 확인하고, 이번 실습에서 사용한 EC2 실행 시간, EBS, 퍼블릭 IPv4 비용을 확인하겠습니다. EIP가 별도로 할당됐는지, 스냅샷·NAT Gateway·로드밸런서 같은 다른 비용 자원이 있는지도 실제 목록과 이름·ID·태그로 확인하겠습니다. 원인을 보지 않고 모든 자원을 지우거나 계정 전체를 변경하지 않겠습니다.

실습 종료 시 인스턴스 종료와 연결 EBS 삭제 여부를 확인하고, 잔여 볼륨·EIP 등은 소유·사용 여부를 확인해 정리하겠습니다. 이후 의존 관계를 살펴 IGW 연결 해제·삭제, 서브넷·사용자 생성 SG·라우팅 관련 자원, VPC를 정리하고 체크리스트에 남기겠습니다. 기본 SG·기본 라우팅 테이블처럼 VPC 삭제 과정에서 처리되는 자원은 무조건 개별 삭제하지 않습니다. 삭제 후에도 요금 반영 지연과 이미 발생한 비용이 있을 수 있어 ‘즉시 청구액 0’이라고 보장하지 않습니다. **후속으로 주요 실습 자원 정리를 수행했고 현재 예상 비용 조회와 확정 청구 미확인을 구분해 체크리스트에 남겼습니다.**

**항목 4 답변 준비 상태:** 실제 권한 문제 경험과 향후 대응 계획을 구분한 초안 있음. 확장은 미수행 계획이고 주요 자원 정리는 실행 증빙 있음.
