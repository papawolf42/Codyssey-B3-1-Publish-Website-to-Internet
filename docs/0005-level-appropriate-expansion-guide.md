# B3-1 수준에 맞춘 확장 학습 안내

[교육 목표](0004-educational-goals-and-learning-scope.md) · [넓은 키워드 지도](0003-cloud-foundations-beyond-assignment.md) · [필수 조건](0002-required-checklist-and-extension-rules.md)

## 1. 넓히되 과제의 난이도를 바꾸지 않는다

이 문서는 고급 기술을 더 설치하는 계획이 아니다. **현재 구성 요소의 가까운 비교 대상을 알아보고, 작은 요청과 오류를 설명하는 학습**이다. 모든 실험은 제안이며 완료 기록이 아니다. AWS 자원 생성·접근 규칙 변경·삭제는 각각 승인된 범위에서만 한다.

## 2. 주소·포트·HTTP

**출발:** 외부에서 웹사이트 접속.

넓힐 내용: URL의 호스트·포트·경로, localhost와 퍼블릭 IP, HTTP 상태와 네트워크 실패. localhost는 명령을 실행한 그 컴퓨터를 가리키므로 내 PC와 EC2에서 의미가 다르다.

질문: ‘EC2 안에서 localhost가 됐으니 내 PC에서도 localhost로 열면 될까?’

작은 비교: 같은 요청을 EC2 내부와 외부에서 보냈을 때 목적지가 어떻게 달라지는지 그림으로 표시한다.

**멈춤:** 어디서 어느 주소의 어느 포트로 요청했는지 말할 수 있다.

미룰 것: TCP 패킷 구조·전체 OSI 계층 암기.

검색어: `localhost`, `URL port path`, `HTTP status`, `curl connection error`.

## 3. VPC·Subnet·CIDR

**출발:** VPC와 Public Subnet 생성.

넓힐 내용: VPC 안의 주소 범위, 그 일부인 Subnet, CIDR의 범위 표기, 사설/공인 주소, 리전과 AZ의 관계. Subnet은 한 AZ에 속하고 VPC는 해당 리전 안에서 여러 AZ의 Subnet을 가질 수 있다.

질문: ‘/32와 0.0.0.0/0을 SSH 소스에 넣으면 허용 범위가 어떻게 달라질까?’

작은 비교: 본인 IPv4 하나를 허용하는 표기와 모든 IPv4를 허용하는 표기의 의미만 설명한다. 실제 SG를 전체 공개하지 않는다.

**멈춤:** 주소 범위·서버 위치·허용 소스를 구분한다.

미룰 것: 대규모 주소 배분·이진수 기반 서브넷 계산 전면 훈련.

검색어: `CIDR basics`, `private public IP`, `region vs Availability Zone`.

## 4. 경로·IGW

**출발:** 0.0.0.0/0 → IGW.

넓힐 내용: 라우트의 목적지와 다음 전달 대상, Subnet과 Route Table 연결, IGW의 역할. 이 IPv4 구성에서는 퍼블릭 주소와 접근 규칙도 별도로 필요하다.

질문: ‘길이 열려 있으면 문도 자동으로 열리나?’ 라우팅과 보안 허용은 다른 설정이다.

작은 비교: 실제 구성 전에 종이에 IGW만 있음/경로만 있음/주소만 있음 각각에서 빠진 조건을 찾는다.

**멈춤:** Public Subnet 이름이 아니라 실제 조건으로 설명한다.

미룰 것: NAT·VPN·Peering 실습. 이름과 목적만 알아도 된다.

검색어: `route table association`, `Internet Gateway`, `public subnet requirements`.

## 5. SG·IAM·SSH 키

**출발:** 최소권한과 접근 제한.

| 장치 | 기본 질문 |
| --- | --- |
| SG | 어떤 네트워크 소스가 어떤 포트로 통신할 수 있나? |
| IAM | 어떤 AWS 신원이 어떤 관리 작업을 할 수 있나? |
| SSH 사용자·키 | 운영체제에 어떤 사용자로 인증해 들어가나? |

작은 비교: EC2 생성 거절, SSH 연결 시간 초과, SSH Permission denied를 같은 오류로 묶지 않고 후보 층을 나눈다. 각 증상은 단서이지 단일 원인을 확정하는 증거는 아니다.

**멈춤:** 문제에 맞는 설정을 찾고 AdministratorAccess·SSH 전체 공개로 우회하지 않는다.

미룰 것: 복잡한 조직 권한·SSO 구축. 실습 역할의 구체적 Policy는 실제 작업과 공식 권한 지원 범위를 확인하며 작성한다.

검색어: `IAM vs security group`, `SSH public key`, `least privilege`.

## 6. EC2·디스크·서비스

**출발:** 인스턴스 1대와 Nginx.

넓힐 내용: EC2는 컴퓨터, EBS는 디스크, Nginx는 그 안의 서비스라는 구분. 인스턴스가 Running이어도 웹 서버는 중지돼 있을 수 있다. 웹 서버가 실행 중이어도 원하는 포트나 파일을 제공하지 않을 수 있다.

작은 비교: 인스턴스 상태·서비스 상태·로컬 HTTP 응답을 서로 다른 확인 항목으로 적는다.

**멈춤:** 설치·실행·리스닝·응답을 구분하고 관련 파일·로그를 찾는다.

미룰 것: 커널 튜닝·이미지 자동화·고가용성 서버 복제.

검색어: `process vs service`, `systemctl status`, `Nginx document root`, `EBS volume`.

## 7. 파일 배포·브라우저 동작

**출발:** B1-1 사이트를 Nginx에서 제공.

넓힐 내용: HTML과 CSS/JS/이미지는 별도 요청이다. Nginx가 파일을 전달하는 것과 브라우저가 GitHub API를 호출하는 것은 별도 단계다. Linux의 파일명 대소문자·경로·읽기 권한도 확인한다.

질문: ‘HTML은 200인데 카드가 안 보이면 VPC부터 다시 만들까?’

작은 비교: HTML·CSS·JS·이미지·GitHub API 요청을 Network에서 분리해 관찰한다.

**멈춤:** 서버 제공 문제와 프런트엔드 실행 문제를 구분한다.

미룰 것: 리버스 프록시·로드밸런서·백엔드 분리 구축.

검색어: `static web server`, `case-sensitive paths`, `browser Network panel`.

## 8. 장애 분석

**출발:** 증상→가설→검증→조치→결과→재발방지.

넓힐 내용: 관찰한 사실과 추측을 분리하고, 한 번에 한 조건을 바꾸며 재검증한다. 로그가 없는 것도 정보지만 그것만으로 모든 원인을 확정하지 않는다.

질문: ‘권한·경로·서비스를 동시에 바꿔 고쳤다면 어떤 조치가 필요했는지 알 수 있나?’

작은 비교: 외부 실패/내부 성공과 외부 실패/내부 실패의 조사 순서를 다르게 적는다. 실제 오류가 없다면 임의 장애를 실제 장애로 꾸미지 않는다. 통제 재현은 승인·복구 계획과 평가 인정 여부를 확인한다.

**멈춤:** 한 건의 문제를 증거와 변경 전후 결과로 설명한다.

미룰 것: 대규모 로그 플랫폼·분산 추적 구축.

검색어: `troubleshooting hypothesis`, `Nginx access error log`, `connection timeout`.

## 9. 정리·비용

**출발:** 실습 끝나면 리소스 삭제.

넓힐 내용: Stop/Terminate, 남는 볼륨·주소·스냅샷, 자원 의존성, 실제 생성 여부. 비용·권한·정리 방법을 만들기 전에 생각한다.

작은 비교: 생성 목록 옆에 삭제 확인 방법을 적는다. 예를 들어 EC2 상태 확인과 EBS 목록 확인을 별개로 둔다. 리소스 ID·리전으로 타깃을 구분하고 다른 작업의 자원을 지우지 않는다.

**멈춤:** 미생성·생성됨·종료됨·삭제됨을 근거로 구분하고 남은 항목을 확인한다.

미룰 것: 비용 최적화 상품·자동 IaC 운영. 현재 요금과 계정 적용 범위는 실제 실습 직전에 별도 확인한다.

검색어: `stop vs terminate`, `orphaned EBS`, `Elastic IP release`, `resource dependencies`.

## 10. HTTPS·Docker는 언제?

필수 요청 경로를 설명하고 내부·외부 응답을 검증한 다음 선택한다.

- HTTPS: 도메인·인증서·암호화·갱신을 작은 단위로 배운다.
- Docker: 이미지·컨테이너·포트 매핑·컨테이너 안과 밖의 localhost를 비교한다.

도구 추가 뒤에도 IAM·SG·라우팅·정리 책임은 사라지지 않는다. 선택 과제 때문에 필수 HTTP·SSH 조건을 임의 변경하지 않는다.

**멈춤:** 추가한 도구가 무엇을 해결하며 기존 경로의 어디에 들어가는지 설명한다.

## 11. 추천 학습 리듬

1. 요청 그림을 그린다. 자원 생성 없이 시작한다.
2. 네트워크·권한·비용 개념을 짧게 확인한다.
3. 승인 후 최소 구성을 한 연결씩 만든다.
4. 내부 응답→외부 응답을 따로 확인한다.
5. 관찰한 실패를 한 가설씩 분석한다.
6. 실제 구성·검증·오류 근거를 문서에 남긴다.
7. 승인된 실습 자원을 정리하고 목록으로 확인한다.

사수의 목표는 대신 빠르게 만드는 것이 아니라 학습자가 ‘이 설정이 없으면 어디가 실패할지’를 예상할 수 있게 하는 것이다. 명세 이행과 학습자의 이해는 별도로 확인한다.
