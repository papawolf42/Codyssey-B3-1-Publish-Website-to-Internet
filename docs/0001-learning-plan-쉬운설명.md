# B3-1 학습 계획 (쉬운 설명판)

## 목표와 학습 방식

인터넷에서 들어온 사용자의 요청이 AWS 클라우드 안에 있는 웹 서버까지 어떻게 안전하게 도달하는지 그 길목을 논리적으로 설명하고, 꼭 필요한 사람과 포트만 열어주는 보안 원칙(접근 제한과 최소권한)을 적용한 뒤, 실습이 끝나면 비용이 나오지 않도록 자원을 깔끔하게 정리하는 방법을 배웁니다. 웹사이트 화면을 단순히 한 번 띄워보는 것만으로는 과제가 끝난 것이 아닙니다.

학습은 **개념 설명 → 학습자의 이해 확인 → 명시적으로 승인받은 아주 작은 단위의 실습 → 화면과 로그를 통한 관찰 결과 확인** 순서로 차근차근 진행합니다. AWS 클라우드 자원을 미리 한꺼번에 만들어두거나 검증되지 않은 명령어를 무작정 실행하지 않습니다. 아래에 적힌 각 단계는 앞으로 진행할 체계적인 계획이며, 실제로 작업을 마쳤다는 완료 증빙이 아닙니다. (현재 시점에서는 어떠한 AWS 리소스도 생성되지 않았습니다.)

## 왜 이 순서로 배우는가?

데이터가 이동하는 네트워크의 전체 흐름을 알지 못한 채 클라우드 관리 콘솔 화면의 버튼만 기계적으로 따라 누르면, 나중에 접속이 안 되거나 오류가 났을 때 무엇이 잘못되었는지 원인을 전혀 찾아낼 수 없습니다.
- 따라서 가장 먼저 웹 통신의 기본 규칙인 HTTP, 컴퓨터 주소(IP), 출입문 번호(포트)의 기본 원리를 배웁니다.
- 그 다음 클라우드 안에서 나만의 네트워크를 구성하는 부품들(VPC, 서브넷, 인터넷 게이트웨이, 라우팅 테이블)의 역할을 이해합니다.
- 네트워크 길목이 정리된 뒤, 누가 들어올 수 있는지 통제하는 두 가지 보안 장치(보안 그룹과 IAM 권한)를 배웁니다.
- 클라우드 요금과 자원 정리 방법은 자원을 만들기 전에 미리 완벽하게 이해해야 실수로 요금이 나가는 사고를 막을 수 있습니다.
- 이 모든 사전 준비와 원리 이해가 끝난 뒤에 비로소 실제 가상 서버를 띄우고, 접속 오류가 발생했을 때 단계별로 원인을 좁혀가는 분석 방법을 훈련합니다.

## 단계별 순서와 확인 기준

### 1단계: 웹 요청과 웹 서버의 기본 원리

- 웹 브라우저(사용자 프로그램)와 웹 서버(응답 프로그램), 웹 데이터를 주고받는 규약(HTTP 요청과 응답), 인터넷 주소(IP 주소), 프로그램 출입문 번호(포트), 내 컴퓨터를 가리키는 주소(`localhost`).
- GitHub Pages처럼 파일만 올려두면 자동으로 운영해 주는 관리형 서비스와, 내가 직접 가상 서버(EC2)를 빌려 운영체제부터 웹 서버까지 관리하는 방식의 본질적인 차이점을 비교합니다.
- **이해 확인 기준:** '내 컴퓨터 웹 브라우저 → 가상 서버의 공인 IP 주소 80번 포트 → 서버 안에서 기다리는 Nginx 웹 서버 프로그램 → 브라우저로 돌아오는 웹페이지 응답'의 흐름을 자신의 말로 설명할 수 있어야 합니다.
- 이전 미션(B1-1 웹 포트폴리오) 코드가 아직 완전히 준비되지 않았더라도, 이 단계의 네트워크 및 서버 기본 개념 학습은 바로 시작할 수 있습니다.

### 2단계: 클라우드 네트워크를 이루는 핵심 부품들

- 가상 사설망(VPC, Virtual Private Cloud): AWS 클라우드 안에 마련하는 다른 사용자와 격리된 나만의 안전한 가상 네트워크 영토.
- 하위 구역(Subnet, 서브넷): 가상 사설망(VPC)의 넓은 IP 주소 범위를 쓰임새(공개 구역, 내부 구역)에 따라 나누어 둔 작은 구역.
- 경로 안내표(Route Table, 라우트 테이블): 데이터가 목적지 IP 주소로 가려면 어디로 통과해야 하는지 알려주는 이정표 목록.
- 인터넷 출입구(Internet Gateway, IGW): 가상 사설망(VPC)과 바깥 인터넷 세상을 이어주는 공식 관문.
- 퍼블릭 IP(공인 IP)와 모든 인터넷 세상(`0.0.0.0/0`)으로 나가는 길을 인터넷 게이트웨이(IGW)로 연결한다는 것의 구체적인 의미.
- **이해 확인 기준:** 단순히 서브넷 이름을 '공개 구역(Public Subnet)'이라고 붙였다고 해서 저절로 인터넷과 연결되는 것이 아니며, 인터넷 출입구(IGW)와 경로 안내표(Route Table) 설정이 반드시 함께 연결되어야 함을 설명할 수 있어야 합니다.
- *주의:* 이 단계에서는 실제 클라우드 자원을 만들지 않고, 종이나 화면에 요청 흐름도를 그리며 개념을 먼저 확인합니다.

### 3단계: 두 종류의 접근 제어 (방화벽 vs 관리 권한)

- 가상 방화벽(Security Group, 보안 그룹): 가상 서버(EC2) 바로 앞 문지기로서 들어오고 나가는 네트워크 통신 패킷을 검사하고 허용하는 규칙 목록.
- 권한 관리 체계(IAM, Identity and Access Management): 누가(어떤 사람이나 프로그램이) AWS 클라우드의 어떤 자원을 만들거나 지우는 관리 작업을 할 수 있는지 통제하는 권한 규칙.
- 일반 웹 접속 포트인 HTTP 80번을 전 세계 모든 사람에게 열어주는 것과, 관리자 접속 포트인 SSH 22번을 내 개인 IP로만 좁히는 것의 보안상 목적 차이.
- **이해 확인 기준:** "가상 서버에 SSH 원격 접속이 안 되는 문제(네트워크 방화벽 문제)"와 "가상 서버를 새로 만들 권한이 없어서 거절당하는 문제(AWS 관리 권한 문제)"가 서로 완전히 다른 차원의 문제임을 구분하여 설명할 수 있어야 합니다.
- 관리자 권한(`AdministratorAccess`)으로 권한을 무작정 다 열어서 문제를 얼렁뚱땅 넘기지 않습니다.

### 4단계: 계정 상태, 비용 요인, 자원 정리 방법 사전 확인

실제 AWS 콘솔에 접속하여 자원을 다루는 작업은 학습자의 사전 승인을 받은 뒤에만 시작합니다.

- 현재 사용하는 AWS 계정의 무료 체험(프리 티어) 조건과 크레딧 상태를 직접 확인합니다. 무조건 무료일 것이라고 짐작하지 않습니다.
- 대한민국 서울 리전(`ap-northeast-2`), 프리 티어 대상 소형 서버 규격(micro급), 리눅스 운영체제, 가상 디스크(EBS) 용량, 공인 IPv4 주소 사용 등 요금이 발생할 수 있는 원인들을 꼼꼼히 확인합니다.
- 실습에 사용할 IAM 사용자(또는 역할)가 가상 서버(EC2), 가상 네트워크(VPC), 방화벽(보안 그룹)을 만들고, 조회하고, 태그를 붙이고, 삭제하는 데 꼭 필요한 최소한의 권한만 가지고 있는지 검토합니다. 최고 관리자(Root) 계정으로 직접 실습하지 않습니다.
- 가상 서버의 일시 중지(Stop, 디스크 요금 계속 발생)와 완전 삭제(Terminate)의 차이점을 배우고, 가상 디스크(EBS)나 고정 IP(EIP)처럼 서버가 꺼져도 별도 과금되는 항목을 파악합니다.
- 앞으로 만들 자원의 이름 규칙과 실습 종료 후 삭제할 순서를 미리 정해 둡니다.
- **이해 확인 기준:** '무엇을 만들 것이며, 비용은 어디서 발생할 수 있고, 실습 후 언제 어떤 순서로 삭제할 것인가'를 스스로 설명하고 승인받은 뒤 실습으로 넘어갑니다.
- 실습 필수 요구사항이 아닌 유료 자원(NAT Gateway, 로드밸런서 ALB, 데이터베이스 RDS 등)은 절대로 생성하지 않습니다.

### 5단계: 최소 단위의 가상 네트워크 만들기

- 승인받은 범위 내에서 가상 사설망(VPC 1개) → 공개 하위 구역(Public Subnet 1개) → 인터넷 출입구(Internet Gateway 연결) → 경로 안내표(Route Table 등록 및 서브넷 연결)를 순서대로 진행합니다.
- 각 단계를 만들 때마다 화면에 부여된 고유 식별 번호(Resource ID)와 자원 간의 연결 관계를 기록해 둡니다.
- **이해 확인 기준:** 실제 경로 안내표에 모든 인터넷(`0.0.0.0/0`)으로 가는 출구로 인터넷 게이트웨이(IGW)가 정확히 등록되어 있고, 그 안내표가 내가 만든 서브넷에 올바르게 연결되어 있음을 콘솔 화면에서 확인합니다.

### 6단계: 가상 서버(EC2) 생성과 안전한 원격 접속(SSH)

- 가상 컴퓨터(인스턴스), 운영체제(OS), 외장 디스크(EBS), 원격 접속 열쇠 파일(키페어)의 역할을 배웁니다.
- 공개 구역(Public Subnet) 안에 가상 서버 1대를 띄우고, 보안 그룹 규칙에 웹 통신(HTTP 80)은 전체 공개, 원격 접속(SSH 22)은 오직 내 개인 인터넷 IP만 허용하도록 설정합니다.
- 원격 접속 열쇠(SSH 개인 키 `.pem` 파일)는 안전한 폴더에 소중히 보관하며, 절대로 깃허브 저장소나 문서에 업로드하지 않습니다.
- **이해 확인 기준:** 내 컴퓨터 터미널에서 가상 서버로 SSH 접속이 실제로 성공하는지, 그리고 가상 서버 안에서 바깥 인터넷으로 나가는 웹 요청(`curl https://example.com`)이 성공하는지 확인합니다.

### 7단계: Nginx 웹 서버 설치와 웹사이트 배포

- 웹 서버 프로그램인 Nginx(엔진엑스)가 웹 브라우저의 HTTP 요청을 받아 준비된 HTML 파일이나 데이터를 어떻게 응답해 주는지 역할을 이해합니다.
- 서버 운영체제 패키지 관리자를 통해 Nginx를 설치하고 백그라운드 서비스로 실행한 뒤, 웹 문서가 저장되는 기본 폴더 위치와 서비스 동작 상태를 확인합니다.
- 먼저 서버 내부에서 로컬 테스트 명령(`curl http://localhost`)을 실행하여 웹 서버가 정상 응답(200 OK)을 주는지 확인한 뒤, 이전 미션(B1-1)에서 만든 정적 웹사이트 파일들을 서버로 복사하여 배포합니다.
- 만약 B1-1 포트폴리오 웹사이트가 아직 준비되지 않았다면 Nginx 기본 안내 페이지만으로 먼저 확인하고, 파일 배포는 준비될 때까지 기다립니다.
- **이해 확인 기준:** 서버 내부에서의 200 정상 응답, 배포된 파일의 경로와 권한, 웹 브라우저가 화면의 서식(CSS), 동작(JS), 이미지를 문제없이 불러오는지 확인합니다.

### 8단계: 외부 접속 검증과 오류 분석 (트러블슈팅)

- 바깥 인터넷 환경에서 가상 서버의 공인 IP로 웹 브라우저 접속(검증 방식 A) 또는 `/health` 주소 호출 시 200 응답과 고정 문구 확인(검증 방식 B) 중 하나를 선택합니다.
- 내가 만든 웹 포트폴리오 화면을 바로 보여줄 수 있는 A 방식을 우선 권장하며, B 방식은 필요에 따라 추가합니다.
- 만약 접속이 되지 않는다면 문제를 IP 주소 오류, 라우팅 경로 오류, 보안 그룹 방화벽 차단, 웹 서버 프로그램 중지, 파일 경로 오류 중 어느 단계인지 나누어 가설을 세웁니다.
- 실제로 문제가 발생하면 **증상 → 가설 → 검증 → 조치 → 결과 → 재발 방지**의 6단계 양식으로 차분하게 기록합니다.
- 만약 실습이 너무 순조로워 아무런 오류도 발생하지 않았다면, 사용자 승인 아래 보안 그룹에서 HTTP 80 허용 규칙을 잠시 빼보는 등 안전하게 복구 가능한 1건의 통제된 실험을 수행해 봅니다. 이때는 의도적인 학습용 실험임을 명확히 밝히며, 실제 시스템 장애인 것처럼 꾸미지 않습니다. (이때도 원격 관리 접속인 SSH 22 포트는 절대 막지 않습니다.)
- **이해 확인 기준:** 서버 내부에서의 접속 성공과 외부 인터넷에서의 접속 성공을 각각 명확한 증거로 제시하고, 접속 오류가 발생했을 때 그 원인을 추측이 아닌 객관적 증거로 설명할 수 있어야 합니다.

### 9단계: 공식 제출 문서 정리

- `docs/architecture.png` 또는 `docs/architecture.pdf`: 실제로 구성한 VPC, 서브넷, 인터넷 게이트웨이, 가상 서버, 보안 그룹과 데이터 트래픽 흐름을 담은 구조도.
- `README.md`: 선택한 외부 접속 검증 방식(A 또는 B), 접속한 실제 공인 IP 또는 URL, 검증 시점과 정상 동작 스크린샷 위치 명시.
- `docs/troubleshooting.md` 또는 `docs/troubleshooting.pdf`: 최소 1건 이상의 오류 재현, 원인 분석, 조치 결과 및 재발 방지 대책 보고서.
- `docs/cleanup-checklist.md`: 실제로 생성했던 리소스 목록과 삭제 완료 증빙.
- 공식 제출 파일들은 과제 명세에 이름이 지정되어 있으므로 일반 학습 노트의 네 자리 순번 규칙 예외로 취급합니다.
- 별도의 세부 평가표는 아직 수집되지 않았으므로 추후 확인되면 공식 요구사항과 함께 대조하여 검토합니다.

### 10단계: 클라우드 리소스 정리와 최종 비용 확인

- 자원을 삭제하기 전에 외부 접속 성공 스크린샷과 증빙 자료부터 먼저 확실하게 저장해 둡니다. (자원을 삭제하고 나면 공인 IP 접속이 끊어지는 것은 지극히 당연한 결과입니다.)
- 삭제할 자원 목록과 안전한 삭제 순서를 다시 확인하고, 사용자의 명시적인 승인을 받은 뒤 정리를 시작합니다.
- 권장 삭제 순서: EC2 가상 서버 완전 종료(Terminated) → 남아 있는 미사용 EBS 디스크 볼륨 확인 및 삭제 → Elastic IP 고정 IP 반환(Release, 할당한 경우) → 네트워크 의존성 정리 → 인터넷 게이트웨이 연결 해제(Detach) 및 삭제 → 공개 서브넷, 라우팅 테이블, 가상 사설망(VPC) 삭제.
- 가상 사설망(VPC)을 만들 때 자동으로 생기는 기본 라우팅 테이블 등은 별도로 삭제할 수 없으며 VPC가 삭제될 때 함께 정리된다는 점을 이해합니다.
- 실제로 추가 생성한 리소스가 있다면 그 목록도 확인하고, 만들지 않은 항목은 '미생성'으로 명확히 기록합니다.
- 남아 있는 자원이 없는지 콘솔 목록을 재확인하고, AWS 요금 대시보드(Billing Dashboard)를 확인합니다. 요금 청구 내역은 반영되는 데 수 시간에서 하루 정도 지연될 수 있으므로, 현재 화면에 0원이라고 뜬다는 사실만으로 자원 정리가 끝났다고 섣불리 단정하지 말고 콘솔의 리소스 목록에서 완전히 사라졌는지를 직접 확인해야 합니다.
- **이해 확인 기준:** 각 리소스별로 종료 및 삭제되었다는 명확한 근거를 확인하고, 연결이 끊긴 채 방치된 미사용 가상 디스크나 고정 IP가 계정에 남아 있지 않음을 확인합니다.

## 두 과제(B1-1 포트폴리오와 B3-1 클라우드) 연결 일정

1. B1-1 미션의 웹 기초(HTML, CSS, JavaScript)를 순서대로 학습하여 내 포트폴리오 웹사이트를 먼저 만듭니다.
2. B3-1 미션의 1~4단계(네트워크 개념, 보안 개념, 비용 및 정리 계획)는 웹사이트 제작과 병행하여 틈틈이 개념을 학습합니다.
3. B1-1 웹사이트 완성 및 GitHub Pages 무료 호스팅 검증이 끝난 뒤, 준비된 웹사이트 코드를 가지고 B3-1의 실제 AWS 클라우드 배포 실습을 진행합니다.
4. AWS 배포 및 외부 접속 증빙 자료를 안전하게 확보한 뒤, AWS 자원을 깔끔하게 정리합니다. (GitHub Pages에 올린 사이트는 무료이므로 계속 유지합니다.)

보너스 선택 과제인 HTTPS 보안 접속과 Docker 컨테이너 배포는 필수 AWS 실습 과정을 완벽하게 설명하고 검증할 수 있게 된 뒤에 도전 여부를 결정합니다. 새로운 도구에 매몰되어 가장 중요한 클라우드 네트워크와 보안의 기본기를 놓치지 않도록 합니다.
