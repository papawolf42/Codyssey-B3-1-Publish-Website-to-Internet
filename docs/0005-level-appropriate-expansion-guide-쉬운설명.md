# B3-1 수준에 맞춘 확장 학습 안내 (쉬운 설명판)

[교육 목표](0004-educational-goals-and-learning-scope-쉬운설명.md) (원문: [0004-educational-goals-and-learning-scope.md](0004-educational-goals-and-learning-scope.md)) · [넓은 키워드 지도](0003-cloud-foundations-beyond-assignment-쉬운설명.md) (원문: [0003-cloud-foundations-beyond-assignment.md](0003-cloud-foundations-beyond-assignment.md)) · [필수 조건](0002-required-checklist-and-extension-rules-쉬운설명.md) (원문: [0002-required-checklist-and-extension-rules.md](0002-required-checklist-and-extension-rules.md))

> 이 문서는 고급 클라우드 기술을 무작정 더 설치하기 위한 계획서가 아닙니다. **현재 다루는 최소 인프라 구성 부품들의 가까운 비교 대상을 올바르게 이해하고, 작은 웹 요청과 오류 상황을 논리적으로 설명할 수 있도록 돕는 학습 안내서**입니다. 아래에 제시된 모든 비교 실험과 생각 질문은 이해를 돕기 위한 제안이며, 실제 실습을 완료했다는 기록이 아닙니다. 실제 AWS 자원 생성, 방화벽 접근 규칙 변경, 자원 삭제는 반드시 사용자의 명시적인 사전 승인을 받은 범위에서만 진행합니다.

---

## 1. 넓히되 과제의 본질적 난이도를 바꾸지 않는다

클라우드 공부를 처음 시작하면 새로운 서비스 이름이 쏟아져 나와 길을 잃기 쉽습니다. 이번 과제의 본질은 복잡한 인프라를 거창하게 꾸미는 데 있지 않습니다. 하나의 작은 웹 요청이 가상 네트워크와 서버를 거쳐 돌아오는 흐름을 빈틈없이 설명하고, 문제가 생겼을 때 원인을 스스로 짚어낼 수 있는 단단한 기초를 다지는 것이 핵심입니다.

## 2. 주소 · 포트 · HTTP 규약

- **출발점:** 외부 인터넷 브라우저에서 내가 띄운 가상 서버의 웹사이트에 접속하기.
- **넓힐 내용:**
  - 인터넷 주소창에 입력하는 URL의 구성 요소: 프로토콜(HTTP), 호스트(IP 주소 또는 도메인), 포트 번호(생략 시 웹 기본값 80), 요청 경로(예: `/index.html`).
  - 내 컴퓨터를 가리키는 가상 주소인 `localhost`(또는 `127.0.0.1`)와, 전 세계 인터넷에서 고유하게 통하는 공인 IP(Public IP)의 차이점.
  - `localhost`는 명령을 내린 바로 그 컴퓨터 자기 자신을 가리키므로, 내 개인 노트북에서 실행하는 `localhost`와 클라우드 가상 서버(EC2) 안에서 실행하는 `localhost`는 서로 전혀 다른 컴퓨터를 가리킵니다.
  - 웹 응답의 결과를 나타내는 HTTP 상태 코드(200 OK, 404 Not Found, 500 Internal Server Error)와, 서버에 닿지도 못한 네트워크 연결 실패(Connection Refused, Connection Timeout)의 차이를 구분합니다.
- **사수의 질문:**
  > \"가상 서버(EC2) 안에서 `curl http://localhost`로 웹페이지가 잘 떴다면, 내 개인 노트북 브라우저 주소창에서도 `http://localhost`를 치면 그 서버 웹페이지가 열릴까요?\"
- **작은 비교 실험:**
  - 똑같은 웹 요청 명령(`curl`)을 EC2 내부에서 보냈을 때와 내 노트북(외부)에서 보냈을 때, 데이터의 목적지 주소가 어떻게 다른지 종이나 화면에 그림으로 그려봅니다.
- **멈춤 기준 (여기까지면 충분):**
  - 내가 '어느 컴퓨터에서', '어느 IP 주소의', '몇 번 포트 번호로' 웹 요청을 보냈는지 말로 명확히 설명할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 네트워크 패킷(Packet)의 2진수 비트 구조, OSI 7계층 모델의 전 계층 암기.
- **더 찾아볼 검색어:** `localhost`, `URL port path`, `HTTP status`, `curl connection error`.

## 3. 가상 사설망(VPC) · 서브넷(Subnet) · CIDR 표기법

- **출발점:** AWS 클라우드에 나만의 가상 사설망(VPC)과 공개 구역(Public Subnet) 1개 만들기.
- **넓힐 내용:**
  - 독립된 가상 사설망(VPC, Virtual Private Cloud)이 갖는 사설 IP 주소 범위.
  - 그 넓은 주소 범위의 일부를 떼어내어 만든 하위 구역인 서브넷(Subnet).
  - IP 주소 대역의 크기를 간결하게 나타내는 CIDR(Classless Inter-Domain Routing, 사이더) 표기법(예: `10.0.0.0/16`).
  - 내부망에서만 쓰는 사설 IP(Private IP)와 외부 인터넷과 통신하는 공인 IP(Public IP).
  - 데이터센터 지역 거점인 리전(Region, 예: 서울 `ap-northeast-2`)과 리전 안의 개별 물리 데이터센터인 가용 영역(AZ, Availability Zone). 서브넷은 하나의 가용 영역 안에 위치하지만, VPC는 해당 리전 안의 여러 가용 영역에 걸쳐 여러 서브넷을 가질 수 있습니다.
- **사수의 질문:**
  > \"원격 관리 접속(SSH, 22번 포트) 허용 규칙에 `/32`를 적는 것과 `0.0.0.0/0`을 적는 것은 보안상 어떤 엄청난 차이가 있을까요?\"
- **작은 비교 실험:**
  - 본인의 현재 접속 IPv4 주소 딱 1개만 콕 집어 허용하는 표기(`내IP/32`)와, 전 세계 모든 IPv4 주소를 전부 허용하는 표기(`0.0.0.0/0`)의 의미 차이를 말로 설명합니다. (실제 실습 시에는 절대로 SSH를 전체 공개하지 않습니다.)
- **멈춤 기준 (여기까지면 충분):**
  - 가상망의 전체 주소 범위(VPC), 가상 서버가 위치한 구역(Subnet), 그리고 접속을 허용해 줄 출발지 IP 범위를 서로 명확히 구분할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 대규모 기업망의 복잡한 서브넷 쪼개기, 2진수 비트 연산 기반의 서브넷 계산 전면 훈련.
- **더 찾아볼 검색어:** `CIDR basics`, `private public IP`, `region vs Availability Zone`.

## 4. 경로 안내표(Route Table) · 인터넷 출입구(Internet Gateway)

- **출발점:** 인터넷 출입구(IGW)를 달고, 모든 인터넷(`0.0.0.0/0`)으로 나가는 길을 라우팅 테이블에 등록하기.
- **넓힐 내용:**
  - 경로 안내표(Route Table, 라우트 테이블)에서 데이터의 목적지(Destination)와 그 데이터를 넘겨받을 다음 전달 대상(Target).
  - 내가 만든 서브넷과 특정 라우트 테이블 간의 연결(Association).
  - 가상 사설망(VPC)과 바깥 인터넷 세상을 물리적으로 이어주는 관문인 인터넷 게이트웨이(IGW, Internet Gateway).
  - IPv4 환경에서 외부와 양방향 통신이 되려면 라우트 테이블의 길목뿐만 아니라 가상 서버 자체에 공인 IP(Public IP)가 부여되어 있어야 하고, 방화벽 규칙도 통과해야 한다는 점.
- **사수의 질문:**
  > \"집 앞마당으로 이어지는 도로(라우팅 경로)가 뚫려 있다고 해서, 우리 집 대문(방화벽)까지 자동으로 활짝 열려 있는 것일까요?\" (라우팅 경로와 방화벽 허용은 완전히 별개의 설정입니다.)
- **작은 비교 실험:**
  - 실제 자원을 만들기 전에 종이에 그림을 그려보고, '인터넷 게이트웨이만 만들어둔 상태', '경로 안내표만 적어둔 상태', '서버에 공인 IP만 있는 상태' 각각에서 외부 통신을 위해 빠진 조건이 무엇인지 찾아봅니다.
- **멈춤 기준 (여기까지면 충분):**
  - 서브넷 이름표가 'Public Subnet'이어서가 아니라, 실제로 인터넷 게이트웨이로 향하는 경로가 등록되어 있고 공인 IP가 연결되어 있기 때문에 공개 서브넷이 된다는 원리를 설명할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 비공개 서브넷용 NAT 게이트웨이, 회사 사내망과 잇는 전용선(Direct Connect)이나 VPN, 가상망 간을 잇는 VPC 피어링(Peering) 실습.
- **더 찾아볼 검색어:** `route table association`, `Internet Gateway`, `public subnet requirements`.

## 5. 보안 그룹(SG) · 권한 관리(IAM) · SSH 접속 열쇠

- **출발점:** 최소한의 권한만 부여하고 접근을 안전하게 제한하기.

| 보안 장치 | 담당하는 핵심 질문 | 다루는 영역 |
| --- | --- | --- |
| 보안 그룹 (Security Group, SG) | \"어떤 출발지 IP의 통신이, 몇 번 포트 번호로 서버에 들어올 수 있는가?\" | 가상 네트워크 수준의 가상 방화벽 (패킷 검사) |
| 권한 관리 체계 (IAM) | \"어떤 AWS 사용자나 프로그램이, 어떤 클라우드 자원을 만들고 지울 수 있는가?\" | AWS 클라우드 관리 API 제어 (관리 권한) |
| SSH 운영체제 사용자 계정과 키 | \"가상 서버 컴퓨터의 리눅스 OS에, 어떤 시스템 계정으로 로그인해 들어갈 것인가?\" | 서버 운영체제 내부의 인증 및 인가 (로그인 열쇠) |

- **넓힐 내용:**
  - 세 장치는 보안을 지키는 층위(Layer)가 완전히 다릅니다.
  - 문제 상황에 따라 의심해야 할 장치가 다릅니다:
    - AWS 콘솔에서 가상 서버(EC2) 생성을 눌렀는데 거절당함 → **IAM 권한 문제**.
    - 내 컴퓨터 터미널에서 SSH 접속 명령을 쳤는데 한참 멈춰 있다가 시간 초과(Connection timed out)가 뜸 → **보안 그룹(방화벽) 또는 네트워크 경로 문제**.
    - 서버 컴퓨터 문앞까지는 갔는데 'Permission denied (publickey)' 오류가 뜸 → **SSH 개인 키 파일이나 리눅스 사용자 이름 불일치 문제**.
- **사수의 조언:**
  - 접속이 안 된다고 해서 모든 권한을 다 주는 `AdministratorAccess`를 달아주거나, 보안 그룹에서 SSH 22번 포트를 `0.0.0.0/0`으로 활짝 열어버리는 방식으로 문제를 덮어버리지 않습니다.
- **멈춤 기준 (여기까지면 충분):**
  - 문제가 생겼을 때 세 장치 중 어느 층에서 발생한 오류인지 원인 후보를 바르게 분리할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 대기업 전사 싱글사인온(SSO), 복잡한 조직(Organizations) 단위 서비스 제어 정책(SCP) 설계.
- **더 찾아볼 검색어:** `IAM vs security group`, `SSH public key`, `least privilege`.

## 6. 가상 서버(EC2) · 가상 디스크(EBS) · 백그라운드 서비스(Service)

- **출발점:** 마이크로급 가상 서버 1대를 띄우고 그 안에 Nginx 웹 서버 설치하기.
- **넓힐 내용:**
  - EC2(Elastic Compute Cloud)는 중앙처리장치(CPU)와 메모리를 가진 가상 컴퓨터 본체입니다.
  - EBS(Elastic Block Store)는 가상 컴퓨터 본체에 연결된 외장 가상 하드디스크입니다.
  - Nginx(엔진엑스)는 그 컴퓨터의 운영체제(OS) 위에서 돌아가는 백그라운드 응용 프로그램(서비스)입니다.
  - 가상 컴퓨터 본체(EC2)가 '실행 중(Running)' 상태라고 해서, 그 안의 Nginx 웹 서버까지 켜져 있는 것은 아닙니다.
  - Nginx 웹 서버가 켜져 있더라도, 내가 원하는 포트(80번)에서 귀를 기울이고(Listening) 있지 않거나 보여줄 파일 경로가 잘못 지정되어 있으면 웹페이지가 뜨지 않습니다.
- **작은 비교 실험:**
  - AWS 콘솔에서 보이는 'EC2 인스턴스 실행 상태', 서버 터미널에서 리눅스 명령(`systemctl status nginx`)으로 확인하는 '웹 서버 서비스 상태', 그리고 터미널에서 직접 웹 요청을 보내보는 '로컬 HTTP 응답 확인'을 서로 다른 단계로 나누어 점검합니다.
- **멈춤 기준 (여기까지면 충분):**
  - 프로그램 설치, 백그라운드 실행, 포트 대기, 정상 응답의 차이를 구분하고, 문제가 있을 때 리눅스 서비스 상태와 로그 파일을 찾아볼 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 리눅스 커널 파라미터 튜닝, 서버 이미지(AMI) 자동 생성 파이프라인, 여러 대의 서버 복제 운영.
- **더 찾아볼 검색어:** `process vs service`, `systemctl status`, `Nginx document root`, `EBS volume`.

## 7. 정적 웹 파일 배포와 브라우저 동작

- **출발점:** Nginx 웹 서버를 통해 내가 만든 웹사이트(B1-1 포트폴리오) 파일 보여주기.
- **넓힐 내용:**
  - 브라우저가 웹사이트를 보여줄 때 한 번의 요청으로 끝나는 것이 아닙니다. HTML 문서를 먼저 가져온 뒤, 그 문서 안에 적힌 스타일시트(CSS), 자바스크립트(JS), 이미지 파일들을 브라우저가 각각 별도의 HTTP 요청으로 서버에 다시 요청하여 가져옵니다.
  - Nginx 웹 서버가 정적 파일들을 브라우저로 건네주는 것과, 브라우저가 화면을 띄운 뒤 자바스크립트를 실행해 GitHub API 같은 외부 서버를 호출하는 것은 완전히 다른 단계입니다.
  - 리눅스 운영체제는 윈도우와 달리 파일 이름의 대소문자를 엄격하게 구분(`Index.html`과 `index.html`은 다른 파일)하며, 웹 서버 프로세스가 해당 파일을 읽을 수 있는 파일 권한(Permission)도 필요합니다.
- **사수의 질문:**
  > \"브라우저가 HTML 파일은 200번으로 잘 받아왔는데 화면 스타일이 깨지거나 카드가 안 보인다면, 가상 사설망(VPC) 네트워크부터 처음부터 다시 만들어야 할까요?\" (그렇지 않습니다. 브라우저의 개발자 도구를 먼저 확인해야 합니다.)
- **작은 비교 실험:**
  - 브라우저 개발자 도구의 '네트워크(Network)' 탭을 열고, HTML, CSS, JS, 이미지, 외부 API 요청들이 각각 성공했는지 실패했는지 개별적으로 분리하여 관찰합니다.
- **멈춤 기준 (여기까지면 충분):**
  - 서버가 웹 파일을 제대로 건네주지 못하는 문제(서버 인프라 문제)와, 파일은 잘 왔는데 브라우저 내부에서 자바스크립트나 경로가 어긋난 문제(프론트엔드 문제)를 구분할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 고성능 리버스 프록시 캐싱 설정, 로드밸런서 연동, 프론트엔드와 백엔드 API 서버의 완전 분리 구축.
- **더 찾아볼 검색어:** `static web server`, `case-sensitive paths`, `browser Network panel`.

## 8. 장애 원인 분석 (트러블슈팅)

- **출발점:** 공식 제출 보고서 양식: **증상 → 가설 → 검증 → 조치 → 결과 → 재발 방지**.
- **넓힐 내용:**
  - 눈으로 직접 관찰한 사실(팩트)과 나의 주관적인 짐작(추측)을 엄격하게 분리합니다.
  - 문제를 해결할 때는 방화벽, 파일 경로, 웹 서버 설정을 한꺼번에 바꾸지 않고, **한 번에 딱 하나의 조건만 변경한 뒤 결과를 다시 검증**합니다.
  - 로그 파일에 아무런 에러 기록이 찍히지 않는 것 자체도 중요한 단서입니다. (예: 요청이 아예 웹 서버까지 닿지도 못하고 앞단 방화벽에서 막혔음을 의미할 수 있습니다.)
- **사수의 질문:**
  > \"접속이 안 될 때 방화벽 규칙, 파일 경로, Nginx 설정을 한 번에 다 고쳐서 마침내 접속이 되었다면, 과연 무엇이 진짜 원인이었는지 알 수 있을까요?\"
- **작은 비교 실험:**
  - '외부 인터넷 접속 실패 / 서버 내부 접속 성공'인 상황과 '외부 인터넷 접속 실패 / 서버 내부 접속 실패'인 상황의 점검 순서를 다르게 계획해 봅니다.
  - 만약 실습 중 자연스러운 오류가 발생하지 않았다면, 제출용 보고서를 위해 가짜 장애를 실제 일어난 것처럼 꾸며내지 않습니다. 학습용으로 의도적인 실험을 할 때는 사전에 복구 계획을 세우고 통제된 상태에서 1건만 수행합니다.
- **멈춤 기준 (여기까지면 충분):**
  - 단 1건의 접속 오류라도, 어떤 구체적 증거를 보고 원인을 좁혔으며 어떤 조치로 해결했는지 전후 결과를 비교하여 설명할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 대규모 중앙 집중식 로그 분석 플랫폼, 분산 추적(Distributed Tracing) 시스템 구축.
- **더 찾아볼 검색어:** `troubleshooting hypothesis`, `Nginx access error log`, `connection timeout`.

## 9. 자원 정리와 클라우드 비용 통제

- **출발점:** 실습이 끝나면 요금이 나오지 않도록 클라우드 리소스 모두 삭제하기.
- **넓힐 내용:**
  - 가상 컴퓨터 일시 중지(Stop, 가상 하드디스크 보관 요금 계속 발생)와 완전 삭제(Terminate)의 차이점.
  - 서버를 지워도 계정에 덩그러니 남아 요금을 유발할 수 있는 고아 자원들: 미사용 외장 디스크(EBS 볼륨), 연결 해제된 고정 IP(Elastic IP), 보관 중인 백업 이미지(AMI/스냅샷).
  - 클라우드 자원의 상하 의존 관계: 서버(EC2)가 살아 있는 동안에는 서브넷이나 가상 사설망(VPC)을 지울 수 없고, 인터넷 출입구(IGW)의 연결을 끊기 전에는 VPC를 삭제할 수 없습니다.
  - 비용, 권한, 삭제 방법은 자원을 만들기 전에 미리 계획해야 실수를 막을 수 있습니다.
- **작은 비교 실험:**
  - 생성할 자원 목록 옆에 삭제를 확인하는 구체적인 점검 방법을 1:1로 함께 적어둡니다. (예: EC2 콘솔에서 종료 상태 확인과, EBS 볼륨 콘솔에서 볼륨 목록이 비어 있음을 각각 별개로 확인.)
  - 내가 만든 리소스 ID와 리전을 정확히 확인하여, 다른 실습이나 다른 사람의 자원을 실수로 지우지 않도록 주의합니다.
- **멈춤 기준 (여기까지면 충분):**
  - 자원의 상태를 '미생성', '생성됨', '종료됨', '완전 삭제됨'으로 명확한 화면 근거를 통해 구분하고 남은 유료 자원이 없음을 확인할 수 있으면 충분합니다.
- **미룰 것 (지금은 불필요):**
  - 기업용 장기 약정 할인(Savings Plans, Reserved Instance), 인프라 자동 폐기 파이프라인.
- **더 찾아볼 검색어:** `stop vs terminate`, `orphaned EBS`, `Elastic IP release`, `resource dependencies`.

## 10. 선택 과제(HTTPS 암호화와 Docker)는 언제 도전하는가?

기본 필수 요청 경로를 막힘없이 설명할 수 있고, 서버 내부와 외부 접속 검증(A 또는 B)을 완벽히 마친 뒤에 선택 과제 도전 여부를 결정합니다.

- **HTTPS 암호화 웹 통신 (선택 과제 1):**
  - 내 도메인 연결, 무료 SSL/TLS 인증서(Let's Encrypt 등) 발급, 암호화 통신(443번 포트), 인증서 자동 갱신 원리를 작은 단위로 배웁니다.
- **Docker 컨테이너 가상화 배포 (선택 과제 2):**
  - 프로그램 실행 환경을 담은 도커 이미지, 격리되어 실행되는 컨테이너, 서버 외부 포트와 컨테이너 내부 포트를 이어주는 포트 매핑(Port Mapping), 그리고 컨테이너 안에서 바라보는 `localhost`와 가상 서버 본체에서 바라보는 `localhost`의 차이를 비교합니다.

새로운 도구를 추가한다고 해서 보안 그룹, IAM 권한, 네트워크 경로 설정, 자원 정리 책임이 사라지는 것이 아닙니다. 선택 과제를 진행하더라도 기본 필수 조건인 HTTP(80) 및 SSH(22) 포트 보안 규칙을 임의로 생략하거나 왜곡해서는 안 됩니다.

- **멈춤 기준:** 새로 추가한 도구가 기존 통신 경로의 어느 위치에 끼어들어가며, 어떤 문제를 해결해 주는지 설명할 수 있으면 충분합니다.

## 11. 사수가 추천하는 가장 건강한 학습 리듬

1. **요청 흐름도를 먼저 그린다:** 실제 클라우드 자원을 단 하나도 만들지 않은 백지 상태에서 데이터 이동 경로를 그려봅니다.
2. **기본 개념을 짧게 확인한다:** 네트워크, 보안 권한, 비용 요인을 머릿속으로 먼저 정리합니다.
3. **승인 후 최소 구성을 한 단계씩 만든다:** 사용자의 확인을 받고 가상망, 서버를 하나씩 천천히 만듭니다.
4. **내부 응답과 외부 응답을 따로 확인한다:** 서버 내부(`localhost`) 성공과 바깥 인터넷 성공을 분리하여 검증합니다.
5. **관찰된 오류를 가설을 세워 하나씩 분석한다:** 한 번에 하나씩만 수정하며 원인을 밝혀냅니다.
6. **실제 구성, 검증 화면, 오류 분석 근거를 문서에 기록한다:** 나중에 다시 재현할 수 있도록 정리합니다.
7. **실습에 사용한 모든 자원을 깔끔하게 정리한다:** 목록을 대조하며 남은 자원이 없는지 확인합니다.

사수의 궁극적인 목표는 코드를 대신 빠르게 짜주거나 콘솔을 대신 클릭해 주는 것이 아닙니다. 학습자가 **\"이 설정이 빠지면 통신 경로의 어디에서 요청이 멈출까?\"**를 스스로 머릿속으로 그려보고 예상할 수 있도록 돕는 것입니다.
