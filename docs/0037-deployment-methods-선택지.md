# 같은 AWS 과제를 완성하는 다양한 방법

[과제 명세](0051-requirements-and-review-reference.md) · [현재 아키텍처](0035-architecture-diagram-설명.md) · [학습 정리](0036-learning-notes.md)

## 핵심: 도구와 아키텍처는 다르다

현재는 AWS 콘솔로 VPC·Subnet·IGW·Route Table·Security Group·EC2를 만들고, SSH에서 Nginx를 설치했다. 같은 아키텍처를 다른 도구로 구성할 수 있다. IaC는 특정 제품명이 아니라 **Infrastructure as Code, 인프라를 코드로 정의하고 관리하는 방식**이다.

아래 방법은 모두 이번에 실행한 것이 아니라 비교를 위한 선택지다. 이 문서를 작성하면서 AWS 리소스를 추가·변경·삭제하지 않았다.

## 1. 인프라를 만드는 방법

### AWS 콘솔

브라우저에서 설정하고 생성 버튼을 누른다. 지금 사용한 방식이다. 초보자가 자원과 연결 관계를 관찰하기 좋지만, 반복 구축과 변경 비교를 수작업으로 관리해야 한다.

### AWS CLI / SDK

AWS CLI는 명령으로, SDK는 Python의 boto3 같은 프로그래밍 라이브러리로 AWS API를 호출한다. 생성·조회·삭제 작업을 스크립트로 묶을 수 있다. 단순 명령 모음에서는 실행 순서, 생성된 ID, 재실행 시 중복 처리, 중간 실패 복구를 직접 설계해야 한다. CLI를 사용한다고 자동으로 선언형 IaC가 되는 것은 아니다.

### Terraform / OpenTofu

원하는 인프라를 구성 파일에 선언한다. state로 코드와 실제 자원을 대응시키고, plan으로 변경 예정 내용을 검토한 뒤 apply로 반영한다. 여러 클라우드를 지원하지만 AWS 자원 정의 자체가 다른 클라우드에 그대로 호환되는 것은 아니다.

### AWS CloudFormation

AWS의 IaC 서비스다. YAML/JSON 템플릿으로 자원과 연결 관계를 정의하고 스택 단위로 관리한다. AWS에 집중해서 학습하려는 경우 선택할 수 있다. 생성·업데이트·삭제 실패나 롤백도 실제 상태 확인이 필요하다.

### AWS CDK / Pulumi

일반 프로그래밍 언어로 인프라를 표현할 수 있다. AWS CDK는 코드를 CloudFormation 템플릿으로 합성해 배포한다. Pulumi는 별도의 엔진과 상태 관리 체계를 사용하므로 CDK와 같은 도구는 아니다. 재사용과 조건·반복 표현에 유용하지만 언어와 도구 체계를 함께 배워야 한다.

## 2. 서버 안을 설정하는 방법

인프라 생성과 OS 설정은 서로 다른 단계다. 조합해서 사용한다.

- **수동 SSH**: 로그인한 뒤 패키지 설치, 웹 파일 복사, 서비스 시작을 직접 수행한다. 현재 사용한 방식이다.
- **EC2 User Data / cloud-init**: 새 서버의 초기 부팅 시 Nginx 설치·웹 파일 준비·서비스 시작 등을 자동화한다. 기본 구성에서 매 재부팅마다 모든 스크립트가 다시 실행되는 것으로 가정하면 안 된다. 완료 여부와 로그도 확인해야 한다.
- **Ansible**: 실행 중인 서버의 패키지·파일·서비스 설정을 플레이북으로 관리한다. 같은 설정을 여러 번 적용해도 원하는 상태를 유지하도록 작성할 수 있다. 서버 생성 자체와 역할을 구분한다.
- **Packer + AMI**: Nginx와 설정을 미리 준비한 서버 이미지를 만들어 배포한다. 반복 생성은 빨라지지만 이미지 빌드와 패치 관리가 추가된다.

## 3. 웹 서비스를 배포하는 방법

- **호스트에 Nginx 직접 설치**: 지금처럼 EC2 OS에 웹 서버를 설치한다.
- **EC2 안에서 Docker 실행**: 웹 서버와 사이트를 컨테이너 이미지로 묶는다. 이번 과제에서 명시한 보너스 선택지다. VPC·EC2·보안 설정은 여전히 필요하다.
- **CI/CD 추가**: GitHub Actions 같은 도구로 코드 변경 후 테스트·배포를 자동 실행한다. IaC나 Docker를 대체하는 것이 아니라, 그 도구들을 실행하는 자동화 경로다. 장기 액세스 키를 저장하기보다 OIDC를 이용한 제한된 AWS 역할 접근 등을 검토할 수 있다. 별도의 신뢰 정책·최소권한 설계가 필요하다.

예를 들어 `Terraform + User Data + Nginx`나 `CloudFormation + Ansible + Docker`처럼 서로 조합할 수 있다. 도구가 많을수록 무조건 더 좋은 것은 아니다.

## 4. 이번 과제에서 바뀌지 않는 조건

명세에 특정 IaC 제품 사용을 강제하는 조항은 없다. 하지만 도구를 바꿔도 다음 조건과 제출 증빙을 유지해야 한다.

- 서울 리전의 VPC·Public Subnet·IGW·기본 경로·EC2·Security Group.
- SSH 접속 가능, SSH 소스 제한, HTTP 외부 접속, localhost HTTP 200, 아웃바운드 통신 검증.
- 별도 최소권한 IAM 주체와 명세가 요구하는 콘솔 접근.
- 다이어그램, 외부 접속 증빙, 트러블슈팅 보고서, 실제 리소스 정리와 체크리스트.

S3 정적 호스팅·Amplify·Lightsail·서버리스 등으로 웹사이트를 공개하는 방법도 있지만, 이번 명세의 VPC/EC2/SSH 구성을 그대로 대체하면 필수 조건을 충족하지 못할 수 있다. 평가자에게 별도 대체 승인을 받은 것으로 간주하지 않는다.

## 5. 지금 단계의 추천 순서

1. 현재 콘솔 방식의 결과와 정리 증빙을 먼저 마무리한다.
2. 현재 구성을 바꾸지 않고 Terraform 또는 CloudFormation 코드로 표현해 본다.
3. 실제 재구축은 별도 승인과 비용 검토 후 진행한다. User Data로 Nginx 초기 설정을 자동화하면 인프라와 서버 설정의 차이를 배우기 좋다.
4. 이후에 Docker나 CI/CD를 하나씩 추가한다.

## 6. 기존 자원에 적용할 때의 주의점

- 기존 자원과 같은 이름을 코드에 쓴다고 자동으로 관리 대상이 되지 않는다. Terraform의 import 등 기존 자원 편입 절차를 검토해야 한다.
- plan에 교체나 삭제가 포함될 수 있다. apply나 destroy를 가볍게 실행하지 않는다.
- destroy나 스택 삭제만으로 계정 전체 자원과 모든 비용이 사라진다고 보장할 수 없다. 관리 대상·보존 정책·남은 자원을 실제로 확인한다.
- 현재 IAM 권한이 새 도구의 모든 작업을 허용한다고 가정하지 않는다. CloudFormation 서비스 작업이나 추가 조회 권한 등이 필요하면 범위를 먼저 검토한다. 이를 이유로 AdministratorAccess를 붙이지 않는다.
- IaC state, 변수 파일, User Data에도 민감 정보가 들어갈 수 있다. 개인키·암호·토큰·state를 공개 Git에 올리지 않는다.
