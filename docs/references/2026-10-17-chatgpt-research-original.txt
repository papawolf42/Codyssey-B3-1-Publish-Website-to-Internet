# AWS 신규 계정의 서울 리전·IAM 콘솔 접근 독립 팩트체크

조사 기준: 2026년 10월 17일 · AWS 공식 문서 우선

## 1. 결론 요약

이전 AI의 결론은 중요한 부분에서는 AWS 공식 문서와 일치하지만, 모든 해결 가능성을 배제하기에는 설명이 부족했습니다.

AWS 문서를 확인한 결과, 실제로 2026년에는 기존 AWS 가입 방식과 다른 \*\*프로젝트 기반 신규 AWS 경험(Sign up for AWS — new)\*\*이 존재합니다. 이 방식에서는 리전과 IAM 콘솔 접근에 기존 계정과 다른 제한이 적용됩니다.

현재 알려주신 화면은 이 신규 경험과 매우 강하게 일치합니다.

### 현재까지 확인된 핵심 사실

1. 한국의 모든 AWS 계정이 시드니에 고정되는 것은 아닙니다. 신규 프로젝트 기반 경험에 한해, 한국 연락처로 생성된 프로젝트의 리소스 리전이 시드니로 지정된다는 AWS 공식 문서가 있습니다.
2. 서울(`ap-northeast-2`)은 일반 AWS 계정에서 기본 활성화된 리전이 맞습니다. 그러나 기본 활성화 상태가 프로젝트에 적용된 Organizations 정책이나 신규 경험의 제한을 무력화하지는 않습니다.
3. 신규 AWS 경험에서는 IAM 사용자를 생성할 수 있어도 콘솔 로그인용 IAM 사용자를 만드는 기능은 공식적으로 제한됩니다. 단순히 화면에서 암호 설정 항목을 못 찾은 문제가 아닐 가능성이 높습니다.
4. 프로젝트와 AWS Builder ID는 AWS 계정의 존재를 부정하지 않습니다. 신규 프로젝트도 내부적으로 실제 AWS 계정을 포함합니다.
5. 유료 플랜 업그레이드와 고급 기능 활성화는 별도 작업입니다. 둘을 동일한 것으로 취급하거나 유료 전환만 하면 모든 문제가 해결된다고 가정해서는 안 됩니다.

주요 공식 근거는 AWS의 [AWS Regions for your projects](https://docs.aws.amazon.com/accounts/latest/reference/project-regions.html?utm_source=chatgpt.com), [Create an IAM user](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_users_create.html?utm_source=chatgpt.com) 및 [Sign up for AWS (new)](https://docs.aws.amazon.com/accounts/latest/reference/sign-in-new.html?utm_source=chatgpt.com)입니다.&#x20;

## 4. 서울 리전은 왜 제한되는가?

AWS는 신규 경험의 프로젝트 리전 배정을 공식적으로 다음과 같이 설명합니다.

| 가입 연락처 국가 그룹    | 신규 프로젝트 리전                              |
| --------------- | --------------------------------------- |
| 미주              | US East (Ohio), `us-east-2`             |
| 유럽·중동·아프리카 등    | Europe (Stockholm), `eu-north-1`        |
| 한국을 포함한 아시아·태평양 | Asia Pacific (Sydney), `ap-southeast-2` |

원문: “Any Regional resources that you create will be hosted in that Region.”

이 표는 프로젝트 리전 정책이지 모든 AWS 계정의 리전 정책이 아닙니다. AWS는 연락처를 변경해도 기존 프로젝트 리전이 바뀌지 않는다고 명시합니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.aws.amazon.com\&sz=32)

AWS Account Management



### 더 결정적인 근거: 실제 AWS 관리형 SCP

AWS의 [Managed policies for your organization](https://docs.aws.amazon.com/accounts/latest/reference/scps-and-rcps-for-projects.html?utm_source=chatgpt.com) 문서에는 신규 프로젝트에 적용하는 서비스 제어 정책(SCP)이 공개되어 있습니다.

그중 `RegionFloor`라는 정책 문장은 대략 다음 구조입니다.

```
{
  "Sid": "RegionFloor",
  "Effect": "Deny",
  "NotAction": ["일부 예외 작업"],
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": [
        "unspecified",
        "us-east-1",
        "selected-region",
        "us-west-2"
      ]
    }
  }
}
```

공식 문서의 RegionFloor 핵심 구조를 발췌·축약한 것입니다. 실제 정책에는 예외 작업 목록과 다른 문장들이 추가되어 있습니다.

`selected-region`은 프로젝트에 지정된 리전을 나타냅니다. 시드니로 지정된 프로젝트라면 서울에서 실행하는 일반적인 EC2/VPC 작업은 이 정책의 제한 대상이 됩니다. 일부 다른 리전에서 특정 글로벌·분할 서비스 API를 호출할 수 있다고 해서 그 리전에서 EC2를 생성할 수 있는 것은 아닙니다.

AWS 원문에서는 `RegionFloor`와 `aws:RequestedRegion`을 직접 확인할 수 있습니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.aws.amazon.com\&sz=32)

AWS Account Management



여기서 중요한 점은 AdministratorAccess가 연결된 역할로 실행하더라도 SCP의 명시적 Deny를 이길 수 없다는 것입니다. Terraform이나 CLI를 사용해도 마찬가지입니다.

### 네 가지 리전 개념의 차이

| 개념         | 의미                                       |
| ---------- | ---------------------------------------- |
| 콘솔 표시 리전   | 지금 보고 있는 콘솔 페이지의 지역                      |
| 기본 활성화 리전  | AWS 계정의 별도 opt-in 없이 사용할 수 있도록 기본 설정된 리전 |
| 프로젝트 선택 리전 | 신규 경험이 리소스 배치 대상으로 지정한 리전                |
| SCP 허용 리전  | 실제 AWS 요청이 조직 정책에 의해 허용되는 리전             |

서울이 기본 활성화 리전이라는 AWS 공식 문서는 맞습니다. 그러나 프로젝트 제한을 판단하는 데는 별도로 `RegionFloor`를 확인해야 합니다.&#x20;

## 5. 비용 없이 현재 환경을 확인하는 절차

가장 안전한 순서는 설정 조회 → 현재 주체 조회 → 읽기 전용 리전 요청입니다.

1단계 — AWS Settings에서 프로젝트 리전 확인

[AWS Settings](https://settings.aws.com?utm_source=chatgpt.com) → `Project` 또는 `프로젝트` → 해당 프로젝트 → `Overview` → `Additional Info` → `Region`

여기서 `ap-southeast-2`인지 확인하세요. 함께 표시되는 12자리 AWS 계정 ID도 기록하세요. 이것은 서비스 URL을 보는 것보다 신뢰할 수 있는 확인 방법입니다.

2단계 — 이미 설정된 AWS CLI 자격 증명으로 현재 주체 확인

```
aws sts get-caller-identity
```

응답의 `Account`와 `Arn`을 확인합니다. `Arn`이 `assumed-role/...` 형식이면 실제로 맡은 역할을 알 수 있습니다.

`AccountFullAccessRole`이 역할 목록에 존재한다고 해서 이 명령의 응답에도 등장하는 것은 아닙니다. 새로운 액세스 키를 만들 필요 없이 기존 CLI 인증이 있을 때만 실행하세요.

3단계 — 서울에서 읽기 전용 요청 테스트

```
aws ec2 describe-vpcs --region ap-northeast-2
```

서울 리전의 VPC 목록을 읽는 요청입니다. VPC나 인스턴스를 생성하지 않습니다.

`AccessDenied`가 나오고 메시지가 SCP의 명시적 거부를 가리키면 실제 적용 제한의 강한 증거입니다. 성공적으로 목록을 반환하면 최소한 이 읽기 작업은 허용된 것입니다. 읽기가 성공했다고 쓰기 작업까지 허용된다는 뜻은 아닙니다.

실행 결과를 판단할 때는 다음처럼 구분해야 합니다.

| 결과                                          | 알 수 있는 것                       |
| ------------------------------------------- | ------------------------------ |
| `explicit deny in a service control policy` | 조직 정책이 해당 요청을 거부               |
| `UnauthorizedOperation`                     | 권한 부족. IAM 정책·SCP 등을 추가 조사해야 함 |
| 빈 `Vpcs: []`가 성공적으로 반환                      | 읽기 권한은 있음. VPC 생성 가능 여부는 미확인   |
| `InvalidClientTokenId` 등의 인증 오류             | 자격 증명 문제. 리전 제한을 판정할 수 없음      |

읽기 요청이 거부되어도 해당 프로젝트의 공개 정책이 자동으로 잘못된 것은 아니며, 성공한 경우에도 전체 과제 가능성을 증명하지는 않습니다. `DescribeRegions`의 리전 목록에 서울이 나타나는 것만으로도 판단하지 마세요.

## 6. IAM 콘솔 접근: 현재 계정에서 가능한 것과 불가능한 것

### 6-1. IAM 사용자 암호 문제는 실제 기능 제한이다

AWS의 IAM 사용자 생성 문서에는 다음 문장이 있습니다.

> “In our new experience, you cannot create IAM users with console access.”

현재 신규 경험을 사용하고 있다면 IAM 사용자에게 직접 정책을 연결할 수 있어도, 그 사용자에게 콘솔 로그인용 암호를 설정할 수 없다는 설명입니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.aws.amazon.com\&sz=32)

AWS Identity and Access Management



일반적인 AWS 계정에서는 `iam:CreateLoginProfile`이나 IAM 콘솔의 Security credentials 기능으로 로그인 암호를 만들 수 있습니다. 하지만 신규 경험에서는 IAM 콘솔 접근 자체가 지원되지 않는다는 더 구체적인 제한이 있으므로, API를 사용해 암호를 강제로 생성하는 방법은 공식 해결책으로 권하지 않습니다. 실제 API 호출을 검증한 것도 아닙니다.

### 6-2. AWS 로그인 문서에는 정말 모순이 있다

지적하신 문서를 대조하니 같은 페이지에 다음 두 설명이 함께 있습니다.

| 위치           | AWS 문서 내용                                                                                     |
| ------------ | --------------------------------------------------------------------------------------------- |
| 도입부          | “This sign-in method is only supported for accounts created with Sign up for AWS (advanced).” |
| 신규 경험 로그인 절차 | “If you signed up for AWS using our new AWS experience, you can sign in ... as an IAM user.”  |

출처: [Sign in to the AWS Management Console as an IAM user](https://docs.aws.amazon.com/signin/latest/userguide/introduction-to-iam-user-sign-in-tutorial.html?utm_source=chatgpt.com)&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.aws.amazon.com\&sz=32)

AWS Sign-In



이것은 실제로 문서 내 설명 범위가 충돌하는 사례입니다.

가능한 해석은 신규 경험의 로그인 화면이 기존 IAM 사용자 로그인 경로도 제공한다는 것이지만, 그 로그인 경로의 존재가 신규 프로젝트 계정에서 IAM 사용자 암호를 발급할 수 있다는 증거는 아닙니다.

현재 증거의 우선순위는 다음과 같습니다.

- 계정 유형과 권한 정책을 명시하는 `Compare sign-up options`
- 신규 경험에 직접 적용하는 `Create an IAM user`의 제한 문구
- 일반 로그인 화면의 사용 절차

따라서 로그인 문서의 충돌은 인정하되, 그것만으로 공식 IAM 사용자 생성 제한이 해제되었다고 결론 내릴 수 없습니다.

### 6-3. Team 초대는 콘솔 접근은 되지만 최소권한은 아니다

AWS의 공식 Team 문서에는 다음과 같이 쓰여 있습니다.

> “Both you and the team member have admin access to the project.”

초대된 팀원은 프로젝트 안에서 AWS 서비스를 생성·변경·삭제할 수 있습니다. 청구 방법 변경이나 팀원 초대처럼 소유자에게만 허용되는 작업은 제한됩니다.

즉, 팀원은 모든 계정 관리 작업을 할 수 있는 소유자는 아니지만, EC2/VPC/Security Group으로 작업 범위를 제한한 실습 주체도 아닙니다.

따라서 Team 초대를 과제의 최소권한 조건에 대한 해결책으로 제시하면 안 됩니다.&#x20;

### 6-4. 기존 `AccountFullAccessRole`은 무엇을 의미하는가?

기존 역할의 신뢰 정책에 있는

```
{
  "Principal": {
    "Service": "account-access.amazonaws.com"
  },
  "Action": [
    "sts:AssumeRole",
    "sts:SetContext"
  ]
}
```

구조는 AWS의 Account access manager가 역할 세션을 생성할 수 있도록 하는 신뢰 정책과 일치합니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.aws.amazon.com\&sz=32)

AWS Identity and Access Management



하지만 이것으로 다음을 증명하지는 못합니다.

- 지금 로그인한 사람이 해당 역할을 사용한다는 것
- 아무 IAM 사용자나 해당 역할로 전환할 수 있다는 것
- 새 역할을 생성하면 자동으로 팀원에게 배정된다는 것

또한 역할에 연결된 `AdministratorAccess`는 그 역할을 성공적으로 맡았을 때 무엇을 할 수 있는지에 관한 권한입니다. 신뢰 정책은 누가 어떤 방식으로 그 역할을 맡을 수 있는지에 관한 규칙입니다.

둘은 서로 다릅니다. 기존 역할은 유지하고, 실습용 역할을 별도로 생성해야 합니다.

### ④번: 별도 최소권한 콘솔 접근의 구체적인 구성

고급 기능 활성화 이후의 공식 Account access manager 방식을 기준으로 하면 다음 절차입니다.

A. 실습용 역할 생성

프로젝트의 실제 AWS 계정 IAM → Roles → Create role에서 `EC2VpcLabRole` 같은 별도 역할을 만듭니다.

AWS의 [Create a role using custom trust policies](https://docs.aws.amazon.com/IAM/latest/UserGuide/aam-prepare-roles.html?utm_source=chatgpt.com)를 따라 Account access manager용 신뢰 정책을 구성합니다. 기존 `AccountFullAccessRole`은 건드리지 않습니다.

B. 역할에 허용 권한 부여

EC2/VPC, Subnet, Internet Gateway, Route Table, Security Group, Key Pair 및 인스턴스 생성·삭제에 필요한 작업만 포함하는 고객 관리형 정책을 연결합니다.

C. 실습자의 신원 분리

IAM Identity Center의 별도 사용자 또는 전용 그룹을 만듭니다. 기존 AWS Builder ID를 사용하는 경우에도 실습자의 접근 배정이 기존 관리자 배정과 분리되어 있어야 합니다.

D. 사용자와 역할 배정

조직의 관리 계정 또는 위임 관리자 계정에서 IAM → Account access manager → `Assign new access`로 들어갑니다.

여기서 `실습자 사용자 ID / 프로젝트 AWS 계정 ID / EC2VpcLabRole ARN`을 연결합니다.

E. 독립 로그인 테스트

실습자는 AWS access portal을 통해 해당 계정의 역할로 콘솔에 들어갑니다. 생성·조회 권한이 작동하는지 확인하고, IAM 사용자 관리나 다른 관리 작업이 거부되는지도 검증합니다.

Account access manager 공식 문서는 배정 단위를 사용자 또는 그룹, 계정, 역할 ARN의 3원 관계라고 정의합니다. [Assign and remove access](https://docs.aws.amazon.com/IAM/latest/UserGuide/aam-assign-remove-access.html?utm_source=chatgpt.com).&#x20;

### 실습용 권한 정책 예시

아래 JSON은 서울 리전으로 작업 범위를 제한하는 출발점입니다. `AdministratorAccess`가 아니며, IAM 관리자 권한이나 `iam:PassRole`을 포함하지 않습니다. 실제 콘솔 작업에 필요한 세부 API와 리소스 ARN·태그 조건을 검토해 더 좁혀야 하므로 최종적으로 검증된 최소권한 정책은 아닙니다.

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadEC2InSeoul",
      "Effect": "Allow",
      "Action": [
        "ec2:Describe*"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "ap-northeast-2"
        }
      }
    },
    {
      "Sid": "ManageEC2VpcLabInSeoul",
      "Effect": "Allow",
      "Action": [
        "ec2:CreateVpc",
        "ec2:DeleteVpc",
        "ec2:ModifyVpcAttribute",
        "ec2:CreateSubnet",
        "ec2:ModifySubnetAttribute",
        "ec2:DeleteSubnet",
        "ec2:CreateInternetGateway",
        "ec2:AttachInternetGateway",
        "ec2:DetachInternetGateway",
        "ec2:DeleteInternetGateway",
        "ec2:CreateRouteTable",
        "ec2:DeleteRouteTable",
        "ec2:AssociateRouteTable",
        "ec2:DisassociateRouteTable",
        "ec2:CreateRoute",
        "ec2:DeleteRoute",
        "ec2:CreateSecurityGroup",
        "ec2:DeleteSecurityGroup",
        "ec2:AuthorizeSecurityGroupIngress",
        "ec2:RevokeSecurityGroupIngress",
        "ec2:CreateKeyPair",
        "ec2:DeleteKeyPair",
        "ec2:RunInstances",
        "ec2:TerminateInstances",
        "ec2:StartInstances",
        "ec2:StopInstances",
        "ec2:CreateTags",
        "ec2:DeleteTags"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "ap-northeast-2"
        }
      }
    }
  ]
}
```

`Resource: "*"`를 사용하므로 이 예시는 작업 종류와 리전 수준의 제한이지 완성된 리소스별 최소권한은 아닙니다. 과제에서 최소권한의 엄밀성을 요구한다면 사용할 리소스 ARN·태그·인스턴스 유형 등의 조건을 추가하고 IAM Policy Simulator 및 실제 테스트로 검증해야 합니다.

또한 역할의 세션에 실제로 이 정책이 적용됐는지 확인해야 합니다. 기존 관리자 권한으로 로그인한 채 역할만 생성하는 것으로는 별도 실습 주체 사용이 증명되지 않습니다.

- 기존 프로젝트 계정은 조직의 멤버 계정으로 유지되며, 관리 계정에서 조직 정책과 사람 접근 배정을 관리합니다.
- 기존 팀원의 접근이 자동으로 최소권한으로 축소되는 것은 아닙니다.
- 고급 기능 활성화 후 그 조직에서는 예전 방식으로 프로젝트를 계속 추가할 수 없으며, 새 조직 멤버 계정 생성 방식을 사용합니다.
- 기존 프로젝트의 리전 제한을 풀기 위해 `RegionFloor` 등을 직접 검토해야 합니다.
- 고급 기능 활성화는 되돌릴 수 없고 기존 프로젝트의 강제 지출 한도는 사라집니다.

이 조건을 수용할 수 있을 때에만 선택해야 합니다.

### 선택지 4 — 새로운 advanced 계정

새로 시작하는 계정이라면 처음부터 서울 리전을 사용하고 IAM 사용자 또는 IAM Identity Center 역할을 구성하는 것이 간단할 수 있습니다.

그러나 지금은 기존 프로젝트에 이미 100달러 크레딧이 있습니다. AWS는 서로 다른 계정 사이의 Free Tier 크레딧 이전을 지원하지 않습니다. 또한 무료 플랜·크레딧은 신규 AWS 고객을 대상으로 하므로, 이미 AWS 계정을 소유한 사람이 새 계정을 만든다고 다시 크레딧을 받을 자격이 보장되지 않습니다.&#x20;

## 최종 판정

현재 계정이 AWS의 신규 프로젝트 기반 경험이라는 가설은 화면 관찰과 공식 문서를 대조했을 때 매우 강하게 지지됩니다. 하지만 계정 유형, 프로젝트 리전, 실제 SCP 적용 결과에 대한 직접 검증은 아직 남아 있습니다.

그 가설이 맞고 프로젝트가 시드니에 고정되어 있다면, 공식 문서상 다음 결론이 가장 타당합니다.

- Free Plan을 그대로 유지하면서 서울 EC2 실습과 별도 최소권한 콘솔 접근을 모두 충족하는 지원 경로는 확인되지 않았습니다.
- Paid Plan으로만 전환해도 두 문제는 해결되지 않습니다.
- 기존 계정을 유지하려면 Paid 업그레이드 → advanced 활성화 → `RegionFloor` 조정 → 별도 역할과 사람 접근 배정이 공식적으로 설명되는 경로입니다.
- 새 계정을 만들 필요는 없습니다. 또한 기존 관리자 역할에 `AdministratorAccess`가 붙어 있다는 이유로 이를 수정할 필요도 없습니다.
- 비용 측면에서는 advanced 활성화 자체가 무료이더라도, 선행 Paid Plan 전환과 강제 지출 한도 상실에 따른 위험을 별도로 판단해야 합니다.

즉, 이전 AI가 주장한 기능 제한의 존재는 대체로 맞지만, “현재 계정을 버려야 한다”거나 “Paid만 선택하면 끝난다”는 식의 결론은 잘못입니다. 반대로 “아무 전환 없이 IAM API나 CLI만으로 해결할 수 있다”는 대안도 공식 근거가 없습니다.

가장 적절한 다음 순서는 프로젝트 리전 확인 → 읽기 전용 권한 검증 → 비용·크레딧 조건 검토 → 필요한 경우에만 되돌릴 수 없는 전환 결정입니다.
