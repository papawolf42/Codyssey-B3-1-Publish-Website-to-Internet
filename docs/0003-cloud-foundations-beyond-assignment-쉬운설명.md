# 과제 너머의 클라우드 기초 — 사수 관점의 확장 지도 (쉬운 설명판)

[교육 목표와 적정 깊이](0004-educational-goals-and-learning-scope-쉬운설명.md) (원문: [0004-educational-goals-and-learning-scope.md](0004-educational-goals-and-learning-scope.md)) · [수준별 확장 안내](0005-level-appropriate-expansion-guide-쉬운설명.md) (원문: [0005-level-appropriate-expansion-guide.md](0005-level-appropriate-expansion-guide.md))

> 넓은 시야를 갖기 위한 브레인스토밍(생각 확장) 지도입니다. 여기에 나오는 모든 기술이 이번 과제의 필수 학습 내용은 아닙니다. 아래의 실험과 질문들은 사고를 넓히기 위한 제안이며, 실제로 실행한 결과가 아닙니다. 추가 요금이 발생하는 리소스를 만들거나 보안을 약화시키는 설정은 사용자의 사전 승인 없이 절대로 실행하지 않습니다.

## 1. IP와 포트 → 통신의 여러 층위

- **지금 배울 기본기:**
  - IP 주소(인터넷에서 컴퓨터의 위치를 식별하는 고유 번호, IP address)는 네트워크상의 주소이고, 포트(컴퓨터 안에서 특정 통신 프로그램이 사용하는 출입문 번호, Port)는 통신 끝점을 구분한다는 기본 모델을 익힙니다.
- **다음 단계:**
  - 사설 IP(Private IP, 가상망 내부에서만 쓰는 주소)와 공인 IP(Public IP, 전 세계 인터넷에서 통하는 주소), 32비트 체계인 IPv4와 확장 체계인 IPv6.
  - 전송 제어 규약(TCP 연결, Transmission Control Protocol), 도메인 이름을 IP 주소로 바꿔주는 이름 해석(DNS resolution, Domain Name System), 웹 응답의 결과를 나타내는 HTTP 상태 코드(200, 404, 500 등).
- **이후 심화:**
  - 실제 주고받는 데이터 조각(패킷, Packet)을 분석하는 패킷 캡처, 한 번에 보낼 수 있는 최대 데이터 크기(MTU), 운영체제의 통신 연결 추적, 통신 유실 시 TCP 재전송 원리.

> **사수의 점검 질문:**\
> "도메인 주소를 찾지 못한 'DNS 조회 실패', 서버 컴퓨터와 연결조차 맺지 못한 'TCP 연결 실패', 서버는 만났지만 요청한 파일이 없다는 'HTTP 404'는 과연 같은 장애일까요?"

- **관찰 요령:** 웹 브라우저나 터미널 요청 도구(`curl`)의 오류 메시지를 보고, 통신이 어느 단계(주소 찾기, 서버 연결, 응답 수신)까지 진행되다가 멈췄는지 명확히 구분합니다. 단순히 네트워크 연결 확인 명령(`ping`)이 응답하지 않는다고 해서 웹 접속(`HTTP`)까지 불가능하다고 섣불리 단정하지 않습니다. (방화벽이 ping 신호만 따로 막아두는 경우가 흔하기 때문입니다.)
- **더 찾아볼 검색어:** `IP address`, `TCP port`, `DNS resolution`, `connection refused vs timeout`.

## 2. VPC와 서브넷 → 주소 계획과 네트워크 격리

- **지금 배울 기본기:**
  - IP 주소 범위를 간결하게 표현하는 CIDR 표기법(Classless Inter-Domain Routing, 예: `10.0.0.0/16`), 넓은 네트워크 주소 범위를 용도별로 나누는 이유, 가상 사설망(VPC) 안에서 하위 구역인 서브넷(Subnet)이 위치하는 원리.
- **다음 단계:**
  - 데이터센터 지역 거점인 리전(Region)과 그 안의 물리적 데이터센터 단위인 가용 영역(AZ, Availability Zone).
  - 인터넷과 통신 가능한 공개 서브넷(Public Subnet)과 외부에서 직접 접근할 수 없는 비공개 서브넷(Private Subnet).
  - 서로 다른 부서나 서비스 간에 주소가 겹치지 않게 설계하는 IP 주소 계획, IPv6 주소 적용.
- **이후 심화:**
  - 서로 다른 VPC를 직접 연결하는 VPC 피어링(VPC Peering), 수많은 가상망을 허브처럼 묶어주는 전송 게이트웨이(Transit Gateway), 회사 사내망과 클라우드를 암호화 터널로 잇는 VPN, 온프레미스(자체 데이터센터)와 클라우드를 결합한 하이브리드 네트워크.

> **사수의 점검 질문:**\
> "서브넷 이름을 콘솔에서 'Public Subnet'이라고 바꾼다고 해서, 그 안에 둔 서버가 자동으로 인터넷에서 접속될까요?"

- **관찰 요령:** 사람이 붙인 이름표에 속지 말고, 실제 경로 안내표(Route Table) 설정, 공인 IP 보유 여부, 방화벽 접근 허용 규칙을 확인합니다. 이번 기초 실습에서는 복잡한 이진수 서브넷 계산 능력 전체를 필수 선수 조건으로 삼지 않습니다.
- **더 찾아볼 검색어:** `CIDR`, `Availability Zone`, `public private subnet`, `address overlap`.

## 3. 라우팅 테이블과 인터넷 게이트웨이 → 요청과 응답의 이동 경로

- **지금 배울 기본기:**
  - 목적지 IP별로 데이터를 어디로 전달할지 적어둔 경로 목록(Route Table), 모르는 모든 목적지로 갈 때 사용하는 기본 경로(`0.0.0.0/0`), 서브넷과 라우팅 테이블의 연결 관계.
- **다음 단계:**
  - 여러 경로가 겹칠 때 더 구체적인 주소 규칙을 우선 적용하는 가장 구체적인 경로 일치(Longest Prefix Match), 나갔던 요청이 돌아오는 반환 경로.
  - 외부에서 들어오는 연결을 차단한 채 내부 서버가 밖으로 나갈 때만 주소를 변환해 주는 NAT 게이트웨이(NAT Gateway)와 양방향 출입구인 인터넷 게이트웨이(Internet Gateway, IGW)의 본질적 차이.
- **이후 심화:**
  - 라우팅 분리를 통한 다중 보안 영역 격리, 인터넷을 거치지 않고 AWS 서비스와 직접 통신하는 VPC 엔드포인트(VPC Endpoint), 모든 외부 통신을 중앙에서 검사하고 내보내는 중앙 egress(아웃바운드) 아키텍처.

> **사수의 점검 질문:**\
> "VPC에 인터넷 게이트웨이(IGW)를 연결해 두었는데, 왜 서브넷 안의 EC2 가상 서버는 인터넷으로 웹 요청을 보내지 못할까요?"

- **관찰 요령:** VPC 전체에 출입구(IGW)가 매달려 있다는 사실과, 그 서브넷이 실제로 참조하는 라우팅 테이블에 출구 경로(`0.0.0.0/0 → IGW`)가 등록되어 있는지는 별개의 문제입니다. 이번 실습은 공인 IPv4 주소를 가진 단일 EC2 인스턴스를 다루므로, 비싼 요금이 나가는 NAT Gateway를 습관적으로 생성하지 않습니다.
- **더 찾아볼 검색어:** `default route`, `route association`, `longest prefix match`, `NAT vs Internet Gateway`.

## 4. 보안 그룹 → 여러 겹의 네트워크 보안 경계

- **지금 배울 기본기:**
  - 통신 프로토콜(TCP), 출입구 포트(HTTP 80, SSH 22), 출발지 주소(소스 IP 대역), 들어오는 통신(Inbound)과 나가는 통신(Outbound), 꼭 필요한 곳만 여는 최소 노출 원칙.
- **다음 단계:**
  - 요청이 들어오면 나가는 길을 자동으로 기억해 열어주는 상태 유지 가상 방화벽(Stateful Security Group)과 들어오는 길과 나가는 길을 둘 다 수동으로 열어주어야 하는 서브넷 단위 무상태 방화벽(Stateless Network ACL).
  - 리눅스 운영체제 자체 방화벽(UFW, iptables), 여러 보안 그룹 허용 규칙이 합쳐질 때의 동작 원리.
- **이후 심화:**
  - 악의적인 웹 공격을 걸러내는 웹 방화벽(WAF, Web Application Firewall), 대규모 트래픽 공격 대응(DDoS 방어), 세분화된 마이크로 세그멘테이션 네트워크 보안 정책.

> **사수의 점검 질문:**\
> "보안 그룹에서 80번 포트를 허용했다고 해서, 서버 컴퓨터 안에서 웹 서버 프로그램이 실제로 실행 중이라는 사실까지 보장될까요?"

- **관찰 요령:** 클라우드 인프라 경계(보안 그룹)와 서버 운영체제 경계(OS 방화벽), 그리고 프로그램이 실제로 포트를 열고 기다리는 상태(리스닝 소켓, Listening Socket)를 각각 분리해서 단계별로 점검합니다. 접속이 안 된다고 해서 모든 포트(0~65535)를 통째로 열어버리는 무책임한 방식으로 문제를 넘기지 않습니다.
- **더 찾아볼 검색어:** `stateful firewall`, `security group vs NACL`, `least exposure`, `listening socket`.

## 5. IAM → 사용자 신원, 클라우드 관리 권한, 임시 자격 증명

- **지금 배울 기본기:**
  - AWS 로그인 사용자(IAM User), 임시로 권한을 빌려 쓰는 역할(IAM Role), 구체적인 허용 작업 명세서인 정책(IAM Policy), 내가 누구인지 증명하는 인증(Authentication)과 무엇을 할 수 있는지 따지는 권한 부여(Authorization), 작업에 꼭 필요한 것만 허용하는 최소권한.
- **다음 단계:**
  - 정책 문서의 핵심 구조: 어떤 작업인가(Action), 어떤 자원인가(Resource), 어떤 조건인가(Condition).
  - 임시 권한을 획득하는 역할 전환(AssumeRole)과 AWS 보안 토큰 서비스(STS, Security Token Service), 2단계 다중 인증(MFA), 가상 서버(EC2)에 비밀 키를 저장하지 않고 안전하게 권한을 주는 인스턴스 프로파일(Instance Profile).
- **이후 심화:**
  - 기업용 통합 로그인 체계(IAM Identity Center), 여러 계정을 묶는 조직 전체 정책(Service Control Policies), 권한의 상한선을 정하는 권한 경계(Permissions Boundary), 다른 AWS 계정 자원에 접근하는 크로스 어카운트(Cross-Account) 접근 제어.

> **사수의 점검 질문:**\
> "IAM에서 EC2에 대한 모든 관리 권한을 가지고 있다면, 서버 운영체제에 원격 로그인할 때 SSH 접속 열쇠(키페어)는 없어도 될까요?"

- **관찰 요령:** AWS 클라우드 자원을 생성하거나 삭제하는 클라우드 관리 API 권한(IAM 신원)과, 서버 컴퓨터 내부 운영체제에 로그인하는 시스템 계정(Linux 로그인 신원)은 서로 완전히 분리된 별개의 체계입니다. 최소권한을 적용할 때는 서비스 이름(EC2)만 제한하는 데 그치지 않고, 가능한 경우 구체적인 자원과 조건까지 검토합니다. 단, AWS의 일부 작업은 개별 자원 단위 제한을 지원하지 않으므로 반드시 공식 문서를 확인해야 합니다.
- **더 찾아볼 검색어:** `principal`, `IAM policy`, `STS`, `instance profile`, `authentication authorization`.

## 6. EC2와 EBS → 가상 컴퓨터, 가상 디스크, 수명 주기

- **지금 배울 기본기:**
  - 가상 서버 인스턴스(EC2), 운영체제 기본 설치 이미지인 AMI(Amazon Machine Image), 컴퓨터의 CPU/메모리 사양을 결정하는 인스턴스 유형(t2.micro 등), 외장 하드디스크 역할을 하는 볼륨(EBS, Elastic Block Store), 서버를 잠시 끄는 중지(Stop)와 영구히 없애는 종료(Terminate)의 차이.
- **다음 단계:**
  - 서버를 껐다 켤 때 고정되지 않은 공인 IP가 바뀌는 현상, 인스턴스가 삭제될 때 디스크도 함께 지울지 결정하는 속성(`DeleteOnTermination`), 디스크 상태를 사진 찍듯 보관하는 백업본(스냅샷, Snapshot), x86과 ARM(Graviton) 등 CPU 아키텍처 차이.
- **이후 심화:**
  - 서비스 배포용 표준 골든 이미지 자동 제작, 서버 트래픽에 맞춰 자동으로 대수를 늘리고 줄이는 오토 스케일링(Auto Scaling), 1~3년 약정으로 요금을 대폭 아끼는 예약 인스턴스(RI) 및 절감형 플랜(Savings Plans), 재해 발생 시 복구 계획(DR, Disaster Recovery).

> **사수의 점검 질문:**\
> "가상 서버(EC2)를 완전히 삭제(Terminate)했으니, 디스크나 백업본도 남김없이 사라져서 비용이 전혀 안 나온다고 장담할 수 있을까요?"

- **관찰 요령:** 컴퓨터의 연산 자원(EC2 컴퓨트) 상태와 데이터를 담아두는 저장 공간(EBS 디스크/스냅샷)의 보존 상태를 콘솔에서 별도로 확인합니다. 스냅샷 백업은 훌륭한 안전장치이지만, 실제로 새 디스크로 복원해서 정상 동작하는지 검증해보지 않았다면 '언제든 복구할 수 있다'고 단정해서는 안 됩니다.
- **더 찾아볼 검색어:** `AMI`, `EBS lifecycle`, `DeleteOnTermination`, `snapshot restore`.

## 7. SSH와 Linux → 원격 접속 이후의 운영체제 관리

- **지금 배울 기본기:**
  - 공개키(서버에 둘 자물쇠)와 개인키(내 PC에 보관할 열쇠) 기반의 비대칭 암호 인증, 리눅스 시스템 사용자 계정(ubuntu, ec2-user), 파일 경로와 접근 권한(읽기/쓰기/실행), 프로그램 설치(패키지 관리자), 실행 중인 프로그램(프로세스)과 백그라운드 서비스.
- **다음 단계:**
  - 리눅스 표준 시스템 관리 데몬(`systemd`)과 서비스 상태 제어(`systemctl`), 시스템 로그를 확인하는 도구(`journalctl`), 디스크 여유 공간(`df -h`) 및 메모리 사용량(`free -m`) 확인, 처음 접속하는 서버가 진짜 내 서버인지 확인하는 SSH 호스트 키(Host Key) 검증.
- **이후 심화:**
  - 포트를 열지 않고 브라우저나 CLI로 안전하게 접속하는 AWS Systems Manager Session Manager, 보안 패치 자동화, 서버를 고쳐 쓰지 않고 새로 배포해 교체하는 불변 인프라(Immutable Infrastructure) 운영.

> **사수의 점검 질문:**\
> "터미널에서 'Permission denied' 오류가 뜬 것은, 방화벽이나 네트워크가 막힌 문제와 같은 원인일까요?"

- **관찰 요령:** 네트워크가 통하지 않아 생기는 접속 실패(Connection timed out)와, 서버까지는 도달했으나 암호키나 파일 권한이 맞지 않아 생기는 권한 거절(Permission denied)을 명확히 구분합니다. 호스트 키 검증을 무조건 무시하도록 설정을 끄거나, SSH 개인키를 깃허브 같은 공개 저장소에 올리는 치명적인 실수를 절대 저지르지 않습니다.
- **더 찾아볼 검색어:** `SSH host key`, `public key authentication`, `Linux permissions`, `systemd`, `journalctl`.

---

## 8. Nginx → 웹 서버와 애플리케이션의 경계

- **지금 배울 기본기:**
  - 정적 웹 파일(HTML, CSS, JS, 이미지), 웹 서버가 파일을 찾아 읽는 기준 폴더(Document Root, 기본 웹 루트), 서비스 포트(80), Nginx 백그라운드 실행 상태, 방문 기록이 남는 접근 로그(`access.log`)와 오류가 적히는 에러 로그(`error.log`).
- **다음 단계:**
  - 도메인 이름별로 다른 웹사이트를 서비스하는 가상 호스트 설정(Server Block), 클라이언트가 요청한 도메인을 담은 `Host` 헤더, 뒤단의 애플리케이션(Node.js, Python 등)으로 요청을 넘겨주는 대리 서버(Reverse Proxy), 자주 요청되는 정적 자원의 캐싱(HTTP Cache), HTTPS 암호화를 풀어서 내부로 넘겨주는 SSL/TLS 종료(TLS Termination).
- **이후 심화:**
  - 여러 대의 웹 서버로 부하를 나누는 로드 밸런서(ALB)와의 연동, 고성능 애플리케이션 서버와의 세밀한 통신 최적화, 무중단 배포 및 고가용성 구조.

> **사수의 점검 질문:**\
> "Nginx가 브라우저에 200 정상 응답으로 HTML을 내려주었다면, 웹페이지 안의 JavaScript가 GitHub API 서버를 불러와 그리는 프로젝트 목록 카드까지 100% 정상이라고 말할 수 있을까요?"

- **관찰 요령:** 서버가 HTML 문서 파일 자체를 성공적으로 전달한 것과, 그 문서를 받은 브라우저가 화면을 그리며 CSS/JS/외부 API를 올바르게 처리했는지는 서로 다른 실행 단계입니다. `/health` 주소에서 고정된 문구("OK")로 200 응답이 온다는 것은 그 헬스체크 경로가 살아있다는 증거일 뿐이며, 웹 애플리케이션의 모든 복잡한 기능이나 외부 의존성까지 건강하다는 뜻은 아닙니다.
- **더 찾아볼 검색어:** `document root`, `server block`, `reverse proxy`, `access log`, `health check`.

---

## 9. HTTPS와 Docker → 선택 과제 도구들의 목적과 위치

- **지금 배울 기본기:**
  - 일반 웹 통신(HTTP)과 암호화 통신(HTTPS)의 보안 차이(도청 및 위변조 방지), 인터넷 도메인 주소(Domain Name)와 암호화 통신을 보증하는 디지털 인증서(TLS Certificate)의 기본 개념.
- **다음 단계:**
  - 무료 인증서 발급 및 주기적인 자동 갱신(Let's Encrypt / Certbot), 실행 환경 전체를 묶어둔 프로그램 원본(Docker 이미지)과 이를 독립된 격리 공간에서 실행한 실체(Docker 컨테이너), 호스트 컴퓨터의 포트와 컨테이너 내부 포트를 이어주는 포트 매핑(Port Publishing).
- **이후 심화:**
  - 대규모 컨테이너를 관리하고 자동 복구하는 오케스트레이션(Kubernetes, ECS), 안전한 컨테이너 이미지 빌드 및 배포 파이프라인(이미지 공급망 보안), 클라우드 기반 완전 관리형 인증서 관리 체계(ACM).

> **사수의 점검 질문:**\
> "가상 서버 안에서 도커 컨테이너가 정상 실행 중(`Up`)으로 표시된다면, 내 컴퓨터 브라우저에서도 그 웹사이트에 반드시 접속할 수 있을까요?"

- **관찰 요령:** 컨테이너 프로그램 자체의 실행 상태, 도커 포트 매핑 설정, 가상 서버(EC2)의 포트 상태, 클라우드 가상 방화벽(보안 그룹), 인터넷 라우팅 경로를 하나씩 떼어놓고 살펴봅니다. 선택 보너스 과제(도커나 HTTPS)를 욕심내다가 필수 과제인 기본 네트워크 흐름 학습을 건너뛰거나 망치지 않습니다.
- **더 찾아볼 검색어:** `TLS certificate`, `renewal`, `Docker port publishing`, `image vs container`.

## 10. 장애 보고서 → 추측이 아닌 증거 기반 문제 해결

- **지금 배울 기본기:**
  - 문제 분석의 6단계 표준 프레임워크: **증상(문제 상황) → 가설(원인 추측) → 검증(확인 방법) → 조치(해결 작업) → 결과(동작 확인) → 재발 방지(예방 대책)**. 설정을 바꾸기 전과 후의 결과를 객관적으로 비교하기.
- **다음 단계:**
  - 오류 발생 시점과 로그 기록의 시간대(Timezone) 일치 확인, 서로 다른 로그 사이의 인과관계 추적, AWS 계정 내 관리 명령 기록을 담는 CloudTrail과 웹 서버 자체 서비스 로그의 차이 이해, 인프라 변경 이력 추적.
- **이후 심화:**
  - 시스템 상태를 종합적으로 관찰하는 3대 요소(메트릭스/로그/분산 추적), 이상 발생 시 담당자에게 알리는 경보(Alerting), 서비스 목표 수준(SLO), 체계적인 장애 사후 분석 보고서(Postmortem).

> **사수의 점검 질문:**\
> "이것저것 동시에 여러 설정을 마구 건드리다가 우연히 고쳐졌다면, 다음에 똑같은 문제가 발생했을 때 다시 침착하게 해결할 수 있을까요?"

- **관찰 요령:** 한 번에 하나의 가설만 세우고 한 번에 하나의 설정만 변경하여 검증합니다. CloudTrail은 콘솔 버튼 클릭이나 API 호출 같은 'AWS 관리 이벤트'를 기록하는 곳이지, 웹 서버로 들어오는 일반 HTTP 요청 내용까지 대신 기록해 주는 곳이 아닙니다. VPC Flow Logs(네트워크 패킷 흐름 기록) 같은 추가 진단 도구도 설정 복잡도와 추가 요금을 먼저 확인한 뒤 도입합니다.
- **더 찾아볼 검색어:** `hypothesis-driven debugging`, `CloudTrail`, `observability`, `postmortem`.

## 11. 비용과 정리 → 클라우드 실습도 엄연한 운영이다

- **지금 배울 기본기:**
  - 생성한 자원 목록, 생성된 리전(`ap-northeast-2`), 각 자원의 고유 식별 번호(Resource ID), 자원을 만든 사람의 정리 책임, 서버 사용 시간·디스크 저장 용량·공인 IPv4 주소 등 요금이 발생하는 구체적 원인 이해.
- **다음 단계:**
  - 어떤 용도로 만든 자원인지 표시하는 태그(Cost Allocation Tag), 예상 요금을 초과하면 이메일을 보내주는 예산 알림(AWS Budgets), 요금 반영 지연(수 시간에서 하루)에 대한 이해, 연결이 끊긴 채 방치된 미사용 자원(Orphaned Resource) 색출.
- **이후 심화:**
  - 코드로 인프라를 정의하고 일괄 생성/삭제하는 코드형 인프라(IaC, Terraform/CloudFormation), 조직 전체의 비용 배분 및 낭비 방지 자동화, 재무와 엔지니어링을 결합한 클라우드 재무 관리(FinOps).

> **사수의 점검 질문:**\
> "가상 서버 컴퓨터를 껐으니(Stop), 클라우드 과금도 그 순간부터 전부 0원으로 멈췄다고 장담할 수 있을까요?"

- **관찰 요령:** 예산 알림(Budgets)은 기준 금액을 넘었을 때 '알려주는' 장치일 뿐, 자동으로 서버를 끄거나 지출을 강제로 차단해 주는 마법의 차단기가 아닙니다. 계정의 보호 설정과 조건은 별도로 확인해야 합니다. 테라폼(Terraform) 같은 멋진 자동화 도구를 쓰더라도, 내가 무엇을 만들었고 무엇을 지워야 하는지 사람이 직접 알지 못하면 안전을 절대로 보장할 수 없습니다.
- **더 찾아볼 검색어:** `resource inventory`, `AWS Budgets`, `cost allocation tags`, `Infrastructure as Code`.

---

## 12. 이번에 배울 것과 나중에 배울 것의 경계

지금 단계에서는 **단 한 대의 가상 서버를 만들더라도 요청이 흐르는 길목, 필요한 보안 권한, 정상 동작과 실패의 원인, 그리고 깔끔한 정리 과정을 막힘없이 설명하는 것**이 최우선입니다. 유행하는 수많은 도구를 겉핥기로 전부 써보는 것이 클라우드 기초를 마스터했다는 뜻이 아닙니다.

- 컨테이너 오케스트레이션 도구인 쿠버네티스(Kubernetes)를 배우기 전에, **EC2 안에서 프로세스가 실행되고 포트를 여는 원리**를 먼저 배웁니다.
- 코드형 인프라 도구인 테라폼(Terraform)을 배우기 전에, **실제 클라우드 리소스가 어떻게 만들어지고 서로 의존하는지**를 먼저 배웁니다.
- 서버가 죽어도 다른 서버가 이어받는 고가용성(High Availability)을 배우기 전에, **단 하나의 요청이 성공하거나 실패하는 길목**을 먼저 배웁니다.
- 대규모 관측 모니터링 플랫폼을 구축하기 전에, **서버 상태 명령, 로그 파일, 논리적 가설 검증**을 먼저 배웁니다.
- 복잡한 대기업 권한 조직 설계를 하기 전에, **방화벽(Security Group)과 관리 권한(IAM)의 본질적인 차이**를 먼저 배웁니다.
