# B3-1 완전 안내형 실습 교재

[과제 요구사항 요약](0051-requirements-and-review-reference.md) · [개요 계획](0007-step-by-step-study-plan.md) · [필수 체크리스트](0002-required-checklist-and-extension-rules.md) · [클라우드 확장 지도](0003-cloud-foundations-beyond-assignment.md) · [교육 목표](0004-educational-goals-and-learning-scope.md) · [PBL 원칙](0006-pbl-top-down-learning-principles.md)

> 이 문서는 “AWS에서 서버를 만든다” 수준의 큰 순서가 아니라, 요청이 어느 계층을 지나가는지 확인하고 다음 버튼이나 명령을 실행하기 전 무엇을 예상하는지까지 쪼갠 **실행용 학습 교재**다. 각 번호를 위에서 아래로 수행한다. AWS 리소스를 만들거나 변경하는 단계는 승인 전까지 실제 실행하지 않고, 읽기·그림·가상 검증으로 공부한다.
>
> 이 문서만 보고도 B3-1의 필수 결과물인 아키텍처 다이어그램, 외부 접속 증빙, 트러블슈팅 보고서, 리소스 정리 체크리스트를 빠뜨리지 않도록 구성했다. 그래도 문서는 사용자의 AWS 계정·비용·IP·권한을 대신 결정할 수 없다. 그 값이 필요한 곳에서는 멈추고 질문한다.
>
> 비밀번호·액세스 키·SSH 개인 키·토큰은 채팅·문서·저장소에 기록하지 않는다. 실제 AWS 리소스 생성·Security Group 변경·SSH 접속·삭제는 사용자의 명시적 승인을 받은 범위에서만 실행한다.

## 0. 사용 규칙: 클라우드 작업은 관찰과 안전을 먼저 한다

### 0-1. 표기

- `[필수]`: 공식 과제 결과를 위해 반드시 통과.
- `[학습]`: 원리 이해를 위해 수행.
- `[선택]`: 필수 경로와 정리를 끝낸 뒤 수행.
- `[읽기]`: 상태·로그·설정을 조회만 하는 단계.
- `[변경]`: 리소스·규칙·서버를 바꾸는 단계.
- `[승인 필요]`: 사용자 확인 전에는 실제 실행하지 않는 단계.
- `[기록]`: 증거와 설명을 문서에 남기는 단계.

### 0-2. 한 번호의 고정 순서

각 번호를 실행하기 전에 다음을 기록한다.

```text
B3-1 번호:
이 요청/설정은 어디에서 어디까지 갈 것인가:
실행 전 예상:
실제 관찰:
내 설명:
비용·보안 영향:
```

그 다음:

1. **전체 위치 확인:** 외부 브라우저 → 인터넷 → VPC → Subnet → Route Table/IGW → Security Group → EC2 → Nginx → 파일 중 어디인가?
2. **예측:** 성공·실패 시 어느 계층에서 어떤 증상이 보일지 말한다.
3. **개념 하나:** 이번 번호의 핵심 용어 하나만 공부한다.
4. **읽기 확인:** 가능하면 변경 전에 콘솔·로그·상태를 조회한다.
5. **작은 변경:** 승인된 경우에만 한 리소스 또는 한 규칙만 변경한다.
6. **관찰:** AWS 콘솔, 터미널, 서버 내부, 외부 브라우저를 섞지 않고 각각 확인한다.
7. **설명:** 설정 → 요청 경로 → 응답 또는 실패를 자신의 말로 설명한다.
8. **작은 변형:** 한 경로·포트·규칙·파일만 바꾼다고 가정하고 결과를 예측한다.
9. **원인 조사·복구:** 증상 보존 → 가설 → 한 가지 검증 → 수정 → 재확인 → 필요 시 원복 순서다.
10. **비용·보안 확인:** 남은 공개 포트·권한·리소스·과금 항목을 확인한다.

### 0-3. 질문 양식

```text
[B3-1 번호: __________________]
내가 하려던 일:
AWS 리전:
대상 리소스/ID(비밀값 제외):
실행 전 예상:
실제 관찰:
브라우저/터미널/콘솔 오류 전문:
내 원인 가설:
비용·보안 영향:
다음에 확인할 한 가지와 이유를 알려줘. 비밀값은 요구하지 마.
```

### 0-4. 비밀정보 규칙

- 비밀번호는 채팅에 보내지 않아도 된다.
- `.env`에 계정을 넣는 방식 자체가 금지인 것은 아니지만, 이번 정적 사이트·AWS 실습에서는 비밀값을 문서·Git·채팅에 저장하지 않는다.
- 액세스 키·SSH 개인 키·세션 토큰·비밀번호를 출력하거나 캡처하지 않는다.
- 화면 캡처 전 주소·계정·공인 IP를 공개해도 되는지 확인한다.

### 0-5. 학습 기록 파일

실제 AWS 작업 전에 `docs/study-log.md`, `docs/resource-inventory.md`를 만든다.

`study-log.md`:

```markdown
## B3-1 번호
- 확인/변경한 것:
- 핵심 개념:
- 예상과 실제:
- 실패와 확인 순서:
- 비용·보안 확인:
- 다음 질문:
```

`resource-inventory.md`:

| 리소스 | 리전 | 생성 여부 | ID/이름 | 생성 근거 | 삭제 방법 | 삭제 확인 |
|---|---|---|---|---|---|---|
| VPC | ap-northeast-2 | 미생성 | - | - | - | - |

ID와 공인 IP를 기록할 때 비밀값과 계정 자격증명은 기록하지 않는다.

### 0-6. 안전 중지 규칙

다음 중 하나면 새 작업을 멈춘다.

- 비용이 예상보다 늘어날 수 있다.
- 어떤 리소스를 바꾸는지 확실하지 않다.
- SSH 키를 잃을 위험이 있다.
- Security Group이 너무 넓게 열릴 수 있다.
- Root/AdministratorAccess로 우회하려 한다.
- 삭제 순서와 복구 방법을 모른다.

## 1. 숲 먼저 보기: 최종 요청 경로와 과제 범위 [필수]

### B3-1-01. B1-1의 배포 대상을 확인한다 [필수]

1. B1-1에서 실제로 검증한 소스 경로를 확인한다.
2. HTML·CSS·JS·images 파일 목록을 적는다.
3. 아직 배포하지 않았다면 `미배포`라고 쓴다.
4. B3-1은 같은 사이트를 다시 만드는 것이 아니라 서버가 파일을 전달하게 하는 과제라고 적는다.

예상:

- B1-1 로컬 결과와 B3-1 서버 결과는 같은 파일을 사용할 수 있지만 실행 환경은 다르다.

변형:

- `index.html`만 서버에 복사하면 CSS·JS·이미지가 왜 빠지는지 설명한다.

통과:

- 배포할 정확한 버전과 아직 미완료인 것을 구분한다.

### B3-1-02. 공식 제출물 네 개를 찾는다 [필수]

`instruction.md`에서 `## 2. 최종 결과물`을 열고 다음 네 줄을 적는다.

1. `docs/architecture.(png|pdf)`.
2. 외부 접속 증빙과 README 기록.
3. `docs/troubleshooting.(md|pdf)`.
4. `docs/cleanup-checklist.md`.

각각 “입력/요청 → 출력/화면 → 최소 규격”을 표로 만든다.

개념:

- 배포 성공 화면만으로는 과제 전체를 완료한 것이 아니다. 구조 설명·문제 해결·정리 증거도 결과물이다.

### B3-1-03. 최종 요청을 한 줄로 그린다 [필수]

종이에 다음을 왼쪽에서 오른쪽으로 쓴다.

```text
외부 브라우저
→ Public IP:80
→ Internet Gateway
→ Route Table
→ Public Subnet
→ EC2 ENI/Security Group
→ Linux
→ Nginx:80
→ B1-1 파일
→ HTTP 응답
```

그림을 그릴 때 화살표마다 “무엇이 이동하는가”를 적는다.

- 브라우저: HTTP 요청.
- 네트워크: 패킷.
- Security Group: 허용/차단 판단.
- Nginx: 파일 응답.

예상:

- 어느 한 요소가 빠지면 특정 종류의 실패가 생긴다.

### B3-1-04. IP·포트·HTTP를 분리한다 [필수]

1. “어느 컴퓨터인가?”에 답하는 값으로 IP를 표시한다.
2. “그 컴퓨터의 어느 프로그램인가?”에 답하는 값으로 포트 80을 표시한다.
3. “무엇을 주고받는 규칙인가?”에 HTTP를 표시한다.
4. `http://<public-ip>:80/`를 세 부분으로 나눈다.

자기 설명:

- IP는 주소, 포트는 프로그램 입구 번호, HTTP는 웹 요청·응답 규칙이다.

변형:

- 포트 22를 넣고 웹 페이지 대신 SSH 관리 접속이라는 점을 예측한다.

통과:

- 주소·출입구·통신 규칙을 섞지 않는다.

### B3-1-05. 내부 localhost와 외부 주소를 비교한다 [필수]

표를 만든다.

| 명령/주소 | 실행한 컴퓨터 | 목적지 |
|---|---|---|
| `http://localhost` | EC2 | EC2 자기 자신 |
| `http://<public-ip>` | 내 브라우저 | EC2 외부 인터페이스 |

개념:

- `localhost`는 명령을 실행한 컴퓨터 자신이다.

변형:

- 내 노트북에서 `localhost`를 열면 EC2가 아닌 내 노트북을 가리키는 이유를 말한다.

### B3-1-06. 실패 증상을 분류한다 [필수]

다음 증상 옆에 첫 확인 계층을 적는다.

- DNS/주소 오류: 이름·주소.
- timeout: 경로·방화벽·응답 부재.
- connection refused: 목적지까지 갔지만 대기 서비스 없음 가능성.
- 403: 웹 서버 권한/접근 거부.
- 404: 경로·파일 없음.
- 502: 앞단과 뒷단 연결 문제 가능성.

실제 오류가 아직 없으면 가상 시나리오임을 표시한다.

### B3-1-07. 비용과 승인 경계를 먼저 쓴다 [필수]

다음은 실제 실행하지 않고 표에 쓴다.

| 작업 | 읽기/변경 | 비용 가능성 | 보안 영향 | 사용자 승인 |
|---|---|---|---|---|
| 리전 확인 | 읽기 | 없음 | 낮음 | 불필요 |
| VPC 생성 | 변경 | 낮음/구성에 따라 | 네트워크 | 필요 |
| EC2 생성 | 변경 | 있음 | 외부 노출 | 필요 |
| HTTP 80 공개 | 변경 | 없음/공개 영향 | 있음 | 필요 |
| SSH 22 제한 | 변경 | 없음 | 중요 | 필요 |
| 리소스 삭제 | 변경 | 과금 방지 | 데이터 손실 | 필요 |

통과:

- 실행 버튼을 누르기 전에 승인·비용·복구를 확인한다.

### B3-1-08. 0절 회상 시험을 한다 [필수]

문서를 덮고 답한다.

1. 네 제출물은 무엇인가?
2. 외부 요청이 지나는 경로를 순서대로 말할 수 있는가?
3. localhost와 public IP의 차이는 무엇인가?
4. HTTP 80과 SSH 22의 용도는 어떻게 다른가?
5. 어떤 작업이 승인 전 금지인가?

## 2. AWS 계정·리전·권한을 안전하게 준비한다 [필수]

### B3-1-09. AWS 콘솔을 열고 리전만 확인한다 [읽기]

1. AWS 콘솔을 연다.
2. 현재 리전 선택기를 찾는다.
3. `Asia Pacific (Seoul) ap-northeast-2`인지 확인한다.
4. 다르면 아직 리소스를 만들지 말고 리전을 서울로 선택한다.
5. 화면에 계정 이메일·계정 번호가 노출되면 캡처하지 않는다.

예상:

- 리전 선택은 어느 지역의 리소스를 보고 만들지 결정한다.

변형:

- 다른 리전의 EC2 목록이 서울 목록과 다를 수 있는 이유를 말한다.

### B3-1-10. Root 계정 사용 여부를 확인한다 [읽기]

1. AWS 콘솔 계정 메뉴를 연다.
2. 현재 로그인 방식이 Root인지 IAM 사용자/Role인지 확인한다.
3. Root라면 리소스를 만들지 않고 멈춘다.

개념:

- Root는 계정 전체 권한을 가지므로 일상 작업에 쓰지 않는다.

통과:

- AWS 관리 권한과 EC2 내부 Linux 로그인 권한은 다른 것이라고 말한다.

### B3-1-11. IAM 사용자·Role·정책을 구분한다 [학습]

종이에 세 칸을 만든다.

- 사용자: 사람이 AWS API/콘솔을 사용하는 주체.
- Role: 서비스나 사용자가 잠시 맡는 권한 주체.
- Policy: 어떤 작업을 허용/거부하는 규칙 문서.

변형:

- “SSH로 서버에 들어갈 수 있으니 VPC를 만들 수 있다”가 왜 틀린지 설명한다.

### B3-1-12. 필요한 관리 작업만 나열한다 [필수]

이번 최소 경로에서 필요한 작업을 쓴다.

- VPC·Subnet 조회/생성.
- Internet Gateway 연결.
- Route Table 생성·연결·경로 등록.
- Security Group 규칙 확인·변경.
- EC2 생성·조회·종료.
- 키페어를 안전하게 사용하는 것.
- 태그 기록.

S3·RDS·ALB 등은 이번 최소 경로에 불필요하다고 별도로 적는다.

통과:

- 관리자 권한으로 막힌 문제를 우회하지 않는다.

### B3-1-13. 비용 정보를 확인할 준비를 한다 [필수]

확인할 항목을 계정에서 읽기 방식으로 찾는다.

- Free Tier 적용 여부.
- 남은 크레딧이 있는지.
- 결제 알림 설정.
- 서울 리전 가격표.
- EC2·EBS·Elastic IP·NAT Gateway 비용 가능성.

계정의 금액·이메일·결제 정보를 문서나 채팅에 복사하지 않는다. “확인됨/확인 필요”만 기록한다.

### B3-1-14. 키페어 보관 규칙을 정한다 [필수]

1. SSH 개인 키를 저장할 안전한 로컬 위치를 정한다.
2. Git 저장소 안이 아닌지 확인한다.
3. 채팅·문서·스크린샷에 넣지 않는다.
4. 분실 시 재발급이 아니라 새 키·접속 복구 절차가 필요하다는 점을 기록한다.

통과:

- 키 파일의 경로를 말할 수는 있지만 내용을 출력하지 않는다.

### B3-1-15. 권한·비용 회상 시험을 한다

1. IAM 오류와 Linux permission denied를 어떻게 구분하는가?
2. AdministratorAccess를 쓰지 않는 이유는?
3. EC2를 멈춰도 남을 수 있는 과금 항목은?
4. 실제 변경 전에 누구의 승인이 필요한가?

## 3. VPC와 Subnet을 그림으로 이해한다 [필수]

### B3-1-16. VPC의 경계를 그린다 [학습]

종이에 큰 상자 하나를 그리고 `VPC 10.0.0.0/16`이라고 쓴다.

개념:

- VPC는 AWS 안의 논리적으로 분리된 네트워크 공간이다.

예상:

- VPC 안에 Subnet·라우팅·EC2가 들어간다.

변형:

- VPC 상자 밖에 EC2를 그려 보고 왜 이번 구성에 맞지 않는지 말한다.

### B3-1-17. CIDR을 작은 범위로 읽는다 [학습]

다음 세 값을 비교해 표에 쓴다.

- `10.0.0.0/16`: 큰 내부 주소 범위.
- `10.0.1.0/24`: VPC 안의 더 작은 구역.
- `0.0.0.0/0`: 모든 IPv4 목적지.

`/32`는 특정 IP 하나에 가까운 제한으로 설명한다.

변형:

- SSH 소스 `내 IP/32`와 `0.0.0.0/0`의 공개 범위를 비교한다.

### B3-1-18. Public Subnet이라는 말을 조건으로 분해한다 [필수]

다음 네 칸을 모두 채워야 public 경로가 된다고 적는다.

1. VPC 안의 Subnet.
2. Route Table이 연결됨.
3. 기본 경로 `0.0.0.0/0 → IGW`.
4. 인스턴스가 공인 IP를 가짐.

여기에 Security Group HTTP 80 허용과 Nginx 대기도 별도 조건이다.

예상:

- Subnet 이름만 Public으로 지어도 외부 접속되지 않는다.

### B3-1-19. Public/Private을 비교한다 [학습]

표를 만든다.

| 항목 | Public 경로 | Private 경로 |
|---|---|---|
| 인터넷으로 직접 경로 | IGW 기본 경로 가능 | 직접 공개하지 않음 |
| 공인 IP | 필요할 수 있음 | 보통 없음 |
| 이번 필수 구성 | 사용 | 추가하지 않음 |

NAT Gateway는 이번 최소 구성에 자동으로 필요한 것이 아니며 비용 가능성이 있다고 기록한다.

문서를 덮고 답한다.

- VPC와 Subnet 중 어느 것이 큰 공간인가?
- `0.0.0.0/0`은 무엇을 뜻하는가?
- Public Subnet이 되려면 어떤 실제 설정이 필요한가?
- Subnet이 public이어도 외부 접속이 실패할 수 있는 이유 세 가지는?

## 4. Internet Gateway와 Route Table을 연결한다 [필수]

### B3-1-21. Internet Gateway의 위치를 그린다 [학습]

1. VPC 상자 옆에 IGW를 그린다.
2. VPC와 IGW 사이에 연결선을 그린다.
3. IGW 바깥에 Internet을 쓴다.

개념:

- IGW는 VPC와 인터넷 사이의 연결 관문이다.

주의:

- IGW만 연결해도 Route Table이 목적지를 안내하지 않으면 경로가 완성되지 않는다.

### B3-1-22. Route Table 한 줄을 읽는다 [필수]

다음 표를 읽는다.

| Destination | Target | 뜻 |
|---|---|---|
| `10.0.0.0/16` | local | VPC 내부 통신 |
| `0.0.0.0/0` | Internet Gateway | 그 외 IPv4 목적지는 인터넷 관문 |

예상:

- Public Subnet과 이 Route Table이 연결되어야 외부 경로가 생긴다.

변형:

- 기본 경로의 target을 지운다면 외부 요청과 응답이 어떻게 달라질지 예측한다.

### B3-1-23. Subnet association을 이해한다 [학습]

- Route Table이 존재하는 것만으로 모든 Subnet에 적용되지 않는다.
- 특정 Subnet과 association되어야 그 Subnet의 인스턴스가 해당 경로를 사용한다.

그림에 `Route Table → Public Subnet` 연결선을 그린다.

### B3-1-24. 생성 전 최소 네트워크 명세를 작성한다 [필수]

실제 생성 전에 아래 값을 사용자가 승인할 명세로 적는다. VPC CIDR과 Subnet CIDR은 공식이 강제하지 않는다면 임의로 결정하지 말고 확인한다.

```text
Region: ap-northeast-2
VPC: 1개
Public Subnet: 1개
Internet Gateway: 1개, VPC 연결
Route Table: 1개, 0.0.0.0/0 → IGW
EC2: 1대, Public Subnet
```

### B3-1-25. 네트워크 계층 고의 실패를 종이에 재현한다

다음 네 경우를 표로 쓴다.

1. IGW 없음.
2. IGW는 있지만 Route Table 기본 경로 없음.
3. Route Table은 있지만 Subnet association 없음.
4. 경로는 있지만 EC2에 Public IP 없음.

각 경우에 “외부 요청이 어느 지점에서 막힐 가능성이 있는가?”를 적는다.

### B3-1-26. 네트워크 회상 시험

- IGW와 Route Table의 책임은 각각 무엇인가?
- Route Table이 Subnet에 연결되지 않으면 왜 영향이 없는가?
- VPC 안의 local route와 인터넷 기본 경로의 차이는?

## 5. Security Group과 SSH 접근을 설계한다 [필수]

### B3-1-27. 포트별 사용자를 나눈다 [필수]

표를 만든다.

| 포트 | 서비스 | 사용자 | 소스 |
|---|---|---|---|
| 80 | HTTP/Nginx | 인터넷 방문자 | `0.0.0.0/0` |
| 22 | SSH | 관리자 | 내 공인 IP/32 또는 지정 대역 |

예상:

- 웹 방문자는 SSH 문을 사용할 필요가 없다.

### B3-1-28. Security Group을 계층으로 이해한다 [필수]

다음 순서로 설명한다.

1. Security Group: AWS 네트워크 경계에서 허용/차단.
2. OS 방화벽: EC2 운영체제 안에서 허용/차단.
3. Nginx listening socket: 실제 프로그램이 어느 포트에서 기다리는지.

변형:

- 세 곳 중 하나만 허용하면 왜 충분하지 않을 수 있는지 말한다.

### B3-1-29. SSH 22 제한 범위를 결정한다 [필수]

1. 현재 공인 IP를 확인해야 한다면 공개적으로 공유하지 않고 콘솔 입력용으로만 확인한다.
2. SSH source는 개인 IP/32 또는 승인된 지정 대역으로 쓴다.
3. `0.0.0.0/0` SSH를 만들지 않는다.
4. IP가 바뀌면 기존 규칙이 다시 필요할 수 있음을 기록한다.

### B3-1-30. HTTP 80 공개 범위를 결정한다 [필수]

- 공식 요구는 HTTP 80이 `0.0.0.0/0`에서 접근 가능해야 한다.
- HTTPS를 아직 하지 않는다면 HTTP와 HTTPS를 혼동하지 않는다.
- 전체 포트 `0-65535` 공개는 만들지 않는다.

### B3-1-31. 실제 Security Group 생성 전 검토한다 [승인 필요]

다음 표를 사용자에게 보여 주고 승인 전에는 생성하지 않는다.

| Type | Protocol | Port | Source | 이유 |
|---|---|---:|---|---|
| HTTP | TCP | 80 | `0.0.0.0/0` | 외부 웹 접속 |
| SSH | TCP | 22 | 개인 IP/32 | 관리자 접속 |

필요하지 않은 규칙은 추가하지 않는다.

### B3-1-32. Security Group 오류 시나리오를 예측한다

- 80이 없고 Nginx가 켜짐: 외부 timeout 가능.
- 22가 없고 키가 맞음: SSH 접속 차단 가능.
- 80은 열었지만 Nginx 중지: connection refused 가능.
- 22를 전체 공개: 기능은 될 수 있지만 보안 요구 위반.

- SSH 접속 실패 시 어떤 순서로 확인하는가?

## 6. 비용·생성·삭제 계획을 승인받는다 [필수]

### B3-1-34. 비용이 남을 수 있는 리소스를 목록화한다 [필수]

## 7. 최소 AWS 네트워크를 실제로 만든다 [승인 후 변경]

이 절부터는 사용자의 승인 전에는 실행하지 않는다. 각 번호는 실제 리소스 ID와 상태를 기록한다.

### B3-1-38. VPC 생성 전 예측한다

- 생성 대상: 서울 리전 VPC 1개.
- 예상 성공: VPC ID가 생기고 기본 local route가 있다.
- 예상 실패: 권한·리전·CIDR 오류.
- 비용·보안: 아직 외부 공개 경로와 서버가 없으므로 HTTP 노출 없음.

승인 후 콘솔에서 VPC를 생성하고 `resource-inventory.md`에 ID·태그를 기록한다. 계정 번호나 키는 기록하지 않는다.

### B3-1-39. VPC 생성 후 읽기 확인한다 [필수]

1. VPC 상태가 Available인지 확인한다.
2. CIDR이 승인한 값과 같은지 확인한다.
3. 이름·태그가 맞는지 확인한다.
4. 다른 리전이 아닌지 다시 확인한다.
5. 실제 변경 없이 상태를 기록한다.

### B3-1-40. Public Subnet을 생성한다 [승인 후 변경]

1. 같은 VPC를 선택한다.
2. 승인한 Availability Zone과 CIDR을 선택한다.
3. Public Subnet 1개를 생성한다.
4. Subnet ID·CIDR·AZ를 기록한다.

예상:

- Subnet이 생기지만 아직 인터넷 경로는 완성되지 않는다.

### B3-1-41. Internet Gateway를 생성·연결한다 [승인 후 변경]

1. IGW 1개를 생성한다.
2. 승인한 VPC에 attach한다.
3. 상태가 Attached인지 확인한다.
4. ID와 연결 VPC를 기록한다.

### B3-1-42. Route Table을 생성한다 [승인 후 변경]

1. 같은 VPC에 Route Table 1개를 만든다.
2. `0.0.0.0/0 → Internet Gateway` route를 추가한다.
3. route가 Active인지 확인한다.
4. Public Subnet association을 만든다.
5. route table ID와 association을 기록한다.

한 번에 여러 route를 추가하지 않는다.

### B3-1-43. 실제 관계를 그림과 대조한다 [필수]

콘솔에서 다음을 클릭해 확인한다.

- VPC → Subnet.
- Subnet → Route Table association.
- Route Table → `0.0.0.0/0 → IGW`.
- VPC → IGW attachment.

그림에서 누락·초과된 연결을 표시하고, 바로 수정하지 말고 가설을 적는다.

### B3-1-44. 네트워크 내부 변형을 종이에 먼저 한다

실제 route를 지우지 않는다. 종이에 route target을 제거했을 때 외부 요청이 어떻게 실패할지 예측한다.

승인된 통제 실험을 하지 않는다면 가상 시나리오라고 보고서에 표시한다.

### B3-1-45. 네트워크 생성 단계를 기록한다 [기록]

각 리소스에 다음을 기록한다.

```text
생성 시각:
리전:
리소스 종류:
ID:
부모/연결:
예상:
실제:
비용/보안 확인:
```

## 8. EC2·EBS·키페어·Security Group을 만든다 [승인 후 변경]

### B3-1-46. EC2 사양을 승인된 명세와 비교한다 [필수]

생성 화면에서 다음을 확인한다.

- 서울 리전.
- micro급 프리티어 대상 여부.
- Ubuntu LTS 또는 Amazon Linux 계열.
- EBS 8~10 GiB 수준.
- Public Subnet.
- Public IP 자동 할당 또는 승인된 공인 IP 방식.
- Security Group.
- 키페어.

값이 다르면 생성하지 말고 질문한다.

### B3-1-47. 키페어를 연결한다 [승인 후 변경]

1. 승인한 키페어를 선택한다.
2. 개인 키 다운로드·보관 상태를 확인한다.
3. 개인 키 내용을 터미널에 출력하지 않는다.
4. Git 상태에서 키 파일이 추적되지 않는지 확인한다.

### B3-1-48. Security Group 규칙을 한 줄씩 만든다 [승인 후 변경]

1. HTTP TCP 80 source `0.0.0.0/0`.
2. SSH TCP 22 source 개인 IP/32.
3. 전체 포트 규칙이 없는지 확인한다.
4. 각 규칙을 `resource-inventory.md`에 기록한다.

### B3-1-49. EC2를 생성하고 상태를 읽는다 [승인 후 변경]

1. Create를 누르기 직전에 예상과 비용·보안 영향을 다시 말한다.
2. 생성한다.
3. Instance state가 Running인지 확인한다.
4. Public IPv4 address를 확인한다.
5. 연결된 Subnet·Security Group·IAM Role을 확인한다.
6. 리소스 ID·공인 IP·상태를 기록한다. 개인 키는 기록하지 않는다.

예상:

- Running은 가상 컴퓨터가 켜졌다는 뜻이지 Nginx가 설치됐다는 뜻이 아니다.

### B3-1-50. EC2 상태 변형을 설명한다

다음 상태를 실제로 바꾸지 말고 의미를 설명한다.

- Pending.
- Running.
- Stopping.
- Stopped.
- Terminated.

특히 Stop은 다시 시작할 수 있는 상태이고 Terminate는 삭제에 가까운 상태임을 구분한다.

## 9. SSH로 내부에 들어가 서버 상태를 본다 [필수]

### B3-1-51. SSH 명령의 각 부분을 분해한다 [학습]

실제 명령을 실행하기 전에 아래 형식을 설명한다.

```bash
ssh -i <private-key-path> <linux-user>@<public-ip>
```

- `ssh`: 원격 셸 접속 프로그램.
- `-i`: 사용할 개인 키 파일.
- Linux user: OS 이미지에 맞는 기본 사용자.
- public IP: 접속 대상 주소.

비밀 키 값 자체를 채팅에 보내지 않는다.

### B3-1-52. SSH 접속 전 네 가지를 확인한다 [필수]

1. EC2 Running.
2. Public IP가 현재 값과 같음.
3. Security Group TCP 22 source가 현재 IP를 포함.
4. 키 파일 경로와 Linux user가 이미지와 일치.

하나라도 모르면 접속 명령을 실행하지 않는다.

### B3-1-53. SSH로 접속한다 [승인 후 변경]

사용자가 직접 실행하거나 승인된 도구로 실행한다. 접속 후 비밀값을 출력하지 않는다.

접속 직후 다음 읽기 명령을 한 줄씩 실행한다.

```bash
whoami
pwd
uname -a
```

예상:

- Linux 사용자, 현재 경로, 커널 정보가 나온다.

관찰:

- 이것은 EC2 내부 관찰이며 웹 서버 성공 증거가 아니다.

### B3-1-54. SSH 실패를 계층별로 나눈다 [학습]

| 증상 | 먼저 볼 곳 |
|---|---|
| timeout | Public IP·Route·SG 22·현재 IP |
| permission denied (publickey) | 키·Linux 사용자 |
| connection refused | SSH 서비스/OS |
| 권한 부족 명령 | Linux 사용자 권한/sudo |

한 번에 키·SG·IP를 모두 바꾸지 않는다.

### B3-1-55. 서버의 인터넷 outbound를 확인한다 [필수]

EC2 안에서 승인된 안전한 URL로 다음을 실행한다.

```bash
curl -I https://example.com
```

예상:

- HTTP headers가 나오면 외부로 나가는 경로가 동작할 가능성이 있다.

관찰:

- 이 결과는 outbound 성공 증거이지 외부에서 EC2로 들어오는 inbound 성공 증거가 아니다.

변형:

- URL을 다른 안전한 공식 사이트로 하나만 바꾼다.

### B3-1-56. 서버 내부 기록을 남긴다 [기록]

```text
SSH 성공 시각:
EC2 상태:
Public IP 확인 여부:
whoami 결과(사용자명만, 비밀값 없음):
pwd 결과:
outbound curl 상태:
아직 확인하지 않은 것:
```

## 10. Nginx를 설치하고 localhost에서 검증한다 [필수]

### B3-1-57. Nginx 역할을 먼저 말한다 [학습]

- Nginx는 브라우저 요청을 받아 정적 HTML·CSS·JS 파일을 전달하는 웹 서버 프로그램이다.
- EC2는 컴퓨터, Nginx는 그 컴퓨터에서 실행되는 프로그램이다.

그림에서 `EC2 box` 안에 `Nginx:80`을 넣는다.

### B3-1-58. Nginx 설치 전 상태를 확인한다 [읽기]

EC2에서 다음을 확인한다.

```bash
which nginx
sudo systemctl status nginx
```

예상:

- 설치 전에는 명령 없음 또는 inactive일 수 있다.

주의:

- 오류 문구를 기록하되 여러 설치 명령을 한꺼번에 실행하지 않는다.

### B3-1-59. Nginx를 설치한다 [승인 후 변경]

OS에 맞는 공식 설치 절차를 확인한 뒤 한 단계씩 실행한다. 설치 명령은 이미지에 따라 달라질 수 있으므로 Ubuntu용과 Amazon Linux용을 섞지 않는다.

설치 후:

```bash
sudo systemctl enable --now nginx
sudo systemctl status nginx
```

예상:

- 서비스가 active/running이 된다.

관찰:

- 설치가 성공했다는 것과 외부 접속이 성공했다는 것을 구분한다.

### B3-1-60. Nginx가 80번에서 기다리는지 확인한다 [필수]

다음 중 사용 가능한 읽기 명령을 선택한다.

```bash
sudo ss -ltnp | grep ':80'
```

또는:

```bash
sudo nginx -t
```

예상:

- 80번 listening 또는 설정 문법 successful.

변형:

- 설정 파일 경로를 확인만 하고 값을 바꾸지 않는다.

### B3-1-61. localhost 200을 확인한다 [필수]

EC2 안에서:

```bash
curl -i http://localhost
```

확인:

1. HTTP status가 200인지.
2. 응답 본문이 Nginx 기본 페이지인지.
3. `Server: nginx` 같은 header가 있는지.

통과:

- “EC2가 켜져 있다”와 “Nginx가 localhost:80에서 200을 준다”를 별도로 말한다.

### B3-1-62. Nginx 내부 실패를 가상으로 분석한다 [학습]

실제 서비스를 멈추지 않고 표에 적는다.

| 조건 | localhost 예상 |
|---|---|
| Nginx stopped | connection refused 가능 |
| 잘못된 root | 404 가능 |
| 파일 권한 문제 | 403 가능 |
| 다른 포트에서 대기 | 80 connection refused 가능 |

실제 실험은 증거·복구·승인을 준비한 경우에만 한다.

### B3-1-63. Nginx 로그 위치를 확인한다 [읽기]

OS에 맞는 로그 경로를 공식 문서와 서버에서 확인한다. 일반적으로 access log와 error log가 분리된다.

```bash
sudo tail -n 20 /var/log/nginx/access.log
sudo tail -n 20 /var/log/nginx/error.log
```

로그에 공인 IP·요청 정보가 보이면 공개하지 않는다.

## 11. B1-1 정적 파일을 Nginx에 배포한다 [필수]

### B3-1-64. 배포 파일 목록을 먼저 확인한다 [필수]

B1-1에서 다음을 하나씩 확인한다.

- `index.html`.
- `css/style.css`.
- `js/app.js`.
- `images/` 안의 이미지.
- API는 브라우저에서 외부 GitHub API를 호출하는 코드인지.

예상:

- HTML만 복사하면 상대 자원이 404가 된다.

### B3-1-65. Nginx document root를 읽는다 [읽기]

Nginx 설정에서 `root` 지시어와 index 파일을 확인한다. 정확한 경로는 OS/설정에 따라 다르므로 추측하지 않는다.

```bash
sudo nginx -T
```

출력에 개인 정보·호스트 정보가 있으면 문서에 그대로 붙이지 않는다.

### B3-1-66. 배포 전 파일 경로를 맞춘다 [필수]

1. B1-1 상대 경로와 Nginx root를 비교한다.
2. `css/style.css`가 `<root>/css/style.css`가 되는지 계산한다.
3. `js/app.js`와 `images/...`도 같은 방식으로 계산한다.
4. 하나라도 경로가 안 맞으면 복사 전에 수정 계획을 세운다.

### B3-1-67. 파일을 한 묶음으로 복사한다 [승인 후 변경]

승인한 안전한 전송 방법을 사용해 B1-1 파일을 Nginx document root에 배치한다. 개인 키·비밀번호를 명령에 포함하지 않는다.

복사 후:

```bash
find <document-root> -maxdepth 2 -type f
```

예상:

- index, css, js, images 파일이 모두 존재한다.

### B3-1-68. 서버 내부에서 정적 자원을 확인한다 [필수]

EC2에서 각각 요청한다.

```bash
curl -i http://localhost/
curl -I http://localhost/css/style.css
curl -I http://localhost/js/app.js
```

이미지 경로도 실제 이름 하나를 사용한다.

예상:

- HTML·CSS·JS가 200이다.

실패:

- HTML 200, CSS 404라면 document root·상대 경로·파일명을 확인한다.

### B3-1-69. 브라우저용 API 요청과 서버 파일 요청을 분리한다 [학습]

- HTML/CSS/JS/image는 EC2 Nginx에서 제공한다.
- GitHub API는 브라우저의 JavaScript가 `api.github.com`으로 요청할 수 있다.
- 두 요청은 서로 다른 host·Network entry·실패 원인을 가진다.

통과:

- Nginx HTML 200만으로 GitHub API까지 성공했다고 말하지 않는다.

### B3-1-70. 배포 내부 검증을 기록한다 [기록]

```text
배포 소스 버전:
Nginx document root:
HTML localhost status:
CSS localhost status:
JS localhost status:
image localhost status:
API는 어디에서 요청되는가:
아직 외부에서 확인하지 않은 것:
```

## 12. 외부에서 HTTP 80을 검증한다 [필수]

### B3-1-71. 검증 방식 A/B를 선택한다 [필수]

- A: 외부 브라우저에서 `http://<public-ip>` 접속.
- B: 외부에서 `GET http://<public-ip>/health` 호출 후 200과 고정 응답.

사용자의 과제 목적에 맞는 하나를 선택하고 README에 기록한다. 실제 Public IP는 공개할 때 주의한다.

### B3-1-72. 외부 요청 전 예상 경로를 말한다 [필수]

브라우저에서 주소를 열기 직전에 말한다.

```text
내 브라우저
→ public IP:80
→ IGW
→ Route Table 기본 경로
→ Public Subnet
→ EC2 ENI
→ Security Group HTTP 80 허용
→ Nginx 80 listening
→ document root/index.html
→ 200 응답
```

실패할 경우 어느 지점에서 멈출지 하나의 가설을 먼저 세운다.

### B3-1-73. 외부 브라우저 또는 curl을 실행한다 [승인 후 변경 아님, 실제 검증]

선택 A:

1. EC2와 다른 외부 브라우저/네트워크를 사용한다.
2. `http://<public-ip>`를 연다.
3. 화면이 표시되는지 확인한다.
4. DevTools Network에서 document status를 확인한다.

선택 B:

```bash
curl -i http://<public-ip>/health
```

정상 기대:

- 200 OK와 README에 적은 고정 응답.

### B3-1-74. 내부·외부 증거를 나란히 기록한다 [필수]

| 위치 | URL | 기대 | 실제 status | 증거 |
|---|---|---|---|---|
| EC2 내부 | localhost | 200 | | 터미널 |
| 외부 | public IP | 200 | | 브라우저/curl |

내부 성공만 있고 외부 성공이 없으면 과제 외부 접속 완료로 표시하지 않는다.

### B3-1-75. 외부 화면에서 B1-1 기능을 다시 실행한다 [필수]

1. 여섯 섹션.
2. CSS 스타일.
3. JavaScript 메뉴·테마·스크롤.
4. 폼 검증.
5. GitHub API 카드.
6. 이미지.

Network에서 HTML/CSS/JS/image/API를 각각 확인한다.

### B3-1-76. 외부 검증 증빙을 저장한다 [필수]

- 선택한 A/B 방식.
- 검증 시각(현재 시간 도구로 확인).
- URL 또는 IP를 공개해도 되는지 판단.
- 브라우저 화면 또는 curl 응답 캡처.
- 내부 localhost 결과.
- 외부 public IP 결과.

개인 키·비밀번호·세션·불필요한 계정 정보는 캡처하지 않는다.

## 13. 트러블슈팅을 한 건 실제 보고서로 만든다 [필수]

### B3-1-77. 실제 증상 하나를 선택한다 [필수]

실제 문제가 있었다면 실제 오류를 쓴다. 문제가 없으면 “통제된 실험” 또는 “가상 시나리오”라고 표시한다.

예시:

- 외부 timeout.
- HTML 200/CSS 404.
- SSH publickey denied.
- localhost connection refused.

### B3-1-78. 증상을 그대로 보존한다 [필수]

다음 중 가능한 것을 저장한다.

- 브라우저 오류 화면.
- HTTP status.
- curl 출력.
- Nginx error log 관련 줄.
- Security Group·Route Table 상태.
- EC2 상태.

공개하면 안 되는 주소·계정·로그 정보는 가린다.

### B3-1-79. 원인 가설을 세 개까지 순위화한다 [학습]

예를 들어 외부 timeout이면:

1. HTTP 80 Security Group 누락.
2. Route Table/IGW/Public IP 문제.
3. Nginx가 80에서 대기하지 않음.

각 가설에 예측을 붙인다.

- 가설 1이면 SG inbound에 80이 없을 것이다.
- 가설 2이면 public 경로/주소 관계가 끊겨 있을 것이다.
- 가설 3이면 EC2 내부 localhost 또는 listening 확인이 실패할 것이다.

### B3-1-80. 가장 싼 읽기 확인부터 한다 [필수]

다음 순서로 조회한다.

1. 사용한 주소·포트.
2. EC2 Running/Public IP.
3. Security Group 80/22.
4. Route Table association/default route.
5. IGW attachment.
6. EC2 내부 `ss`, `nginx -t`, `curl localhost`.
7. Nginx logs.

한 번에 여러 설정을 바꾸지 않는다.

### B3-1-81. 한 가지 조치만 한다 [필수]

원인이 확인된 뒤 한 가지 설정만 수정한다.

- SG에 80 추가.
- Route Table association 수정.
- Nginx 시작.
- document root 파일 배치.

변경 전 상태와 변경 후 상태를 기록한다.

### B3-1-82. 같은 요청을 다시 실행한다 [필수]

같은 URL·같은 방식으로 재검증한다.

- 성공하면 무엇이 원인이었는지 설명한다.
- 실패하면 기존 가설을 폐기하고 새 가설을 세운다.
- 세 번 이상 수정해도 안 되면 더 넓은 변경을 하지 말고 사용자와 구조를 다시 검토한다.

### B3-1-83. 보고서를 작성한다 [필수]

`docs/troubleshooting.md`를 만들고 아래 형식을 쓴다.

```markdown
# 트러블슈팅 보고서

## 증상

## 실행 전 예상

## 원인 가설

## 조치 후 결과

## 재발 방지

## 실제 오류/통제 실험/가상 시나리오 구분
```

### B3-1-84. 트러블슈팅 회상 시험

문서를 덮고 다음에 답한다.

- timeout과 connection refused의 첫 확인 위치는 어떻게 다른가?
- localhost 200인데 외부 timeout이면 어떤 계층 후보가 남는가?
- 왜 한 번에 여러 규칙을 바꾸면 안 되는가?
- 증상과 원인을 보고서에서 어떻게 분리했는가?

## 15. 리소스를 안전하게 정리하고 비용을 확인한다 [필수]

### B3-1-89. 증거를 먼저 저장한다 [필수]

삭제 전에 다음을 저장한다.

- 외부 접속 화면.
- 내부 curl 결과.
- 아키텍처 다이어그램.
- 트러블슈팅 보고서.
- 실제 리소스 inventory.

삭제 후에는 주소와 로그가 사라질 수 있으므로 증거를 먼저 남긴다.

### B3-1-90. EC2를 종료한다 [승인 필요]

1. 인스턴스 ID를 다시 확인한다.
2. 다른 인스턴스가 아닌지 확인한다.
3. 사용자의 삭제 승인을 확인한다.
4. Terminate를 실행한다.
5. Terminated 상태를 읽어 확인한다.

Stop과 Terminate를 혼동하지 않는다.

### B3-1-91. EBS·EIP·추가 서비스 잔여물을 확인한다 [필수]

서울 리전에서 다음을 하나씩 조회한다.

- Volumes.
- Snapshots.
- Elastic IP.
- NAT Gateway.
- Load Balancer.
- RDS.

이번에 미생성인 것은 미생성으로 체크한다. 남은 것은 삭제 승인 후 처리한다.

### B3-1-92. 네트워크 리소스를 의존성 순서로 정리한다 [승인 필요]

1. EC2 의존성 제거.
2. EIP 해제.
3. IGW detach.
4. Subnet 삭제.
5. Route Table association/Route Table 삭제.
6. VPC 삭제.

각 단계 후 목록을 다시 조회하고 ID를 확인한다.

### B3-1-93. Billing과 리소스 목록을 다시 확인한다 [필수]

- 서울 리전 리소스 목록이 비었는가?
- 다른 리전에 실수로 만든 것은 없는가?
- EBS/EIP/NAT 등 비용 가능 항목이 남지 않았는가?
- Billing 반영 지연 가능성을 기록했는가?

금액이나 계정 정보를 채팅에 복사하지 않는다.

### B3-1-94. 정리 회상 시험

- Terminate와 Stop은 어떻게 다른가?
- EC2 외에 왜 EBS·EIP를 확인하는가?
- 삭제 전에 증거를 저장하는 이유는?
- 리소스 목록과 Billing을 둘 다 확인하는 이유는?

## 16. 독립 트러블슈팅과 선택 확장 [필수 학습/선택]

### B3-1-95. 네트워크 실패를 독립적으로 분석한다 [필수 학습]

문제:

> IGW는 연결되어 있고 EC2 내부 localhost는 200인데 외부 브라우저는 timeout이다.

문서를 닫고 후보를 세 개 순위화한다.

- Route Table association/default route.
- Public IP/주소.
- Security Group HTTP 80.
- OS/Nginx 상태도 이미 내부 200으로 일부 제외할 수 있다.

각 후보의 확인 명령·콘솔 위치를 적는다.

### B3-1-96. SSH 실패를 독립적으로 분석한다 [필수 학습]

문제:

> EC2는 Running인데 SSH에서 `Permission denied (publickey)`가 난다.

분석 순서:

1. 키 파일이 맞는가.
2. Linux user가 이미지와 맞는가.
3. 인스턴스 생성 시 연결한 키와 같은가.
4. 파일 권한/SSH 클라이언트가 키를 읽는가.
5. Security Group 22는 timeout 문제와 별도로 확인한다.

### B3-1-97. HTML 200/CSS 404를 독립적으로 분석한다 [필수 학습]

문제:

> 외부 브라우저에 HTML 글자는 보이지만 디자인이 없고 Network에서 CSS 404.

후보:

- Nginx root.
- 파일 복사 누락.
- 상대 경로.
- 파일명 대소문자.

한 가설씩 확인한다.

### B3-1-98. HTTPS 또는 Docker를 하나만 고른다 [선택]

필수 경로와 정리가 끝난 후에만 선택한다.

선택 전에 기록한다.

- 추가 리소스·포트.
- 예상 비용.
- 인증서 또는 컨테이너 개념.
- 실패 시 원래 HTTP/Nginx로 돌아가는 방법.
- 삭제 대상.

둘을 동시에 시작하지 않는다.

### B3-1-99. 도움 없이 전체 경로를 설명한다 [필수 학습]

다음 질문에 답한다.

1. 브라우저 요청이 어느 계층을 통과하는가?
2. HTTP 80과 SSH 22가 왜 다른가?
3. EC2 Running과 Nginx active의 차이는?
4. localhost 200과 외부 200의 차이는?
5. timeout·refused·404의 첫 확인 위치는?
6. 왜 리소스를 삭제해야 하는가?

막힌 질문만 질문하고, 답을 받은 뒤 자기 말로 다시 설명한다.

- GitHub Pages와 EC2는 각각 다른 배포 환경이다.
- 로컬 성공이 EC2 성공을 보장하지 않는다.
